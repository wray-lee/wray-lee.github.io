ZTE F50(MU300)に Debian を入れるメモ

2026-10-26 ~ 27、ZTE F50 ストレージ版を B08 から B09 に書き換え、root 化、userdata 縮小、Debian unstable（カーネル 7.3）をインストールして Android + Debian デュアルシステムにした。前半は日常的な使い方、後半はインストール手順、踏んだ罠、リバース結果。

一、まずここ:日常使用

デバイスの現在の状態

ZTE F50 / MU300 ストレージ版、Unisoc UMS9620、eMMC 234 GiB、電源ボタンなし、画面なし。

  • Android は B09 ファームウェア（F50_FLYMODEM_ZYV1.0.0B09）、root 化済み（Magisk 28.1、Shell は許可済み）、slot a にインストール、userdata は約 30 GiB に縮小。
  • Linux は Debian forky/sid、カーネル 7.3.0、slot b と userdata 後の 198 GiB 領域にインストール（ext4、使用可能約 191G）。デフォルトで Linux を起動し、連続起動失敗 5 回で Android に戻る。
  • bootloader は locked 表示、パッチ版 trustos は書き込み済み、locked 状態でも Linux は起動できる。
  • Linux 内のユーザーは wray のみ（sudo、docker グループ、zsh + oh-my-zsh + powerlevel10k）。インストーラが作成した ubuntu ユーザーは削除済み。root はロック（PermitRootLogin no）、root が必要なら sudo -i または adb shell を使う。
  • docker 28.5、ufw、neovim、fzf、zoxide、lsd、duf、fastfetch、git、curl などをインストール済み。タイムゾーン Asia/Tokyo。
  • SIM なし、よってセルラーネットワークなし。ネット接続は Wi-Fi（自宅ルーター RayWrt に接続、デバイス IP 10.17.1.143）または PC をプロキシにする。
  • wray のパスワードは F:\Projects\tmp\f50\wray-credentials.txt（平文、使用後は自分で処理）。answers-install.txt 内のインストールパスワードは消去済み。

デバイスへの接続

方式 コマンド 説明
Wi-Fi ssh wray@10.17.1.143 デバイスがルーターに接続しているときに使用、IP はルーター割当に従う
USB ネットワーク ssh wray@192.168.77.1 USB ケーブルで PC に直結、NCM NIC、Windows 11 はドライバ不要、PC は 192.168.77.111 を取得
USB adb adb shell そのまま root shell

SSH は鍵のみ（Windows の ~/.ssh/authorized_keys 内の 3 本:Wray-Arch ed25519、Wray-Win rsa、スマホ u0_a355）。Linux 内の adb も /etc/mu300/adb_keys 内の鍵のみ（adb_auth=keys）、すべての PC に開放しているわけではない。インストーラ末尾の ssh ubuntu@192.168.77.1 は固定文言で、実際には wray@ を使う。

Git Bash で adb に /data/... のようなパスを渡すときは、先に export MSYS_NO_PATHCONV=1 を実行する。そうしないとパスが Windows パスに書き換えられる。

システム切り替え:必ず覚えておく罠

Android から mu300-linux を実行して Linux に入るのは「一回だけの試し起動」であり、このとき /etc/mu300/default-boot はまだ android。Linux 内でそのまま reboot すると Android に戻り、「再起動後に自動フォールバック」に見えるが、実際はそういう設計。Linux を常にデフォルトにするには、入った後に一度 sudo mu300-next-boot linux を実行する。現在は設定済み（default-boot の内容は linux）。

2026-10-27 の例:起動ログに mu300-next-boot: default boot is not linux, nothing to do があり、前回のカーネルログは pstore にあり、正常な Restarting system で、クラッシュではない。

MU300_BUSYBOX を必ず付ける。Magisk 同梱の busybox はこの機体では壊れている（--list が空、readlink -f が空を返す）ため、付けないと misc resolves outside /dev/block () を報告し、status は「boot_b は Android イメージで、Linux 未インストール」と誤判定する。それは誤判定で、Linux は消えていない。インストールパッケージ内の busybox を使い、しかもファイル名は必ず busybox でなければならない（マルチコールバイナリは argv[0] で applet を探すため、名前を変えると applet not found を報告する）:

切り替え後、status は boot_b: the Linux boot image を表示するはず。slot 状態確認時の出力は slot a priority 15, tries 1, successful 1、slot b priority 14, tries 1, successful 0 の形。

PC がないときの保険:Linux 起動中に 5 回連続で電源断すると自動で Android に戻る。

Wi-Fi:デバイスをルーターに接続する

SC2355 の無線は一度に一つのことしかできない:ホットスポット（AP）またはクライアント（station）。ルーターに接続すると、デバイス自身のホットスポット FRayWrt は切れる。ホットスポットからクライアントへの変更は再起動が必要、クライアントからホットスポットへは不要。WPA2 と WPA2/WPA3 混合のみ対応、純粋な WPA3 と Wi-Fi 7 のネットワークは拒否される。USB の 192.168.77.1 は影響を受けない。

無線がこの時点でまだホットスポットモードなら、scan / connect は “the radio is an access point right now … cannot turn it back into a client without a reboot” を表示する。これは故障ではなく、connect が先にネットワークを保存し、再起動後に参加する。パスワードは対話入力または --password-file を使い、コマンドラインに書かない（journal と ps に入る）。設定は /etc/mu300/wifi-client.conf（0600、root）にあり、内容は SSID、PSK、ENABLE=1、METRIC=50。接続後は Wi-Fi アップリンクがモバイルデータより優先され、理論上 NAT 経由で USB クライアントに共有できる（未実測）。

このデバイスはすでに自宅ルーターに接続し、起動時自動参加（サービス mu300-wifi-client.service が wifi-client up を実行）。

時計が正しくないときは先に時刻合わせ（date -u -s @<时间戳>）、そうしないと TLS が失敗する。現在は Wi-Fi で直接ネット接続できるため、通常この手順は不要。

ファイアウォール

インバウンドルールは現在 ufw が管理:デフォルト拒否、アウトバウンド許可、フォワード拒否、22（tcp/udp、IPv6 含む）のみ許可。

wifi-client は独自の nft テーブル inet mu300_wifi_filter を持つ。元の input チェーンは wlan0 上の、確立済み接続、DHCP 応答、レート制限 ping 以外のインバウンドをすべて落とすため、LAN からデバイスに ping は通るが SSH できない（sshd 自体は *:22 を listen していて問題ない）。現在この input チェーンは削除し、forward チェーンだけ残している（アップリンク共有時に内部ネットワークへの転送を禁止）。wifi-client status は正常なら shared with the LAN (internet only) を表示する。mu300_wifi_filter is not as wifi-client puts it を表示するなら、ルールとスクリプト生成内容が不一致。

パッチスクリプトは F:\Projects\tmp\f50\tools\wifi-client.noinput.sh、元ファイルのバックアップは /opt/mu300/bin/wifi-client.orig2。パッチはインストール済みファイルを変更するため、システムアップグレードや再インストールで上書きされる。その時は再適用が必要。プロジェクト自身の mu300_filter（/etc/mu300/firewall.nft）はセルラーポート、docker0、br-* のみ管理し、wlan0 には影響しない。

日常メンテナンス

Linux 内の adb と Android の adb は別物。Linux 側の adbd はイメージ同梱の静的 aarch64 プログラム（/opt/mu300/bin/adbd）で、mu300-adbd.service により起動時自動起動し、自身を USB gadget（FunctionFS）に追加する。Android 内の HTTP スイッチや Samba トリガーとは無関係。adb 接続が終わるたびに gadget は unbind され、スクリプトが再び bind するため、PC 側では抜き差ししたように見える。

問題が起きたら

SSH に接続できない。 まず ping。ping は通るが SSH 不可なら sudo ufw status と wifi-client status を確認。ping が通らないなら、まずデバイスが Android に戻っていないか確認（Android に 22 番ポートはない）。

Linux が起動しない / 前回のログを見たい。 デバイスは自動再試行し、連続失敗 5 回で Android に戻る。Android 内で Linux ルートパーティションを読み取り専用マウントして journal を見られる。領域オフセットはインストール時に計算された値（38700843008）、ルートファイルシステムはマウントポイント下の ubuntu/ ディレクトリ内:

journal はバイナリ形式なので、PC（または WSL）に持ってきて journalctl --file=<文件> で読む。前回クラッシュのカーネルログは Android の /sys/fs/pstore/console-ramoops-0。MU300_OFF を付けないと NO-EXT4 magic=0000 を報告する。デフォルトオフセットはこの機体の領域ではないため。

Android に adb がない。 B09 を書き込んだ後や工場出荷状態に戻した後でも adb は使える。persist.sys.usb.config=adb と persist.adb.tcp.port=5555 が persist パーティションに存在するため。万一本当になくなったら、後述の「無線 adb はどう有効化するか」の節を見て、F:\Projects\tmp\f50\re\f50_wireless_adb.py を使う。

完全に文鎮化した。 テストポイントを短絡してダウンロードモードに入り、B08 の元バックアップで書き戻す。

避けるべき罠（早見表）

  1. mu300-update は .disabled に改名済み。その apply はシステム全体を Ubuntu 24.04 に置き換え、自作 Debian を破壊する。この種のアップデータを繰り返し実行しない。Debian の更新は apt を使う。
  2. コントロールパネルと mu300-os はこのシステムを Ubuntu 26.04 と見なし、バージョン番号は空表示になるが正常。
  3. Android から Linux への起動は一回限り。上記参照。
  4. Debian sid の wpa_passphrase にはバグがあり、wifi-client connect のオリジナルは could not build the wpa_supplicant configuration を報告する。パッチ済み（完全なコードは後述）。
  5. デバイスに python3 と openssl はない。スクリプトは sh / awk / sed で書く。
  6. sid はローリングリリース。full-upgrade の前に考える。問題が起きたときに戻せる公式イメージはない。
  7. ホットスポット国コード COUNTRY=TR はプロジェクトのデフォルト値。日本では JP に変更すべきだが、まだ変更していない。
  8. 「一時無線 adb ツール」を繰り返し実行すると破壊的。そうしない（後述）。

三、どうやってインストールしたか

1. ダウンロードモードに入る（この機体最大の罠）

直結 --kickto 2 はこの機体では常に失敗:ログに kick reboot timeout が出るが、spd_dump の終了コードは 0、bat 末尾には pause もあり、正常終了に見えるが実際には 1 バイトも書かれていない。以前「B09 を書き込んだのにまだ B08」だったのはおそらくこれ。

使えるのは「短絡モード」コマンドで、--kickto を付けず、FDL1 と FDL2 を手動ロードする:

操作順:ケーブルを抜く → テストポイントを短絡 → 短絡したままケーブルを挿す（コマンドは先に起動していても、すでに接続していてもよい）。usb_send failed (0 / 1) が一度出るのは接触不良、やり直す。成功したかどうかはログの Write Part Done だけで判断し、終了コードは見ない。

2. B09 を書き込む（userdata を消去）

書き込み前に、必ず B08 の元バックアップがあることを確認する。ROM 書き込みは ztepersist、splloader などのデバイスパーティションを上書きする。

zte-f50-b09\ 下のすべての .bin（splloader、ztepersist、2GB の super、misc 含む）を書き込み、合計約 2.7GB。

3. root + パッチ trustos

現在の slot（slot a）の trustos_a と boot_a のみ書き込み、userdata は消去しない。f50b09_t.bin は 5178856 バイト（MD5 先頭 a110ecb1）で、作成者パッケージ内の trustos.bin と同じ。boot は magiskf50b09.img（0e9e8a4d）を使用。作成者 kkroot の boot.bin（f2e8db4a）は別ファイルで、どちらも Magisk イメージ。書き込み後 ro.boot.flash.locked はまだ 1 を表示するが、Linux は起動できる。

4. adb

B09 書き込み後、または userdata 縮小後の工場出荷状態戻し後でも adb は使える。この ROM には UFI-TOOLS（com.minikano.f50_sms）と Magisk stub が同梱され、persist.sys.usb.config=adb、persist.adb.tcp.port=5555 は persist パーティションに保存され、工場出荷状態に戻しても消えない。B09 書き込み直後の最初の一度だけ、「一時無線 adb ツール」で有効化する必要がある（第五部参照）。ファームウェアの adbd は鍵を検証しない:ro.adb.secure=1、ただし /data/misc/adb/adb_keys が存在しなくても接続でき、ペアリング不要。

5. Magisk

  1. adb install Magisk_28103_origin.apk。root 後デバイス上には stub しかなく、バージョン表示は 1.0。
  2. アプリを開いて「環境を修復」、再起動。
  3. scrcpy で画面に接続し、Shell に root 権限を付与。
  4. adb shell su -c id は uid=0 のはず。修復前は su が PATH になく、/debug_ramdisk/su のみ。

userdata 縮小による工場出荷状態戻し後、Magisk のアプリは残るが、再度修復と権限付与が必要。

6. インストーラと userdata 縮小

インストーラは PowerShell 版 install.ps1 を使用（本機に lz4 なし）。Git Bash で実行する前に三つの環境罠を処理する:

読み取り専用チェック:install.ps1 -Check -Lang en。

userdata 縮小は回答ファイル（-AnswersFile）を使用。回答変数は install.sh 先頭コメント参照。どれか一つの変数が欠けると、インストーラは質問箇所で no answer to the question ... set MU300_ANS_xxx を報告して中止し、中止時には何も書かれていない。

結果:userdata は 228.19 GiB から 30.19 GiB に縮小、後ろに 198.00 GiB が空き、Android は recovery で工場出荷状態に戻る。

7. Debian パッケージをインストール

カスタムパッケージで続行インストールすると失敗:The prepared installation cannot be continued: this installer's tools or the package differ。原因はトランザクション内の payload identity が縮小時（当時パッケージなし）に計算された値で、カスタムパッケージインストール時に identity が変わるため。対処は -NoResume を追加。領域先頭にはインストーラ自身が書いた token があり、「unpartitioned space is not empty」と表示されるので MU300_ANS_OVERWRITE=overwrite と答える（この領域は自分で切り出したもので、空であることを確認済み）。

完全な回答ファイル:

コマンド:

インストール後デバイスは自動再起動して Linux に入る。今回のインストールログの領域オフセットは 38700843008、サイズ 198.0 GiB、ext4 を作成し、Linux 領域、boot_b、32 バイトの misc を書き込み、boot_a、GPT、userdata は変更しない。

インストール後デバイス上では /etc/mu300/adb は on、adb_auth は keys。つまり USB adb は /etc/mu300/adb_keys 内の鍵のみ受け入れる。

五、Wi-Fi クライアントの sid バグとパッチ

ルーター接続時、wifi-client connect が could not build the wpa_supplicant configuration を報告。

調査過程。ユーザーはまず “the radio is an access point right now … cannot scan either”（正常な案内）を見て、案内に従い connect した後に上記エラー。grep -n "could not build the wpa_supplicant" /opt/mu300/bin/wifi-client で 832 行目を特定、そこは network_block()（約 733–755 行）を呼ぶ。関数内で h=$(printf '%s\n' "$2" | wpa_passphrase "$1" | sed … psk=<64位hex>)、h が空なら return 1。デバイス上で直接 printf '%s\n' testpass1234 | wpa_passphrase test を試す:何も出力なし。

根本原因。Debian sid の wpasupplicant 2.11 では、wpa_passphrase がパイプからパスワードを読むときに stdin に対して tcgetattr を呼び、非端末で失敗し出力なし、network_block() が PSK のハッシュを取得できない。Ubuntu の旧版にはこの問題なし。

パッチ方針。wpa_passphrase が成功すれば従来通りハッシュを使用。失敗すれば psk="密码" に戻し、wpa_supplicant 自身に PBKDF2 を計算させる。パスワード長は 8–63 文字。設定ファイルは 0600 root。SAE 経路は元々平文 sae_password を書くので安全性は同等。ユニットテストで WPA2、WPA2/WPA3（SAE）、オープンネットワーク、短いパスワード（失敗を返す）の 4 種出力を確認し、すべて正しい。制限:パスワードに非 ASCII や二重引用符が含まれる場合は問題があるかもしれないが未テスト。

4. Web バックエンドで USB_PORT_SETTING は実際に何をするか

逆コンパイル /system/priv-app/ZteWebServer/ZteWebServer.apk より（プロセス com.zte.web、8080 を listen、sharedUserId=android.uid.system）。完全レポートは F:\Projects\tmp\f50\zteweb\notes\。

USB_PORT_SETTING は一つのことだけ:システム設定 Settings.Global adb_enabled を書く（1 がオン、0 がオフ、その他は 0 扱い）。persist.sys.usb.config / sys.usb.config は書かず、UsbManager も呼ばず、shell も実行せず、ブロードキャストも送らず、再起動もしない。実際に反映されなくても success を返す。状態照会 cmd=usb_port_switch が読むのも adb_enabled で、USB の実状態ではない。

実際に効くのは system_server（証拠は同機 B09 バックアップ内の services.jar）:

  • AdbService.setAdbEnabled() は値が実際に変化した場合のみ続行し、同値ならそのまま return。実際に変化したとき ctl.start adbd / ctl.stop adbd、コールバック UsbDeviceManager。
  • UsbDeviceManager.setAdbEnabled():オン → persist.sys.usb.config="adb";オフ → "charging";その後 sys.usb.config を再設定。
  • 起動時 AdbService.systemReady() は逆:persist.sys.usb.config を読み、adb を含めば adb_enabled を 1 に、そうでなければ 0 に設定し、前回 Web が Settings に書いた値を上書きする。
  • init 内:on post-boot && property:sys.usb.config=none → setprop sys.usb.config ${persist.sys.usb.config};on property:sys.usb.config=adb && property:sys.usb.configfs=1 → start adbd。
  • SettingsProvider は「同じ値の書き込み」でもオブザーバー通知しないため、1 の重複書き込みは完全な no-op。

REBOOT_DEVICE は先に success を返し、500ms 後に PowerManager.reboot("manualreboot")。UsbTools（オンで rndis,diag,diag_mdm,adb、オフで rndis、最後に無条件再起動）は DEVELOPER_MODE_SETTING / SET_DEVICE_MODE からのみ呼ばれ、本 APK の DeveloperModule は USB_PORT_SETTING のみ登録しているため、この経路はこのファームウェアでは到達不能。Web UI は index.html#usb_port → js/adm/usb_port.js で、送信するのは goformId=USB_PORT_SETTING + usb_port_switch=1/0、Apply を押して初めてリクエスト送信、radio だけ押しても送信されない。APK 内に service.adb.tcp.port / persist.adb.tcp.port を書いたり adbd を起動停止するコードは一切ない。デバイス上の persist.adb.tcp.port=5555 は ROM 元々の永続プロパティ。

5. 「adb がないときどう有効化するか」

  • 有線 adb:adb_enabled に実際の 0→1 変化を起こさせる。フレームワークは即座に ctl.start adbd、persist.sys.usb.config を adb に書き、USB を再設定する。コード上は再起動不要。REBOOT_DEVICE は再起動後に persist=adb に従って安定して USB を再構成するためで、最も確実な方法。
  • Web 上でスイッチを押すだけでは効かない理由:スイッチが元々 1 の場合（UI 表示は adb_enabled で、persist でも adbd の実状態でもない）、再度 1 を送信すると同値で、二重にショートカットされて no-op。persist.sys.usb.config は adb に書かれず、再起動時に systemReady() が persist から再計算して 0 に戻る。よって adb は依然としてなく、UI は ON のまま。元ツールが先に 0 を送ってから 1 を送るのは、強制的に実際の 1→0→1 変化を作るため。手動なら:Web で先にオフ、Apply、再度オン、Apply。
  • 二次的な可能性:radio を押して Apply を押していない;非同期 persist 書き込みより再起動が先;特定 SIM 状態で ZTE_ADB_USB_SECURITY_RESTRICTION が adb を強制オフ;adbd または USB エンドポイントが固まり再列挙が必要。
  • 無線 adb の TCP listen:adbd は起動時に service.adb.tcp.port / persist.adb.tcp.port を読む。この ROM は persist.adb.tcp.port=5555 を持つため、adbd 起動と同時に TCP 5555 も listen する。Samba の仕組みはこのファームウェアでは実行できない（smb.conf は immutable）うえ、必須でもない。

現場確認（デバイスが Android 時、Web インターフェースにログインして照会）:usb_port_switch → '1'、developer_mode_enable → '1';デバイス上 settings get global adb_enabled = 1、persist.sys.usb.config = adb、sys.usb.config = rndis,mtp,adb、init.svc.adbd = running、persist.adb.tcp.port = 5555。二つの診断インターフェースはログイン後 adb なしで使える:

  • GET /goform/goform_get_cmd_process?isTest=false&cmd=usb_port_switch → adb_enabled
  • GET /goform/goform_get_cmd_process?isTest=false&cmd=developer_mode_enable → persist.sys.usb.config に adb が含まれるか

前者が 1、後者が 0 なら、上記「UI は ON だが persist に adb がない」分岐で、先に 0 を送ってから 1 を送ればよい。

リスク:単独で usb_port_switch=0 を送る（実際の 1→0）と persist.sys.usb.config が charging に書かれる。その後の 1 が成功しない場合、再起動後 USB は充電のみになり、RNDIS / ECM と Web バックエンドの両方が到達不能になる可能性。復旧手段がないときは 0 を単独で送らない。元プログラムと我々のスクリプトが第 1 ステップ後に失敗すると、この悪い状態が残る。フレームワーク側の証拠は同機 B09 バックアップイメージ由来で、デバイスがこのファームウェアでない場合、services.jar の詳細は異なるかもしれない。

adb connect 192.168.0.1:5555 失敗:10053 / 10060;デバイス上 [::]:5555 は listen 中、iptables filter INPUT はデフォルト ACCEPT だが、PC から Wi-Fi 経由で入れず、原因未調査

スクリプトを修正した点:

  1. Cookie 再利用により 2 回目ログインが失敗:第 1 ステップのログイン後に古い Cookie を第 2 ステップのログインリクエストへ持ち込み、デバイスが {"result":0} を返し Set-Cookie を送らず、login: no Set-Cookie を報告。元プログラムは各ステップで新しい zreq プロセスを使い、ログイン時に Cookie がない。毎回 login() 前に Cookie をクリアするよう変更。この問題はデバイスを USB デバッグオフ状態で止めることがあり、元プログラムの同種副作用の原因でもある。
  2. デフォルト動作を元プログラムと一致に戻す（--yes で再起動;以前はデフォルトで再起動をスキップし、USB adb が出なくなる）。
  3. SMB トリガーに impacket の純 Python 実装を追加（Windows はデフォルトで Guest SMB を拒否し、smbclient もない）。
  4. 第 5、6 ステップをベストエフォートに変更:失敗時は警告のみで adb connect を続行し、最終的に adb が接続できるかで判断。

その他の発見:

  • 有線 adb は HTTP の USB_PORT_SETTING と再起動で十分。
  • 再起動後 sys.usb.config は rndis,mtp,adb から ecm,mtp,adb に変化。Windows に ECM NIC ドライバがないため、PC の USB NIC が消え、HTTP チャネルは Wi-Fi（デバイスホットスポット接続）経由でなければ確実でない。
  • デバイス iptables の INPUT は送信元 192.168.0.0/24 の 8080 のみ許可し、adb forward のループバックから来た 8080 は落とされる。
  • persist.sys.usb.config は試験前後とも adb、スクリプト内の setprop persist.sys.usb.config adb,rndis は shell 権限では効かなかった。
  • USB adb と 192.168.0.1:5555 の二つのデバイスが同時に存在すると、コマンドは more than one device を報告するので、先に adb disconnect。
  • 元プログラムは毎回先に usb_port_switch=0 を送り、失敗しても復旧しないため、繰り返し実行すると persist.sys.usb.config を adb,rndis から adb に変え、192.168.0.1 を一時的に到達不能にする。よって繰り返し実行しない。

テスト後の復元:/data/samba/etc/ 内の sed 失敗で残った 12 個の一時ファイル（smb.conf と 6 桁ランダム文字）とスクリプトが作った smb.conf.bak.opener は削除済み。smb.conf の MD5 は前後一致（cf419aec312cf4b6abaa849d67e31093）、immutable 属性は未変更。USB デバッグスイッチは最終的にオン、persist.adb.tcp.port=5555、persist.sys.usb.config=adb はテスト前と同じ。Android 側に無害な /data/local/tmp/bbdir/busybox が残る（Linux 切り替えに必要、削除しない）。

Linux に切り戻すときに踏んだ罠は前述の Magisk busybox 問題。他に観察したこと:dd で出た boot_b の MD5（9d7a4a10…）がインストール時にプッシュした work/boot-linux-slotb.img（029289…）と不一致だが、内容は Linux イメージ（mu300 文字列を含み、Magisk なし、正常起動可能）。原因未調査（インストーラが書き込み前に処理したか、初回起動後に更新された可能性）。

七、未完了および未検証

  • SIM 挿入後のモバイルデータと USB 共有ネット接続の検証。
  • Wi-Fi ホットスポット（再起動で AP モードに戻る）、Bluetooth、GPU、modem の個別検証。
  • PC から Wi-Fi 経由で 192.168.0.1:5555 にアクセスするとタイムアウトする理由が未解明（ip6tables、raw / mangle テーブル、hostapd クライアント分離、adbd がループバックのみ listen しているかを見る必要）。
  • 新品デバイスで初めて adb を有効化する場合も、HTTP の 0→1 と再起動だけでよいか確認。
  • ホットスポット国コード COUNTRY=TR を JP に変更。
  • Android から Shell の Magisk root 権限を自動付与したい場合、root 後に magisk --sqlite でポリシーを事前設定する方法を研究できるが未試行。
  • 自動化構想:バックアップ検証、B09 書き込み、trustos + boot 書き込み（デバイスがダウンロードモード時）、Magisk インストール、--check、回答ファイル駆動の縮小とインストール、インストール後環境構築（setup-env.sh）はスクリプト化可能。必ず人手が必要なのは、テストポイント短絡、Magisk 修復後の Shell 権限付与、新品デバイス初回の adb 有効化。
