SPF とは

現在広く使われている送信プロトコル SMTP では、送信者は送信者のメールアドレスを任意に設定でき、誰でも boss@your-corp.com になりすまして他の人にメールを送信できます。そのため、SPF（Sender Policy Framework）の仕組みが提案され、電子メールの送信者（メール転送エージェント、MTA）を検証し、your-corp.com に認められたサーバーだけが boss@your-corp.com を送信者とするメールを送信できるようにします。メール受信側は SPF レコードと IP アドレスを用いて送信サーバーが正当かどうかを識別し、SPF レコードの指示に従ってメールの受信を許可するか拒否するかを判断します。

SPF レコードの形式

SPF レコードは複数のサブ項目の区切りとして単一の空白を使用し、各サブ項目は qualifier、mechanism、modifier などのコンポーネントで構成されます。解析時には左から右へマッチングし、いずれかのサブ項目がマッチに成功した場合、直ちにマッチング処理を中止し、qualifier に従って SPF 検証結果を返します。

SPF レコードは固定の v=spf1 で始まり、SPF バージョンを示します。現在は固定で spf1 です。

Qualifier と Mechanism

Qualifier

SPF に存在する qualifier は mechanism の前に置かれ、以下の 4 種類があります。このうち + はデフォルトの qualifier であり、省略できます。

Qualifier Result Explanation (対応する mechanism がマッチに成功した場合)
+ Pass 送信側のマシンが検査に合格し、本ドメインのメールボックスからメールを送信できるという明確な宣言
- Fail 送信側のマシンが検査に合格せず、本ドメインのメールボックスからメールを送信できないという明確な宣言
~ Soft Fail より弱い宣言で、送信側のマシンは検査に合格しなかったようだ
? Neutral 本ドメインの管理者は、送信側のマシンが検査に合格したかどうかを明確に宣言していない

Mechanism

all

all は常にマッチに成功します。そのため、all より後ろの mechanism は有効になりません。all は通常、最後の mechanism として qualifier と組み合わせ、「デフォルト動作」を設定するために使われます。つまり、ほかのポリシーがすべてマッチに失敗した場合、本ドメインがこうした漏れに対してどのような方針を取るか、というものです。

当サイトの SPF 設定 v=spf1 include:spf.mail.qq.com ~all を例にすると、include という mechanism がマッチに失敗した場合、最終的に all に到達してマッチに成功し、その qualifier に従って「soft fail」という結果を返します。一般にメール受信側はこのメールを拒否しませんが、メールを迷惑メールフォルダーに入れます。

include

include の形式は include: *domain-spec* です。これは再帰的な SPF 検証プロセスを 1 回トリガーし、メール受信側に domain-spec で設定された SPF レコードを検査させます。domain-spec の検証結果が pass である場合にのみ（注意：soft fail でも不可）、この mechanism はマッチに成功したと見なされます。

include メカニズムは「管轄境界をまたぐ」状況、すなわち必要な SPF ルールが本ドメインの管轄に属さないドメインの下に置かれている場合を処理するために想定されています。これはむしろ「サードパーティの依存ライブラリをインポートする」ようなもので、後述の redirect はむしろ「社内の共通コード」のようなものです。

exists

形式は exists: *domain-spec* です。受信側は指定ドメインに対して A レコード問い合わせを送信し（IPv6 であっても A レコード問い合わせを使用します）、何らかの応答があればマッチに成功します。比較的複雑な検証に使用できます。

ここで、domain-spec には以下のマクロを含めることができます：

マクロ 意味 例
s 送信者のメールアドレス hsiaoxychen@example.com
l 送信者の「ローカル部分」 hsiaoxychen
o 送信者のドメイン部分 example.com
d 現在検証中の SPF 権威ドメイン。通常は上記と一致しますが、include の解析時に変化する可能性があります example.com
i 送信側の IP 114.5.1.4
v IPv4 の場合は in-addr、IPv6 の場合は ip6 in-addr
h HELO/EHLO のドメイン mail.example.com

その他の Mechanism

その他の mechanism には a、mx、ip4、ip6、exists があります。これらの仕組みは比較的類似しており、理解しやすいため、以下のように整理します：

a 送信側 IP が指定ドメインの任意の A レコード（または AAAA レコード。今回の送信が IPv4 経由か IPv6 経由かによって決まります）の IP アドレスに一致すれば、マッチに成功
mx 送信側 IP が指定ドメインの任意の MX レコードに一致すれば、マッチに成功
ip4 送信側 IP が指定された IPv4 アドレス（範囲）に一致すれば、マッチに成功
ip6 送信側 IP が指定された IPv6 アドレス（範囲）に一致すれば、マッチに成功

Modifier

modifier の構文は mechanism と少し異なり、qualifier がなく、キーと値の区切りも : ではなく = です。現在、modifier には redirect と exp の 2 種類があります。exp は SPF 検証失敗後にサーバーへ説明テキストをどのように生成するかを伝えるためのもので、ここでは紹介しません。redirect は後続の SPF 検証プロセスを対象ドメインへ「リダイレクト」できます。たとえば gmail.com の SPF レコード：
