Explanation

​ rp_filter

​ is a network security protection feature of the Linux kernel for networking; it checks the source address and source network interface (network card) of data packets:

  • If set to 0 (i.e., disabled), all data packets are allowed through.

    • However, some packets that cannot be properly replied to (with no corresponding entry in the routing table) will also be handed to applications for processing, consuming extra system resources.

    • Still, the extra consumption should be very small, so setting the above two items to 0 is fine.

  • If set to 1 (strict mode), and the packet’s source network card is not the optimal network card for sending this packet (that is, if your machine were to reply to this address, it would pick a different network card), then this packet is

    dropped

    .

    • Having the source and the reply on different network cards is a very common situation in DN42, so you must never, absolutely never set rp_filter to 1!

  • If set to 2 (loose mode),

    theoretically

    , if the packet’s source address is not in the routing table (that is, the local machine does not know how to reply to this address), then this packet is dropped.

    • But theory is theory: in newer kernels (5.0+), in actual use a large number of normal packets with correct source addresses are still dropped. So do not use this mode; use 0 consistently.

  • Then, you absolutely must turn off your UFW and other tools that help you easily configure iptables firewalls.

OpenWrt Configuration (no shell required)

Configure the WAN port/firewall

At this point, even if you configure nothing at all, the external network can already connect to the internal network through zerotier.

  • But at this point, assuming your OpenWrt IP in the virtual network is 192.168.191.50, you can access the LuCI page, but all the ports you originally mapped for the WAN port will become completely inaccessible.
  • For example, if you originally configured external port 3389 on the WAN to map to port 3389 of the device 192.168.1.100 under the internal LAN, then you cannot access it via 192.168.191.50:3389, because the traffic does not come from the WAN but from the zerotier virtual network card, and its traffic cannot be forwarded to the destination.

Configuring it is also very simple.

Create an interface named: ZTVPN (any name will do)

Set the protocol to: DHCP 客户端 (because only this way can zerotier automatically assign an IP, without you needing to specify it yourself; specifying it yourself involves many parameters, and leaving them unmodified is also troublesome)

Remember: at this step, absolutely do not perform remote configuration while you are on the external network — it is very likely that a misconfiguration, or a loading-order problem, will cause you to lose access to the internal network.

In “Physical Settings”, check the virtual network card created by zerotier, the Ethernet adapter

In “Firewall Settings”, specify the WAN firewall zone — only this way can your ZTVPN network card apply the rules originally set for the WAN and for the network card of the default outbound public IP. Likewise, the port forwarding content configured earlier will also take effect.

Remember to save and apply.

A Solution for the LAN Side Being Unreachable After Setting Up Zerotier on OpenWrt

  1. Under Network – Interfaces, create a new interface with any name, and select the zt-prefixed network port automatically generated by zerotier as the port. Choose static as the network protocol (dropbear needs to bind an IP, so you need to configure the IP in zt as a static address, otherwise SSH will not work)
  2. Edit the port, create a new zone in that port’s firewall settings with any name (for example: zerotier), and add the newly created interface to this zone
  3. Under Network – Firewall, allow input, output, and forwarding for the zerotier zone
  4. Click the edit button, and in “Allow forward to destination zones”, check wan
  5. Restart the router
