    Unreal

    Dumper-7 extracts the SDK

    Import Basic.cpp Engine_functions.cpp CoreUObject_ functions.cpp
    Import additional libraries for whichever methods you use

    1. Core & UObject System

    These functions are used to get the game world instance, determine object types, and get class templates.

    Function Name Usage in Code Description
    UWorld::GetWorld() UWorld::GetWorld() Gets the current global world pointer (UWorld*), the entry point for all logic.
    AActor::IsA(...) Actor->IsA(...) Determines whether an Actor belongs to a specific class (e.g. whether it’s a monster or a player).
    UClass::StaticClass() APlayer_char_main_C::StaticClass() Gets the reflection object (UClass*) of a class, often used together with IsA.
    UObject::GetDefaultObj() APlayer_char_main_C::GetDefaultObj() Gets the default object (CDO) of a class. In the code it’s used to read the default movement speed and base values so the multiplier can be calculated.

    2. Actor & Spatial

    These functions are used to get or set an object’s position and distance in the game world.

    Function Name Usage in Code Description
    AActor::K2_GetActorLocation() Actor->K2_GetActorLocation() Gets the Actor’s current world coordinates (FVector).
    Note: the K2_ prefix is usually the version exposed to Blueprints; the native C++ version is GetActorLocation(), and the K2 version is commonly used in the SDK.
    AActor::K2_SetActorLocation(...) Actor->K2_SetActorLocation(TargetLoc, ...) Teleports the Actor to the specified coordinates. In the code this is used for magic bullet (teleporting the bullet onto the enemy’s head).
    AActor::GetDistanceTo(...) MyChar->GetDistanceTo(Actor) Calculates the 3D distance between two Actors (usually in centimeters).
    USceneComponent::K2_GetComponentLocation() Monster->see_Scene->K2_GetComponentLocation() Gets the world coordinates of a component (e.g. a monster’s vision component).
    USkinnedMeshComponent::GetSocketLocation(...) Monster->Mesh->GetSocketLocation(...) Gets the world coordinates of a specified bone or socket on a skeletal mesh. In the code it’s used to get the position of the monster’s head bone bone_head.

    3. Controller & Camera

    These functions involve control of the player’s viewpoint and the conversion from 3D world to 2D screen.

    Function Name Usage in Code Description
    APlayerController::ProjectWorldLocationToScreen(...) PC->ProjectWorldLocationToScreen(...) World to Screen (W2S). Converts 3D coordinates to 2D screen coordinates; it is the core function for drawing ESP and the aim crosshair.
    APlayerCameraManager::GetCameraLocation() PC->PlayerCameraManager->GetCameraLocation() Gets the camera’s current absolute world coordinates (used to calculate the origin of the aimbot angle).
    AController::GetControlRotation() PC->GetControlRotation() Gets the player’s current view rotation angles (Aim Angles).
    AController::SetControlRotation(...) PC->SetControlRotation(FinalRot) Sets the player’s view rotation angles. In the code this is used for aimbot (forcibly changing the view direction toward the enemy).

    4. Kismet Math Library

    UE’s built-in math library is used to perform complex vector and angle calculations, replacing hand-written math functions.

    Function Name Usage in Code Description
    UKismetMathLibrary::FindLookAtRotation(...) UKismetMathLibrary::FindLookAtRotation(Start, Target) Calculates the rotation (Rotator) needed to look from the start point toward the end point. In the code this is used to compute the ideal aimbot angle.
    UKismetMathLibrary::RLerp(...) UKismetMathLibrary::RLerp(Current, Target, Alpha, ...) Rotation interpolation. Used for smooth aimbot, so the crosshair doesn’t lock instantly but transitions smoothly to the target angle.

    Unity

    If we shift the target from Unreal Engine (UE) to Unity, the underlying programming paradigm changes from C++ (UE SDK) to C# (Unity API / Mono).

    Although the core logic (such as calculating distance and aimbot angles) is the same, the API names, object structures, and coordinate systems differ greatly.

    Below is a summary of the correspondence between the UE functions used in your code and their Unity equivalents:

    1. Core System & Object Retrieval (Core & Object)

    UE is based on the hierarchy UWorld -> Level -> Actor, while Unity is based on Scene -> GameObject -> Component.

    UE Native Function (C++) Unity Equivalent API (C#) Description
    UWorld::GetWorld() SceneManager.GetActiveScene() Unity has no single World pointer; it’s usually accessed via the scene manager.
    UWorld->PersistentLevel->Actors Object.FindObjectsOfType<T>()
    or GameObject.FindGameObjectsWithTag()    		 This is the biggest difference. Unity, i.e. what’s called “iterating GObjectList”. You usually need to iterate through all object lists to find enemies.
    Actor->IsA(Class) obj is EnemyClass
    or obj.GetComponent<EnemyClass>() != null    		 C# type checking is more intuitive; you can directly use the is keyword, or check whether a certain script component is attached.
    GetDefaultObj() (CDO) Prefab (Prefab) Unity has no CDO concept. You usually read the Prefab asset directly or hardcode the base values.
    Actor GameObject The base class for entities in the game.
    APlayerController No strict equivalent; usually scattered across Update() Player input logic is usually written in the MonoBehaviour script attached to the player character.

    2. Transform & Spatial

    Note the coordinate system difference: UE is Z-up (right-handed/left-handed mixed), Unity is Y-up (left-handed).

    UE Native Function Unity Equivalent API Description
    FVector Vector3 Basic vector struct (x, y, z).
    K2_GetActorLocation() transform.position Gets world coordinates.
    K2_SetActorLocation(...) transform.position = newPos Sets world coordinates (to implement teleport / Magic Bullet).
    GetDistanceTo(Actor) Vector3.Distance(posA, posB) Calculates the distance between two points.
    GetSocketLocation(BoneName) animator.GetBoneTransform(HumanBodyBones.Head).position Bone retrieval. If it’s not a standard humanoid, you iterate through child objects via transform.Find("Root/Spine/Head") to find the head node.
    K2_GetComponentLocation() component.transform.position Components are also attached to GameObjects; just take their transform directly.

    3. Camera & Screen Conversion (Camera & W2S)

    This is the most critical part for ESP and aimbot.

    UE Native Function Unity Equivalent API Description
    ProjectWorldLocationToScreen Camera.main.WorldToScreenPoint(pos) W2S core. Note: Unity’s screen origin (0,0) is at the bottom-left, while ImGui/drawing library origins are usually at the top-left. You need to manually flip the Y axis: screen.y = Screen.height - screen.y.
    GetCameraLocation() Camera.main.transform.position Gets the main camera position.
    GetControlRotation() Camera.main.transform.eulerAngles
    or transform.localEulerAngles    		 Unity has no enforced “controller rotation”. You usually just read the camera’s Euler angles directly.
    SetControlRotation() transform.eulerAngles = new Vector3(...) Sets the camera angle (to implement aimbot).

    4. Math & Aimbot Calculation (Math & Aimbot)

    Unity internally uses Quaternions to handle rotation, but for convenience it usually exposes Euler Angles/Vector3 externally.

    UE Native Function Unity Equivalent API Description
    FRotator Quaternion (internal) / Vector3 (external) UE’s Rotator is (Pitch, Yaw, Roll); Unity’s Vector3 is (x, y, z) corresponding to (Pitch, Yaw, Roll).
    FindLookAtRotation(Start, End) Quaternion.LookRotation(Target - Start)
    or transform.LookAt(Target)    		 Calculates the rotation quaternion facing the target.
    RLerp / RInterpTo Quaternion.Slerp(curr, target, t)
    or Quaternion.RotateTowards(...)    		 Smooth aimbot. Slerp is spherical interpolation, more suitable for rotation than Lerp.
    ClampAngles (custom) Mathf.Clamp / Mathf.DeltaAngle Unity’s Mathf.DeltaAngle automatically handles the -180 to 180 angle difference problem; very convenient, no need to hand-write all that while > 180 logic.

    Summary of Differences in Unity Hooking

    1. Head Position:

      • UE: Via Mesh->GetSocketLocation("head").
      • Unity: Bones are just ordinary GameObjects. You need to iterate the hierarchy to find a child object named “Head”, or if you used Animator, you can use animator.GetBoneTransform(HumanBodyBones.Head).

    2. W2S Pitfalls:

      • Unity’s WorldToScreenPoint returns Z as depth.
      • You must check result.z > 0 to confirm the object is in front of the camera (similar to UE’s return bool).
      • You must flip the Y axis: If you draw with ImGui, Unity’s y is measured from the bottom, while ImGui measures from the top.
      • Code: screenPos.y = Screen.height - screenPos.y;

    3. Finding Lists:

      • UE reverse engineering usually involves finding the offset of GWorld -> Level -> ActorArray.
      • Unity reverse engineering (Mono) usually involves finding the static linked list of the BaseEntity class, or directly hooking a specific function of GameObject to collect the object list.

    Source

    Source Engine is an engine developed by Valve (representative works: CS:GO/CS2, Apex Legends, L4D2, TF2).

    When moving from Unreal Engine to Source Engine, you’ll find the biggest difference is: UE relies heavily on the reflection system (UObject/Reflection), while Source Engine relies heavily on virtual interfaces and netvars.

    Below is how the features you used correspond in Source Engine:

    1. Core System & Object Retrieval (Interfaces vs UWorld)

    UE has a global UWorld that stores all Actors.
    Source Engine uses the Interface Pattern. You need to obtain the global interface pointers exposed by the engine.

    UE Native Function Source Engine Equivalent Interface/Method Description
    UWorld::GetWorld() No single entry point; usually you get IClientEntityList and IVEngineClient You need to use the CreateInterface exported function to get these global interfaces.
    PersistentLevel->Actors IClientEntityList::GetClientEntity(index) Source’s entities are stored in an indexed array. Index 0 is the world, 1~64 are players, 64+ are entities/weapons. You need to write a for loop from 0 to GetHighestEntityIndex().
    Actor C_BaseEntity / IClientEntity The base class of all objects.
    IsA(...) GetClientClass()->m_pNetworkName Source determines types via the ClientClass linked list. Usually you compare ClassID (e.g. CCSPlayer).
    APlayerController C_BasePlayer (Local) The local player is usually obtained via GetClientEntity(GetLocalPlayerIndex()).

    2. Vectors & Netvars

    UE’s properties (such as HP, Pos) are usually class member variables.
    Source Engine’s properties are usually Netvars, obtained by reading memory offsets or the RecvTable.

    UE Native Function Source Engine Equivalent Description
    FVector (X, Y, Z) Vector (x, y, z) Also Z-up.
    FRotator (Pitch, Yaw, Roll) QAngle (Pitch, Yaw, Roll) A struct specifically for angles.
    K2_GetActorLocation() GetAbsOrigin() or read m_vecOrigin Gets coordinates.
    K2_SetActorLocation(...) Cannot be set directly. Source has strong server-side validation. Modifying local coordinates usually gets you pulled back. Teleporting usually relies on exploits (like L4D2’s warp) or sending specific packets.
    GetSocketLocation(...) (bones) SetupBones + m_dwBoneMatrix This is the hard part. Source needs to call SetupBones to update the bone matrices, then read the coordinates from the matrix array via a bone index (e.g. 8=Head).
    HP_current (member variable) m_iHealth (Netvar) You need to use the Netvar Manager to scan the DT_BasePlayer table to find the offset of m_iHealth.

    3. Camera & Input (CreateMove vs SetControlRotation)

    This is the essence of Source Engine hooking.
    In UE, you directly change the Controller’s Rotation.
    In Source, you usually hook the CreateMove function.

    UE Native Function Source Engine Equivalent Description
    SetControlRotation CUserCmd::viewangles In CreateMove, each frame the client generates a CUserCmd and sends it to the server. Directly modifying cmd->viewangles achieves aimbot.
    GetControlRotation IVEngineClient::GetViewAngles Gets the current view.
    Advantage Silent Aim In Source, you can modify the viewangles sent to the server but not modify the local camera angle. The result: you look forward, but the bullet flies to an enemy on the side. This is very hard to do in UE (usually requires modifying Bone Transform).

    4. World to Screen (W2S)

    Source Engine’s W2S needs to rely on the ViewMatrix.

    UE Native Function Source Engine Equivalent Description
    ProjectWorldLocationToScreen WorldToScreen (hand-written) You need to find the ViewMatrix (4x4 matrix) from IVEngineClient or the renderer. Then perform standard matrix multiplication to convert 3D to 2D.
    Debug drawing ISurface interface Source provides a ISurface interface that can draw lines, text, and rectangles; more native than ImGui (but ImGui is more popular in modern cheats).

    5. RayCast / Visibility

    Determines whether an enemy is behind a wall.

    UE Native Function Source Engine Equivalent Description
    LineTraceSingle IEngineTrace::TraceRay This is a very powerful interface. You need to construct Ray_t and CTraceFilter, then call the engine’s TraceRay to check visibility.

    Summary of Source Engine Hooking Characteristics

    1. More “low-level”: There aren’t as many pre-packaged K2_ functions as in UE; many times you have to operate on matrices and vectors.
    2. Netvars: You must understand RecvTable; all game data is synchronized through network tables, and reverse engineering mainly involves dumping the offsets of these tables.
    3. CreateMove: This is the core of Source cheats; all bhop, aimbot, anti-aim, and triggerbot are implemented here.
    4. Dormant: To optimize networking, Source does not send data for distant enemies to the client. If IsDormant() == true, you can’t even know where the enemy is (this is a natural anti-wallhack barrier, whereas UE by default usually sends all Actors unless Relevancy optimization is enabled).
