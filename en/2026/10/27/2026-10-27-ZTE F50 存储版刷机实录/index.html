2. Download mode (the biggest trap) [Verified]

  • Directly connecting --kickto 2 always fails on this device: the log shows kick reboot timeout, but the spd_dump exit code is 0, and at the end of the bat pause; it looks like a normal finish but actually wrote no bytes. The user’s previous “flashed B09 or B08?” was very likely this [Inferred].
  • Usable: short-pin mode command (without --kickto, manually loading FDL1/FDL2):
The status query `cmd=usb_port_switch` also reads `adb_enabled`, <strong>not the real USB state</strong>.

### B2. What actually takes effect is system_server [Code evidence, from services.jar of B09 on the same device]
- `AdbService.setAdbEnabled()`: <strong>continues only when the value actually changes; the same value returns directly</strong>. On a real change, `ctl.start adbd`/`ctl.stop adbd`, and calls back `UsbDeviceManager`.
- `UsbDeviceManager.setAdbEnabled()`: on → `persist.sys.usb.config="adb"`; off → `"charging"`; then reconfigure `sys.usb.config`.
- At boot, `AdbService.systemReady()` does the reverse: reads `persist.sys.usb.config`; if it contains `adb` → `adb_enabled=1`, otherwise `0`—<strong>it overwrites the value last written to Settings by the web page</strong>.
- init: `on post-boot && property:sys.usb.config=none` → `setprop sys.usb.config ${persist.sys.usb.config}`; `on property:sys.usb.config=adb && property:sys.usb.configfs=1` → `start adbd`.
- SettingsProvider also does not notify observers for "writing the same value". So <strong>repeatedly writing 1 is a complete no-op</strong>.

### B3. Other
- `REBOOT_DEVICE`: returns success first, then `PowerManager.reboot("manualreboot")` after 500 ms. [Code evidence]
- `UsbTools` (`USB_PROPERTY_KEY=persist.sys.usb.config`, `USB_PROPERTY_KEY_TMP=sys.usb.config`, writes `rndis,diag,diag_mdm,adb` on enable and `rndis` on disable, then unconditionally reboots) is only called by `DEVELOPER_MODE_SETTING`/`SET_DEVICE_MODE`, while this APK's `DeveloperModule` only registers `USB_PORT_SETTING`, so this path is <strong>unreachable</strong> on this firmware. [Code evidence + inference]
- Web UI: `index.html#usb_port` → `js/adm/usb_port.js` → `setUsbPortSwitch()`; what is submitted is `goformId=USB_PORT_SETTING` + `usb_port_switch=1/0`; <strong>you must click Apply to send the request</strong>; clicking only the radio does not send. The page label is "USB Port / USB port"; it controls `adb_enabled`.
- The APK has <strong>no</strong> code that writes `service.adb.tcp.port`/`persist.adb.tcp.port` or starts/stops adbd; `persist.adb.tcp.port=5555` on the device is a persistent property already present in the ROM.

### B4. Final answer to "how to enable it when there is no adb"
- <strong>Wired adb</strong>: cause `adb_enabled` to undergo <strong>one real 0→1 change</strong>. The framework immediately `ctl.start adbd`, writes `persist.sys.usb.config` as `adb`, and reconfigures USB; <strong>code-wise no reboot is needed</strong>; `REBOOT_DEVICE` only makes the USB reliably reassemble according to `persist=adb` after reboot, which is the most stable approach.
- <strong>Why clicking the switch only on the web page does not work (your experience)</strong>: if the switch is already 1 (the UI shows `adb_enabled`, not persist and not adbd's actual state), submitting 1 again is the same value and is short-circuited by two layers into a no-op; `persist.sys.usb.config` is not written as `adb`, and at reboot `systemReady()` recalculates according to persist and goes back to 0 → still no adb, while the UI can keep showing ON. <strong>The tool sends 0 first and then 1, which forces one real 1→0→1 change.</strong> In other words: on the web page you must <strong>turn it off first, click Apply, then turn it on, then click Apply again</strong>.
- Secondary possibilities: clicked the radio but not Apply; reboot raced ahead of the asynchronous persist write; `ZTE_ADB_USB_SECURITY_RESTRICTION` under a specific SIM state forcibly disables adb; adbd/USB endpoint hung and needs re-enumeration.
- <strong>Wireless adb TCP listener</strong>: adbd reads `service.adb.tcp.port`/`persist.adb.tcp.port` at startup; this device's ROM already has `persist.adb.tcp.port=5555`, so adbd listens on TCP 5555 as soon as it starts. <strong>The Samba approach can neither be done on this firmware (`smb.conf` immutable) nor is it necessary</strong>. However, this time connecting to `192.168.0.1:5555` from the computer Wi-Fi still timed out; the reason is not investigated (A9).

### B5. On-site confirmation (2026-10-27, device on Android)
After logging in and making read-only queries through the web interface: `usb_port_switch → '1'`, `developer_mode_enable → '1'`; on the device `settings get global adb_enabled = 1`, `persist.sys.usb.config = adb`, `sys.usb.config = rndis,mtp,adb`, `init.svc.adbd = running`, `persist.adb.tcp.port = 5555`. Consistent with the model. Two diagnostic interfaces can be used without adb (after login):
- `GET /goform/goform_get_cmd_process?isTest=false&cmd=usb_port_switch` → `adb_enabled`
- `GET /goform/goform_get_cmd_process?isTest=false&cmd=developer_mode_enable` → whether `persist.sys.usb.config` contains `adb`
If the former is 1 and the latter is 0, it is the branch described above where "the UI shows ON but persist has no adb"; in that case just send 0 then 1.

### B6. Risks
- Sending `usb_port_switch=0` alone (a real 1→0) writes `persist.sys.usb.config` as `charging`; if the following 1 does not succeed, after reboot USB will only charge, and RNDIS/ECM and the web backend may both be unreachable. <strong>Do not send 0 alone when you have no recovery method</strong>—this is exactly the bad state left after the original program and our script fail after step 1.
- The agent's framework-side evidence comes from the B09 backup image of the same device; if the device is not running this firmware, the `services.jar` details may differ (the APK side is unaffected).

### B7. Corrections to the preceding content
- The statement in Appendix A that "Samba's `preexec = start adbd` is the key to enabling wireless adb" and the corresponding inference in §3-D are <strong>downgraded to: the original program's approach is not necessary on this firmware</strong>; what is decisive is a real 0→1 change of `adb_enabled`.
- The statement in the A2 table that "`usb_port_switch=1` makes USB add the ADB interface" is inaccurate: it sets `adb_enabled`; the USB interface is reconfigured by system_server in response to the change.
