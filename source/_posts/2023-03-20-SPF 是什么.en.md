## What is SPF

In the currently widely used mail-sending protocol [SMTP](https://zh.wikipedia.org/zh-hans/Simple Mail Transfer Protocol), the sender can arbitrarily set the sender's email address, and anyone can impersonate *boss@your-corp.com* to send emails to others. Therefore, the SPF (Sender Policy Framework) mechanism was proposed to verify the email sender (Mail Transfer Agent, MTA), so that only servers recognized by *your-corp.com* can send emails with *boss@your-corp.com* as the sender. The email recipient uses SPF records and IP addresses to identify whether the sending server is legitimate, and based on the instructions in the SPF record decides whether to accept or reject the email.

## How to Deploy SPF

The DNS system once had a dedicated SPF resource record type, but it has been abolished. Nowadays SPF all exists in the form of TXT resource records, and the hostname is generally @. For example, this blog's SPF is as follows:

```bash
➞ dig chenxy.me txt +short
"v=spf1 include:spf.mail.qq.com ~all"
```

## Format of SPF Records

An SPF record uses a single space as the delimiter for multiple terms, and each term consists of components such as qualifier, mechanism, and modifier. During parsing, matching proceeds from left to right. If any term matches successfully, the matching process stops immediately and the SPF verification result is returned according to the qualifier.

An SPF record starts with the fixed `v=spf1 `, which identifies the SPF version, currently fixed as spf1.

### Qualifier and Mechanism

#### Qualifier

Qualifiers in SPF are placed before the mechanism, and there are the following four. Among them, + is the default qualifier and can be omitted.

| **Qualifier** | **Result** | **Explanation** *(if the corresponding mechanism matches successfully)* |
| ------------- | ---------- | ------------------------------------------------------------ |
| +             | Pass       | An explicit statement that the sender's machine passed the check and can send mail from this domain's mailboxes |
| -             | Fail       | An explicit statement that the sender's machine failed the check and is not allowed to send mail from this domain's mailboxes |
| ~             | Soft Fail  | A weaker statement that the sender's machine appears to have failed the check |
| ?             | Neutral    | The administrator of this domain has not explicitly stated whether the sender's machine passed the check |

#### Mechanism

##### all

all will always match successfully. For this reason, mechanisms after all will not take effect. all is generally used as the last mechanism, together with a qualifier, to configure the "default behavior"—if all other policies fail to match, what this domain's policy is for these exceptions.

Take this site's SPF configuration `v=spf1 include:spf.mail.qq.com ~all` as an example: if the include mechanism fails to match, then it eventually reaches all and matches successfully, returning a "soft fail" result according to its qualifier—generally the email recipient will not reject this email, but will classify it as spam.

##### include

The format of include is `include: *domain-spec*`. It triggers a recursive SPF verification process, causing the email recipient to check the SPF record set by *domain-spec*. Only when the verification result of *domain-spec* is pass (note: soft fail does not count either) is this mechanism considered to have matched successfully.

The include mechanism is expected to handle "cross-administrative-boundary" situations, that is, when the required SPF rules are placed under a domain not managed by this domain. It is more like "importing a third-party dependency library", while the redirect mentioned below is more like "a piece of shared code inside the company".

##### exists

The format is `exists: *domain-spec*`. The recipient will send an A record query to the specified domain (even for IPv6, an A record query is used). If there is any response, it matches successfully. It can be used for some relatively complex verification.

Among them, *domain-spec* can include the following macros:

| Macro | Meaning                                                      | Example                 |
| ---- | ------------------------------------------------------------ | ----------------------- |
| s    | Sender's email address                                       | hsiaoxychen@example.com |
| l    | Sender's "local part"                                        | hsiaoxychen             |
| o    | Sender's domain part                                         | example.com             |
| d    | The current SPF authoritative domain being verified. Generally consistent with the above, but may change when parsing include | example.com             |
| i    | Sender's IP                                                  | 114.5.1.4               |
| v    | `in-addr` if IPv4, `ip6` if IPv6                         | in-addr                 |
| h    | HELO/EHLO domain                                             | mail.example.com        |

Also, if r is appended after a macro, the value can be reversed. For example, suppose we have the following SPF record:

```log
v=spf1 exists:%{ir}.%{l}._spf.example.com -all
```

Also, under the _spf.example.com subdomain there is only one A record:

```log
4.1.5.114.noreply._spf.example.com IN A 127.0.0.1
```

Then only emails from `noreply@example.com` sent from `114.5.1.4` can pass SPF verification.

##### Other Mechanisms

Other mechanisms include: a, mx, ip4, ip6, exists. Their mechanisms are relatively similar and easier to understand, summarized as follows:

| a    | If the sender IP matches the IP address of any A record (or AAAA record, depending on whether this sending action goes over IPv4 or IPv6) of the specified domain, it matches successfully |
| ---- | ------------------------------------------------------------ |
| mx   | If the sender IP matches any MX record of the specified domain, it matches successfully |
| ip4  | If the sender IP matches the specified IPv4 address (range), it matches successfully |
| ip6  | If the sender IP matches the specified IPv6 address (range), it matches successfully |

### Modifier

The syntax of a modifier is slightly different from that of a mechanism: it has no qualifier, and the key-value separation is not `:` but `=`. There are currently two modifiers: redirect and exp. exp is used to tell the server how to generate explanatory text after SPF verification fails, and will not be introduced here; redirect can "redirect" the subsequent SPF verification process to the target domain. For example, gmail.com's SPF record:

```bash
➞  dig gmail.com txt +short
"globalsign-smime-dv=CDYX+XFHUw2wml6/Gb8+59BsH31KzUr6c1l2BPvqKX8="
"v=spf1 redirect=_spf.google.com"

➞  dig _spf.google.com txt +short
"v=spf1 include:_netblocks.google.com include:_netblocks2.google.com include:_netblocks3.google.com ~all"
```

Although under a different domain, the SPF policy of _spf.google.com can represent gmail.com.

Note that redirect must appear as the last part of the SPF record, and when all is present, redirect must be ignored.

## Example Analysis of SPF Records

```bash
➞  dig chenxy.me txt +short
"v=spf1 include:spf.mail.qq.com ~all"
# 检查 spf.mail.qq.com 的匹配结果，如果匹配失败，则返回 soft fail

➞  dig spf.mail.qq.com txt +short
"v=spf1 include:spf-a.mail.qq.com include:spf-b.mail.qq.com include:spf-c.mail.qq.com include:spf-d.mail.qq.com include:spf-e.mail.qq.com include:spf-f.mail.qq.com include:spf-g.mail.qq.com -all"
# 依次检查各个 include 的匹配结果，如果都匹配失败，则返回 fail

➞  dig spf-a.mail.qq.com txt +short
"v=spf1 ip4:203.205.251.0/24 ip4:103.7.29.0/24 ip4:59.36.129.0/24 ip4:113.108.23.0/24 ip4:113.108.11.0/24 ip4:119.147.193.0/24 ip4:119.147.194.0/24 ip4:59.78.209.0/24 ip4:113.96.223.0/24 ip4:183.3.226.0/24 ip4:183.3.255.0/24 ip4:59.36.132.0/24 -all"
# 如果发件方不在这些 ip 段之中则返回 fail
```

It seems that in practically applied SPF records, mechanisms such as exists and exp are almost never used; most merely simply define legitimate IP ranges.

Another relatively typical way of writing an SPF record is:

```log
v=spf1 a mx ip4:114.5.1.4 -all
```

It means "only the IPs in this domain's a and mx records plus 114.5.1.4 can send email on behalf of this domain", commonly seen in self-built private mail servers.
