## 2. ダウンロードモード（最大の罠）[検証済み]

- 直接 `--kickto 2` はこの機体では**常に失敗**する。ログに `kick reboot timeout` が出るが、**spd_dump の終了コードは 0**、bat の最後は `pause` で、正常終了に見えて実際には 1 バイトも書き込んでいない。ユーザーが以前に「B09 を焼いたのか B08 のままなのか」と迷ったのはおそらくこれ [推定]。
- **使用可能：短絡モードコマンド**（`--kickto` を付けず、FDL1/FDL2 を手動ロード）：
```
spd_dump.exe --wait 300 exec_addr 0x65012f48 fdl <fdl1-dl.bin> 0x65000800 fdl <fdl2-dl.bin> 0xb4fffe00 exec path <dir> <操作...> reset
```
- 操作：ケーブルを抜く → テストポイントを短絡 → 短絡を保持したままケーブルを挿す（コマンドを先に起動しても、既に接続済みでもよい）。
- `usb_send failed (0 / 1)` が 1 回出た場合は接触不良なのでやり直す。**成功可否はログ内の `Write Part Done` だけで判断し、終了コードは見ない。**

## 3. 書き込み手順

### A バックアップ（ユーザー実施）

### B B09 ROM を書き込む（userdata を消去）[検証済み]
```
spd_dump.exe --wait 300 exec_addr 0x65012f48 fdl <fdl1> 0x65000800 fdl <fdl2> 0xb4fffe00 \
  exec path <temp> write_parts <zte-f50-b09\> e userdata reset
```
`zte-f50-b09\*.bin` をすべて書き込む（splloader、ztepersist、super 2GB、misc を含む）。約 2.7GB。

### C root + パッチ trustos [検証済み]
```
... exec path <bin> w trustos <bin\f50b09_t.bin> w boot <bin\magiskf50b09.img> reset
```
現在の slot（slot a）の `trustos_a`、`boot_a` のみを書き込み、userdata は消去しない。`f50b09_t.bin`（5178856 バイト、MD5 先頭 a110ecb1）は作者の `trustos.bin` と同じ。boot には `magiskf50b09.img`（0e9e8a4d）を使用。作者 kkroot の `boot.bin`（f2e8db4a）は別ファイルで、いずれも Magisk イメージ。書き込み後も `ro.boot.flash.locked` は 1 のままだが、Linux は起動できる。

### D adb を有効化 [効果は検証済み、仕組みは **[補足待ち]** ]
- **重要な発見：B09 を書き込んだ後、または userdata 縮小後の工場出荷状態リセット後でも adb は引き続き使用可能**。この ROM には UFI-TOOLS（`com.minikano.f50_sms`）と Magisk stub が同梱されており、`persist.sys.usb.config=adb`、`persist.adb.tcp.port=5555` は persist パーティションに保存されるため、工場出荷状態リセットでも失われない。最初の一度だけ（B08 から B09 を書き込んだ直後）は一時的な無線 adb ツールで有効化する必要がある。
- 一時的な無線 adb ツール（静的リバースは完了済み、**詳細は付録 A**）。**訂正**：以前に「シリアル経由で AT を送る」と書いたが、それは誤りで、このツールには**シリアルロジックが一切ない**。実際のフローは 6 ステップ：① HTTP `USB_PORT_SETTING&usb_port_switch=0`（まず OFF）→ ② `=1`（再 ON）→ ③ `REBOOT_DEVICE`（再起動）→ ④ `adb wait-for-device` → ⑤ `adb shell` で `setprop` を変更し、`/data/samba/etc/smb.conf` に `preexec = start adbd`、`guest ok = yes` などを書き込む → ⑥ Guest の空パスワードで SMB（445）に接続して `start adbd` を発火；最後に `adb connect 192.168.0.1`。HTTP ログイン：`H1=SHA256(pwd)`、`H2=SHA256(H1+LD)`、AD=`SHA256(SHA256(wa_inner_version+cr_version)+RD)`、ポート **8080**。「ポートを操作できません」は実際にはステップ 1 の HTTP 応答に `result` がないことであり、シリアルエラーではない。
- したがって「単に Web のスイッチだけでは足りない」理由：無線 adb のスイッチは Samba の `preexec = start adbd` で、誰か（Guest）が一度 SMB に接続して初めて adbd が起動する。再起動後に誰も接続しなければリスニングはない [推定]。
- 代替スクリプト：`F:\Projects\tmp\f50\re\f50_wireless_adb.py`。**実機で試験済み（2026-10-27、付録 A §A9 参照）**：HTTP ログイン、`USB_PORT_SETTING` の 0→1、`REBOOT_DEVICE`、USB adb が戻るのを待つ、という一連は**検証通過**。Samba の部分はこのファームウェアでは使用不可（`smb.conf` が immutable）。`adb connect` の無線部分は今回は**通らなかった**。リスクは付録 A §A6 参照。
- **前述の訂正**：Samba の `preexec = start adbd` はこのファームウェアで adb を有効化する鍵ではない。実際に adb を出現させるのは最初の 3 ステップの HTTP（`USB_PORT_SETTING` をまず 0 にしてから 1、その後 `REBOOT_DEVICE`）であり、これは実測済み。TCP 5555 のリスニングは `persist.adb.tcp.port=5555` 由来。
- **このプログラムには破壊的な副作用がある**：毎回まず `usb_port_switch=0` を送り、失敗しても復元しない。繰り返し実行すると `persist.sys.usb.config` が `adb,rndis` から `adb` に変わり、`192.168.0.1` が一時的に到達不能になる。USB adb と `192.168.0.1:5555` の 2 デバイスが同時に存在すると `more than one device` を報告するので、先に `adb disconnect`。
- ファームウェアの adbd は**鍵を検証しない**：`ro.adb.secure=1` でも `/data/misc/adb/adb_keys` が存在しなくても接続でき、ペアリング不要。

### F インストーラ、userdata 縮小 [検証済み]
- PowerShell 版 `install.ps1` を使用（本機に lz4 なし）。
- **環境の罠 1**：Git Bash の `PSModulePath` が PowerShell 7 モジュールを前に並べるため、5.1 では `Get-FileHash` が見つからないと報告される。実行前に：
`export PSModulePath='C:\Program Files\WindowsPowerShell\Modules;C:\WINDOWS\system32\WindowsPowerShell\v1.0\Modules'`
- **環境の罠 2**：カスタムパッケージ検証時に Git 同梱の GNU tar が `F:\...` をリモートホストとして扱う（`Cannot connect to F: resolve failed`）。実行前に Windows 同梱の tar を前に置く：`export PATH="/c/Windows/System32:$PATH"`。
- `export MU300_NO_SELF_UPDATE=1`（そうしないとスクリプトの自己更新後に再実行され、出力が飲み込まれる）。
- 読み取り専用チェック：`install.ps1 -Check -Lang en`。
- 縮小には answers ファイル（`-AnswersFile`）を使用。回答変数は `install.sh` 冒頭のコメント参照。いずれかの変数が欠けると質問箇所で `no answer to the question ... set MU300_ANS_xxx` を報告して中止し、**中止時には何も書き込まない**。
```
MU300_LANG=en
MU300_ANS_MAKE_ROOM=yes
MU300_ANS_LINUX_GIB=198
MU300_ANS_ERASE_ANDROID=ERASE
MU300_ANS_REBOOT=yes
```
結果：userdata は `228.19 → 30.19 GiB`、その後ろに 198.00 GiB が空く。Android recovery で工場出荷状態にリセット。

### G Debian パッケージをインストール [検証済み]
- 継続インストール失敗：`The prepared installation cannot be continued: this installer's tools or the package differ`。原因：トランザクション内の payload identity は縮小時（パッケージなし）に計算されたもので、カスタムパッケージをインストールすると identity が変わる。**処理：`-NoResume`**。領域先頭にはインストーラが書いた token があり、「unpartitioned space is not empty」と表示されるので、`MU300_ANS_OVERWRITE=overwrite` と答える（この領域は自分で切り出したもので、空であることを確認済み）。

## 4. Debian unstable 7.3 イメージ（非公式ビルド）

**これはプロジェクト公式イメージではない。** 公式は Ubuntu 24.04/26.04 と OpenWrt のみを配布しており、`docs/DISTROS.md` の Debian 13 ビルドは「same package names as Ubuntu」とあるだけで実機試験はされていない。今回はバックグラウンドエージェントが WSL でビルドした。

- ビルド基盤：`debian:unstable`（arm64、qemu binfmt が必要）、Dockerfile パッチ：`docker-compose-v2`→`docker-compose` および `docker-cli` を追加。
- `assemble.sh` パッチ：`KREL`、`UBUNTU` は `MU300_KREL`、`MU300_UBUNTU_RELEASE` で上書き可能。`/release` マウントを追加して release 同梱の `opt/mu300`、`etc/mu300` などを再利用。**NTFS チェックアウトにより overlay が 1000:1000/0777 になる問題を修正**（`/`、`/etc`、`/usr` まで 777 になっていた）。release のマニフェストに従って所有者権限を復元。
- マニフェスト内の `SYSTEM=ubuntu-26.04`/`OS=ubuntu` の identity とファイル名をホワイトリスト通過のために保持し、rootfs ペイロードのみを差し替え、`SHA256_ROOTFS` と `SHA256SUMS` を更新し、署名を削除（パッケージは未署名で、ローカル自己使用のみ）。
- release の静的 aarch64 補助プログラム（`logdw`、`adbd`、`mu300-keys`、`mu300-bt-init`、`mu300-carry`）を再利用。カーネルモジュールは `mu300-kernel-7.3.tar.gz` 由来（3059 個の `.ko`）。**カーネルは自分でコンパイルしていない**。
- 成果物：rootfs `mu300-ubuntu-26.04-rootfs.tar.gz`（261.7 MiB、展開後 834 MiB、SHA256 `5e5797470b61810c32d2d51b111ba6f9667b91aea0e0e7e373b39896ccb48bf2`）。パッケージ全体は 319.8 MiB。
- 検証：インストーラ `package_load/package_verify` → `PACKAGE OK`。`dpkg --audit` はクリーン。apt は deb.debian.org から実測成功。主要コンポーネントは揃っている。

### 既知のリスク
- **`mu300-update apply` はシステム全体を Ubuntu 24.04 に置き換える**（Debian には `VERSION_ID` がなく、Ubuntu rootfs にフォールバックする）。対応済み：`/opt/mu300/bin/mu300-update` と `/usr/local/bin/mu300-update` を `.disabled` に改名し、`mu300-update-notice.timer` は disable 済み。コントロールパネルの更新インターフェースはバイナリ欠如時に unsupported を返し、`mu300-accounts.service` はマーカーファイルが存在する場合にのみそれを呼ぶ（通常は存在しない）。Debian の更新には `apt` を使用。
- パネル/`mu300-os` はこれを Ubuntu 26.04 として扱い、バージョン番号は空表示になる。
- sid はローリングリリースであり、ビルド結果は日付によって変動する。
- SIM がないため modem/モバイルデータは未試験。Wi-Fi ホットスポット、Bluetooth、GPU は個別検証していない。

## 6. 再起動検証 [検証済み]
`reboot` 後、約 1 分で `192.168.77.1` に到達可能。SSH（鍵）、docker、カーネル 7.3.0、`mu300-update` の無効化はいずれも維持。初回の `is-system-running` は `degraded`（失敗マーカーが 1 つ残る）、`systemctl reset-failed` 後は `running`。

## 7. システムの切り替え方法（Linux ⇄ Android）

**Linux** 内で（`wray` は sudo が必要、または adb root を使用）：
```
sudo mu300-next-boot android     # 下次(及之后)重启进 Android
sudo mu300-next-boot linux       # Linux 保持为默认(每次成功启动后自动重新武装)
sudo mu300-next-boot status
sudo mu300-next-boot attempts N  # 连续失败几次回 Android(1-6,现为 5)
sudo mu300-next-boot lock        # 无论如何都留在 Linux(失败启动也不回 Android)
sudo mu300-next-boot unlock
sudo mu300-os <系统>             # 多个 Linux 系统之间选(目前只有一个 ubuntu=本次的 Debian)
```
その後 `sudo reboot`。コンピュータがない場合の保険：Linux 起動中に 5 回連続で電源を切ると、自動的に Android に戻る。

**Android**（Magisk）内で：`su -c mu300-linux`、次回 Android 起動後に Linux に入る。

## 11. Wi-Fi クライアント（デバイスがルーターに接続）

- **制限**：SC2355 無線は同時に 1 つのことしかできず、ルーターに接続するとデバイス自身のホットスポット（`FRayWrt`）はオフになる。ホットスポット→クライアントは**再起動**のみ、クライアント→ホットスポットは再起動不要。WPA2、WPA2/WPA3 混合のみ対応し、純粋な WPA3 / Wi-Fi 7 は拒否される。USB の `192.168.77.1` は影響を受けない。
- ツール：`wifi-client`（`/opt/mu300/bin/wifi-client`）。
```
sudo wifi-client scan-mode on  &&  sudo reboot     # 下次开机保持客户端,才能 scan
sudo wifi-client scan
sudo wifi-client connect "SSID"                    # 交互输入密码,不回显;已知名字时不需要 scan
sudo reboot                                        # 重启后才真正加入
wifi-client status | disconnect | forget
```
  現在無線がホットスポットモードのとき、`scan`/`connect` は「the radio is an access point right now … cannot turn it back into a client without a reboot」と表示する。これは故障ではなく、`connect` が先にネットワークを保存し、再起動後に参加する。パスワードは対話入力または `--password-file` を使い、**コマンドラインにパスワードを書かない**（journal と `ps` に入る）。
- **Debian sid のバグとパッチ [関数レベルまで検証済み]**：`connect` が `could not build the wpa_supplicant configuration` を報告。根本原因：sid の `wpasupplicant 2.11` の `wpa_passphrase` がパイプからパスワードを読むときに `tcgetattr` を呼び、非端末上で失敗して出力がなく、`network_block()` が PSK ハッシュを取得できない。Ubuntu の旧版にはこの問題がない。デバイス上に python3/openssl はない。
  - パッチ：`tools/wifi-client.patch.sh`（バックアップは `/opt/mu300/bin/wifi-client.orig`）：`wpa_passphrase` が成功すれば従来どおりハッシュを使用し、失敗すれば `psk="密码"` にフォールバック（`wpa_supplicant` 自身に PBKDF2 を計算させる）。パスワード長は 8–63 が必要。設定ファイルは 0600 root。SAE 経路はもともと平文 `sae_password` を書くので、安全性は同等。
  - 単体検証：WPA2、WPA2/WPA3（SAE）、オープンネットワーク、短いパスワード（失敗を返す）の 4 種類の出力はすべて正しい。**まだ実際にルーターへ接続したことはない**。
  - 制限：パスワードに非 ASCII や二重引用符が含まれる場合は問題があるかもしれない [未検証]。このパッチはインストール済みファイルを変更するため、更新/再インストールで上書きされ、再適用が必要。
  - **調査過程（再現可能）**：
    1. ユーザーはまず「the radio is an access point right now … cannot scan either」（正常な案内、上記参照）を見て、案内に従って `connect` した後 `could not build the wpa_supplicant configuration` を報告。
    2. `grep -n "could not build the wpa_supplicant" /opt/mu300/bin/wifi-client` → 832 行目で `network_block()`（約 733–755 行）を呼ぶ。関数内で `h=$(printf '%s\n' "$2" | wpa_passphrase "$1" | sed … psk=<64 hex>)`、`h` が空なら `return 1`。
    3. デバイス上で直接試す：`printf '%s\n' testpass1234 | wpa_passphrase TestSSID` は `# reading passphrase from stdin` と `tcgetattr: Inappropriate ioctl for device` のみを出力し、`psk=` 行はない。`dpkg -l wpasupplicant` = `2:2.11-4`（sid）。
    4. 代替案を排除：デバイス上に `python3`、`openssl` はどちらもなく、PBKDF2 を計算できない。`wpa_supplicant` 自身が `psk="明文密码"` をサポートするので、これをフォールバックに使う。
    5. パッチ適用後、関数を単独で抽出して 4 種類の入力で検証し（上記参照）、その後ユーザーに `connect` を再実行してもらう。

### 11.1 修正後の完全版

**修正後の `network_block()`（`/opt/mu300/bin/wifi-client` 内の同名関数を置換、約 733–760 行。その他は不変）**：

```sh
# the supplicant's network block. The name goes in hex, so any byte (quotes, UTF-8) is taken as it is. The
# passphrase goes in as wpa_passphrase's hash, handed to it on stdin (an argument would be on its command line
# for ps), and its "#psk=" comment with the plain passphrase is left out. SAE cannot use the hash: with SAE it
# also goes in as sae_password, which is why the file is root's alone.
# Debian sid: wpa_passphrase 2.11 calls tcgetattr on stdin and prints nothing when piped, so h is empty there;
# fall back to a quoted passphrase, which wpa_supplicant hashes itself (8..63 characters, same 0600 root file).
network_block() {  # network_block SSID PASS SAE
    printf 'network={\n\tssid=%s\n' "$(hex "$1")"
    if [ -z "$2" ]; then
        printf '\tkey_mgmt=NONE\n'
    else
        h=$(printf '%s\n' "$2" | wpa_passphrase "$1" 2>/dev/null | sed -n 's/^[[:space:]]*psk=\([0-9a-fA-F]\{64\}\)$/\1/p')
        if [ -n "$h" ]; then
            printf '\tpsk=%s\n' "$h"
        else  # wpa_passphrase failed (sid)
            [ "${#2}" -ge 8 ] && [ "${#2}" -le 63 ] || return 1
            printf '\tpsk="%s"\n' "$2"
        fi
        if [ "$3" = 1 ]; then
            # WPA2, WPA2/WPA3 and WPA3-only networks alike; WPA3 requires management frame protection
            printf '\tkey_mgmt=WPA-PSK SAE\n\tieee80211w=1\n\tsae_password=%s\n' "$(hex "$2")"
        else
            printf '\tkey_mgmt=WPA-PSK\n'
        fi
    fi
    printf '}\n'
}
```

### A3. HTTP ログインアルゴリズム（`zreq`）[検証済み]

- ベース `http://192.168.0.1:8080`。リクエストヘッダ `User-Agent: Mozilla/5.0`、`Referer: http://<ip>:8080/index.html`、`Content-Type: application/x-www-form-urlencoded`、`Cookie: <登录后 Set-Cookie 第一段>`。`Host` ヘッダのソースは `<ip>` と書かれているが、Go が実際に送るのはおそらく `<ip>:8080` [未確認]。
- LD：`GET /goform/goform_get_cmd_process?isTest=false&cmd=LD&_=<毫秒>` → JSON `LD`。
- ログイン：
  - `H1 = SHA256(password).upper()`
  - `H2 = SHA256(H1 + LD).upper()`
  - `POST /goform/goform_set_cmd_process` body `goformId=LOGIN&isTest=false&password=<H2>`、`Set-Cookie` の最初のセグメントを Cookie として取得。
- UFI 情報取得：`GET …cmd=Language,cr_version,wa_inner_version&multi_data=1` → `wa_inner_version`、`cr_version`。RD 取得：`GET …cmd=RD`。
- AD：`H3 = SHA256(wa_inner_version + cr_version).upper()`、`AD = SHA256(H3 + RD).upper()`（**RD** であり、U20 スクリプトの JSESSIONID ではないことに注意）。
- 最終 POST body は `url.Values.Encode()` が生成（key の辞書順）。例：`AD=<AD>&goformId=USB_PORT_SETTING&isTest=false&usb_port_switch=0`。
- パスワードはツール内蔵の 14 バイト汎用管理者ログイン文字列で、`zreq` は**リテラル 14 バイト**に対して SHA-256 を行い、base64 デコードはしない。**本文にはその文字列を記録しない**。必要なら `F:\Projects\tmp\f50\re\f50_wireless_adb.py` 参照。
- U20 の PowerShell スクリプト（`O:\F50\kkfile\bin\u20_openadb.ps1`）は別のアルゴリズム（`192.168.88.1`、80 ポート、JSESSIONID）を使うので、**混用しない**。

## 付録 B：`USB_PORT_SETTING` はデバイス内で一体何をしているのか（Web バックエンド APK の逆コンパイル）

出典：`/system/priv-app/ZteWebServer/ZteWebServer.apk`（プロセス `com.zte.web`、8080 をリッスン、`sharedUserId=android.uid.system`）。エージェントがオフラインで逆コンパイル。完全なレポートとコード断片：`F:\Projects\tmp\f50\zteweb\notes\{REPORT.txt,UsbTools.java,DeveloperModule_usb_excerpt.java.txt,framework_adb_chain.txt}`。2026-10-27。注記 **[コード証拠]** / **[推定]**。現場での裏付けは B5 参照。

### B1. 中核結論
**`USB_PORT_SETTING` は 1 つのことだけを行う：システム設定 `Settings.Global adb_enabled` を書く（1 = ON、0 = OFF、その他の値は 0 扱い）。** `persist.sys.usb.config`/`sys.usb.config` は書かず、`UsbManager` を呼ばず、shell を実行せず、ブロードキャストを送らず、再起動もしない。[コード証拠]
```java
// com.zte.web.module.developer.DeveloperModule.processGoFormId()
case "USB_PORT_SETTING":
    String s = bundle.getString("usb_port_switch");
    setUsbDeveloperMode(getContext(), "1".equals(s));
    JSONUtils.responseSuccess(jSONObject);          // 即使没有真正生效也回 success
public static void setUsbDeveloperMode(Context c, boolean z) {
    Settings.Global.putInt(c.getContentResolver(), "adb_enabled", z ? 1 : 0);
}
```
状態照会 `cmd=usb_port_switch` が読むのも `adb_enabled` であり、**USB の実際の状態ではない**。

### B2. 実際に効いているのは system_server [コード証拠、同機 B09 の services.jar 由来]
- `AdbService.setAdbEnabled()`：**値が実際に変化した場合のみ続行し、同値ならそのまま return**。実際に変化したときは `ctl.start adbd`/`ctl.stop adbd` を行い、`UsbDeviceManager` をコールバック。
- `UsbDeviceManager.setAdbEnabled()`：ON → `persist.sys.usb.config="adb"`、OFF → `"charging"`。その後 `sys.usb.config` を再設定。
- 起動時 `AdbService.systemReady()` は逆に、`persist.sys.usb.config` を読み、`adb` を含めば → `adb_enabled=1`、そうでなければ `0`——**前回 Web が Settings に書いた値を上書きする**。
- init：`on post-boot && property:sys.usb.config=none` → `setprop sys.usb.config ${persist.sys.usb.config}`、`on property:sys.usb.config=adb && property:sys.usb.configfs=1` → `start adbd`。
- SettingsProvider も「同じ値の書き込み」ではオブザーバに通知しない。したがって**1 を繰り返し書くのは完全な無操作**。

### B3. その他
- `REBOOT_DEVICE`：まず success を返し、500ms 後に `PowerManager.reboot("manualreboot")`。[コード証拠]
- `UsbTools`（`USB_PROPERTY_KEY=persist.sys.usb.config`、`USB_PROPERTY_KEY_TMP=sys.usb.config`、ON で `rndis,diag,diag_mdm,adb` を書き、OFF で `rndis` を書き、最後に無条件で再起動）は `DEVELOPER_MODE_SETTING`/`SET_DEVICE_MODE` からのみ呼ばれるが、本 APK の `DeveloperModule` は `USB_PORT_SETTING` のみを登録しているため、この経路は本ファームウェアでは**到達不能**。[コード証拠+推定]
- Web UI：`index.html#usb_port` → `js/adm/usb_port.js` → `setUsbPortSwitch()`。送信するのは `goformId=USB_PORT_SETTING` + `usb_port_switch=1/0`。**Apply を押して初めてリクエストを送る**ので、radio をクリックしただけでは送信されない。ページラベルは「USB Port / USBポート」で、制御しているのは `adb_enabled`。
- APK 内には `service.adb.tcp.port`/`persist.adb.tcp.port` を書いたり adbd を起動/停止したりするコードは**一切ない**。デバイス上の `persist.adb.tcp.port=5555` は ROM にもともとある永続プロパティ。

### B4. 「adb がないときにどう有効化するか」の最終回答
- **有線 adb**：`adb_enabled` に**一度だけ実際の 0→1 変化**を起こす。フレームワークは直ちに `ctl.start adbd` し、`persist.sys.usb.config` を `adb` に書き、USB を再設定する。**コード上は再起動不要**。`REBOOT_DEVICE` は再起動後に `persist=adb` に従って安定して USB を再構成するためのもので、最も確実な方法。
- **Web 上でスイッチをクリックするだけでは効かない理由（あなたの経験）**：スイッチがもともと 1 の場合（UI が表示しているのは `adb_enabled` であり、persist でも adbd の実際の状態でもない）、再度 1 を送信しても同値で、2 層の短絡により無操作になる。`persist.sys.usb.config` は `adb` に書かれず、再起動時に `systemReady()` が persist に従って再計算し、再び 0 に戻る → adb は依然としてなく、UI は ON を表示し続けられる。**ツールが先に 0 を送ってから 1 を送るのは、強制的に実際の 1→0→1 変化を作るため。** 言い換えれば、Web 上では**まず OFF にして Apply、次に ON にして Apply** する必要がある。
- 次要的な可能性：radio をクリックして Apply を押していない。再起動が非同期の persist 書き込みより先に走った。特定の SIM 状態で `ZTE_ADB_USB_SECURITY_RESTRICTION` が adb を強制 OFF にした。adbd/USB エンドポイントがハングし、再列挙が必要。
- **無線 adb の TCP リスニング**：adbd は起動時に `service.adb.tcp.port`/`persist.adb.tcp.port` を読む。本デバイスの ROM には `persist.adb.tcp.port=5555` が既にあるため、adbd が起動すると同時に TCP 5555 もリッスンする。**Samba の仕組みは本ファームウェアでは実行できない（`smb.conf` が immutable）うえ、必須でもない**。ただし今回、コンピュータの Wi-Fi から `192.168.0.1:5555` に接続すると依然としてタイムアウトし、原因は未解明（A9）。

### B5. 現場での裏付け（2026-10-27、デバイスは Android）
Web インターフェース経由で読み取り専用照会し、ログイン後：`usb_port_switch → '1'`、`developer_mode_enable → '1'`。デバイス上：`settings get global adb_enabled = 1`、`persist.sys.usb.config = adb`、`sys.usb.config = rndis,mtp,adb`、`init.svc.adbd = running`、`persist.adb.tcp.port = 5555`。モデルと一致。2 つの診断インターフェースは（ログイン後なら）adb なしで使用可能：
- `GET /goform/goform_get_cmd_process?isTest=false&cmd=usb_port_switch` → `adb_enabled`
- `GET /goform/goform_get_cmd_process?isTest=false&cmd=developer_mode_enable` → `persist.sys.usb.config` に `adb` が含まれるか
前者が 1 で後者が 0 なら、上記の「UI は ON だが persist に adb がない」分岐であり、その場合は先に 0、次に 1 でよい。

### B6. リスク
- `usb_port_switch=0` を単独で送る（実際の 1→0）と `persist.sys.usb.config` が `charging` に書かれる。その後の 1 が成功しなければ、再起動後の USB は充電のみになり、RNDIS/ECM と Web バックエンドの両方に到達できなくなる可能性がある。**復旧手段がないときに 0 を単独で送らないこと**——これはまさに元プログラムと我々のスクリプトのステップ 1 以降の失敗が残す悪い状態。
- エージェントのフレームワーク側証拠は同機 B09 バックアップイメージ由来。デバイスがこのファームウェアで動作していない場合、`services.jar` の詳細は異なる可能性がある（APK 側は影響を受けない）。

### B7. 前述内容の訂正
