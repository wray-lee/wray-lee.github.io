現在広く使われている送信プロトコル [SMTP](https://zh.wikipedia.org/zh-hans/%E7%AE%80%E5%8D%95%E9%82%AE%E4%BB%B6%E4%BC%A0%E8%BE%93%E5%8D%8F%E8%AE%AE) では、送信側は送信者のメールアドレスを任意に設定でき、誰でも *[boss@your-corp.com](mailto:&#x62;&#111;&#x73;&#115;&#x40;&#x79;&#111;&#117;&#114;&#x2d;&#99;&#x6f;&#114;&#x70;&#x2e;&#99;&#x6f;&#x6d;)* を装って他人にメールを送信できる。そのため、電子メール送信者（メール転送エージェント、MTA）を検証する仕組みとして SPF (Sender Policy Framework) が提案された。*your-corp.com* に認められたサーバーのみが、*[boss@your-corp.com](mailto:&#x62;&#x6f;&#115;&#115;&#64;&#121;&#111;&#x75;&#x72;&#45;&#x63;&#x6f;&#x72;&#x70;&#46;&#x63;&#x6f;&#x6d;)* を送信者とするメールを送信できる。メール受信側は SPF レコードと IP アドレスを利用して送信サーバーが正当かどうかを識別し、SPF レコードの指示に従ってメール受信を許可するか拒否するかを判断する。

## SPF の導入方法

DNS システムにはかつて SPF 専用のリソースレコードタイプが存在したが、すでに廃止されている。現在の SPF はすべて TXT リソースレコードの形式で存在し、ホスト名は通常 @ である。たとえば、このブログの SPF は次のとおりである：

```bash
➞ dig chenxy.me txt +short
"v=spf1 include:spf.mail.qq.com ~all"
```

## SPF レコードの形式

SPF レコードは複数のサブ項目の区切りとして単一の空白を使用し、各サブ項目は qualifier、mechanism、modifier などのコンポーネントで構成される。解析時には左から右へ照合し、いずれかのサブ項目が一致した場合、直ちに照合処理を中止し、qualifier に従って SPF 検証結果を返す。

SPF レコードは固定の `v=spf1 `で始まり、SPF バージョンを示す。現在は spf1 に固定されている。

### Qualifier と Mechanism

#### Qualifier

SPF に存在する qualifier は mechanism の前に置かれ、以下の 4 種類がある。このうち + はデフォルトの qualifier であり、省略できる。

| Qualifier | Result | Explanation（対応する mechanism が一致した場合） |
| --- | --- | --- |
| + | Pass | 送信側のマシンが検査に合格し、本ドメインのメールボックスからメールを送信できるという明確な宣言 |
| - | Fail | 送信側のマシンが検査に合格せず、本ドメインのメールボックスからメールを送信できないという明確な宣言 |
| ~ | Soft Fail | 送信側のマシンが検査に合格しなかったようだという弱い宣言 |
| ? | Neutral | 本ドメインの管理者が、送信側のマシンが検査に合格するかどうかを明確に宣言していない |

#### Mechanism

##### all

all は常に一致する。このため、all より後ろの mechanism は有効にならない。all は通常、最後の mechanism として qualifier と組み合わせて「デフォルトの挙動」を設定するために使われる——他のポリシーがすべて一致に失敗した場合、本ドメインがこうした取りこぼしをどう扱うか。

本サイトの SPF 設定 `v=spf1 include:spf.mail.qq.com ~all` を例にすると：include の mechanism が一致に失敗した場合、最終的に all に到達して一致し、その qualifier に従って「soft fail」の結果を返す——通常、メール受信側はこのメールを拒否しないが、迷惑メールフォルダーに振り分ける。

##### include

include の形式は `include: *domain-spec*` であり、再帰的な SPF 検証プロセスを一度トリガーし、メール受信側に *domain-spec* で指定された SPF レコードを検査させる。*domain-spec* の検証結果が pass である場合にのみ（注意：soft fail でも不可）、この mechanism は一致したと見なされる。

include メカニズムは「管理境界を越える」ケース、つまり必要な SPF ルールが本ドメインの管轄に属さないドメインの下に置かれている場合を扱うために期待されている。これは「サードパーティの依存ライブラリをインポートする」ものに近く、後述の redirect はむしろ「社内の共有コード」に近い。

##### exists

形式は `exists: *domain-spec*` であり、受信側は指定されたドメインに A レコードの問い合わせを送信する（IPv6 であっても A レコードの問い合わせを使用する）。何らかの応答があれば一致成功となる。比較的複雑な検証に使うことができる。

このうち、*domain-spec* には以下のマクロを含めることができる：

| マクロ | 意味 | 例 |
| --- | --- | --- |
| s | 送信者のメールアドレス | &#x68;&#x73;&#x69;&#x61;&#x6f;&#x78;&#x79;&#x63;&#x68;&#x65;&#x6e;&#x40;&#x65;&#x78;&#x61;&#x6d;&#x70;&#x6c;&#x65;&#x46;&#x63;&#x6f;&#x6d; |
| l | 送信者の「ローカルアドレス」 | hsiaoxychen |
| o | 送信者のドメイン部分 | example.com |
| d | 現在検証中の SPF 権威ドメイン。通常は上記と一致するが、include を解析する際に変わる可能性がある | example.com |
| i | 送信側の IP | 114.5.1.4 |
| v | IPv4 なら in-addr、IPv6 なら ip6 | in-addr |
| h | HELO&#x2F;EHLO のドメイン | mail.example.com |

また、マクロの後ろに r を付加すると、値を逆順にできる。たとえば、次の SPF レコードがあるとする：

```log
v=spf1 exists:%{ir}.%{l}._spf.example.com -all
```

また、_spf.example.com サブドメインの下には A レコードが 1 つだけある：

```log
4.1.5.114.noreply._spf.example.com IN A 127.0.0.1
```

この場合、`114.5.1.4` から送信された `noreply@example.com` からのメールだけが SPF 検証を通過できる。

##### その他の Mechanism

その他の mechanism には、a、mx、ip4、ip6、exists がある。これらの仕組みはどれも比較的似ており、理解しやすい。整理すると以下のとおり：

| a | 送信側 IP が、指定ドメインの任意の A レコード（または AAAA レコード。今回の送信が IPv4 経由か IPv6 経由かによって決まる）の IP アドレスに一致すれば、一致成功 |
| --- | --- |
| mx | 送信側 IP が、指定ドメインの任意の MX レコードに一致すれば、一致成功 |
| ip4 | 送信側 IP が、指定された IPv4 アドレス（範囲）に一致すれば、一致成功 |
| ip6 | 送信側 IP が、指定された IPv6 アドレス（範囲）に一致すれば、一致成功 |

### Modifier

modifier の構文は mechanism と少し異なり、qualifier を持たず、キーと値の区切りは `:` ではなく `=` である。現在、modifier には redirect と exp の 2 種類がある。exp は SPF 検証失敗後にサーバーへ説明文をどのように生成するかを伝えるために使われるが、ここでは紹介しない；redirect は後続の SPF 検証プロセスを対象ドメインへ「リダイレクト」できる。たとえば gmail.com の SPF レコード：

```bash
➞  dig gmail.com txt +short
"globalsign-smime-dv=CDYX+XFHUw2wml6/Gb8+59BsH31KzUr6c1l2BPvqKX8="
"v=spf1 redirect=_spf.google.com"

➞  dig _spf.google.com txt +short
"v=spf1 include:_netblocks.google.com include:_netblocks2.google.com include:_netblocks3.google.com ~all"
```

異なるドメインの下にあるが、_spf.google.com の SPF ポリシーは gmail.com を代表できる。

注意：redirect は SPF レコードの最後の部分として現れなければならず、all が存在する場合、redirect は必ず無視されなければならない。

## SPF レコードの実例分析

```bash
➞  dig chenxy.me txt +short
"v=spf1 include:spf.mail.qq.com ~all"
# 检查 spf.mail.qq.com 的匹配结果，如果匹配失败，则返回 soft fail

➞  dig spf.mail.qq.com txt +short
"v=spf1 include:spf-a.mail.qq.com include:spf-b.mail.qq.com include:spf-c.mail.qq.com include:spf-d.mail.qq.com include:spf-e.mail.qq.com include:spf-f.mail.qq.com include:spf-g.mail.qq.com -all"
# 依次检查各个 include 的匹配结果，如果都匹配失败，则返回 fail

➞  dig spf-a.mail.qq.com txt +short
"v=spf1 ip4:203.205.251.0/24 ip4:103.7.29.0/24 ip4:59.36.129.0/24 ip4:113.108.23.0/24 ip4:113.108.11.0/24 ip4:119.147.193.0/24 ip4:119.147.194.0/24 ip4:59.78.209.0/24 ip4:113.96.223.0/24 ip4:183.3.226.0/24 ip4:183.3.255.0/24 ip4:59.36.132.0/24 -all"
# 如果发件方不在这些 ip 段之中则返回 fail
```

実際に運用されている SPF レコードでは、exists や exp などの mechanism はほとんど使われておらず、大半は正当な IP 範囲を簡単に指定しているだけのようだ。

もう一種類の比較的典型的な SPF レコードの書き方は：

```log
v=spf1 a mx ip4:114.5.1.4 -all
```

これは「本ドメインの a、mx レコードに含まれる IP および 114.5.1.4 だけが本ドメインとしてメールを送信できる」ことを表し、自前で構築した個人向けメールサーバーによく見られる。
