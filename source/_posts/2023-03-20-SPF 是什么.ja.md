## SPF とは何か

現在広く使われている送信プロトコル [SMTP](https://zh.wikipedia.org/zh-hans/简单邮件传输协议) では、送信側が送信者のメールアドレスを任意に設定でき、誰でも *boss@your-corp.com* と名乗って他人にメールを送ることができます。そのため、SPF (Sender Policy Framework) 機構が提案され、電子メール送信側（メール転送エージェント、MTA）を検証し、*your-corp.com* に承認されたサーバーのみが *boss@your-corp.com* を送信者とするメールを送信できるようにします。メール受信側は SPF レコードと IP アドレスを利用して送信サーバーが正当か識別し、SPF レコードの指示に従ってメール受信を承認するか拒否するかを判断します。



## SPF の導入方法

DNS システムにはかつて専用の SPF リソースレコードタイプが存在しましたが、すでに廃止されています。現在の SPF はすべて TXT リソースレコードの形式で存在し、ホスト名は通常 @ です。たとえば本ブログの SPF は以下のとおりです：



```bash
➞ dig chenxy.me txt +short
"v=spf1 include:spf.mail.qq.com ~all"
```

## SPF レコードの形式

SPF レコードは単一のスペースを複数のサブ項目の区切りとして使用し、各サブ項目は qualifier、mechanism、modifier などのコンポーネントで構成されます。解析時には左から右へ一致を試み、いずれかのサブ項目が一致に成功すると、直ちに一致処理を中止し、qualifier に従って SPF 検証結果を返します。

SPF レコードは固定の `v=spf1 `で始まり、SPF バージョンを示します。現在は spf1 に固定されています。

### Qualifier と Mechanism

#### Qualifier

SPF に存在する qualifier は mechanism の前に置かれ、以下の 4 種類があります。このうち + はデフォルトの qualifier として省略できます。

| **Qualifier** | **Result** | **Explanation** *(対応する mechanism が一致に成功した場合)*              |
| ------------- | ---------- | ------------------------------------------------------------ |
| +             | Pass       | 送信側のマシンが検査に合格し、本ドメインのメールボックスからメールを送信できるという明確な宣言 |
| -             | Fail       | 送信側のマシンが検査に合格せず、本ドメインのメールボックスからメールを送信できないという明確な宣言 |
| ~             | Soft Fail  | より弱い宣言で、送信側のマシンは検査に合格していないようである |
| ?             | Neutral    | 本ドメインの管理者は、送信側のマシンが検査に合格したかどうかを明確に宣言していない |

#### Mechanism

##### all

all は常に一致に成功します。そのため、all より後ろの mechanism は有効になりません。all は通常、最後の mechanism として用いられ、qualifier と組み合わせて「デフォルト動作」を設定します——他のポリシーがすべて一致に失敗した場合、本ドメインがこうした漏れに対処する方針は何か、ということを定めます。

本サイトの SPF 設定 `v=spf1 include:spf.mail.qq.com ~all` を例にすると：include という mechanism が一致に失敗した場合、最終的に all に到達して一致に成功し、その qualifier に従って「soft fail」結果を返します——通常、メール受信側はこのメールを拒否しませんが、メールを迷惑メールフォルダーに入れます。

##### include

include の形式は `include: *domain-spec*` で、再帰的な SPF 検証プロセスを一度トリガーし、メール受信側に *domain-spec* で設定された SPF レコードを確認させます。*domain-spec* の検証結果が pass の場合にのみ（注意：soft fail でも不可）、本 mechanism は一致に成功したと見なされます。

include 機構は「行政境界をまたぐ」状況、すなわち必要な SPF ルールが本ドメインの管轄に属さないドメインの下に置かれている場合を処理するために期待されています。これはむしろ「サードパーティ依存ライブラリのインポート」であり、後述の redirect はむしろ「社内の共通コード」に似ています。

##### exists

形式は `exists: *domain-spec*` で、受信側は指定ドメインに A レコード照会を送信し（IPv6 であっても A レコード照会を使用）、何らかの応答があれば一致に成功します。比較的複雑な検証に使用できます。

このうち、*domain-spec* には以下のマクロを含めることができます：

| マクロ | 意味                                                         | 例                    |
| ---- | ------------------------------------------------------------ | ----------------------- |
| s    | 送信者のメールアドレス                                               | hsiaoxychen@example.com |
| l    | 送信者の「ローカルアドレス」                                         | hsiaoxychen             |
| o    | 送信者のドメイン部分                                             | example.com             |
| d    | 現在検証中の SPF 権威ドメイン。通常は上記と一致するが、include の解析時には変化する可能性がある | example.com             |
| i    | 送信側の IP                                                  | 114.5.1.4               |
| v    | IPv4 なら `in-addr`、IPv6 なら `ip6`           | in-addr                 |
| h    | HELO/EHLO のドメイン                                             | mail.example.com        |

同時に、マクロの後ろに r を付加すると、値を逆順にできます。たとえば、次の SPF レコードがあるとします：



```log
v=spf1 exists:%{ir}.%{l}._spf.example.com -all
```

また、_spf.example.com サブドメイン下には A レコードが 1 つだけあります：



```log
4.1.5.114.noreply._spf.example.com IN A 127.0.0.1
```

その場合、`114.5.1.4` から送信された `noreply@example.com` からのメールだけが SPF 検証に合格できます。

##### その他の Mechanism

その他の mechanism には、a、mx、ip4、ip6、exists が含まれ、それらの仕組みはどれも比較的似ており理解しやすいので、以下のように整理します：

| a    | 送信元 IP が指定ドメインのいずれかの A レコード（または、今回の送信が IPv4 か IPv6 かによって AAAA レコード）の IP アドレスに一致すれば、一致成功 |
| ---- | ------------------------------------------------------------ |
| mx   | 送信元 IP が指定ドメインのいずれかの MX レコードに一致すれば、一致成功     |
| ip4  | 送信元 IP が指定された IPv4 アドレス（範囲）に一致すれば、一致成功         |
| ip6  | 送信元 IP が指定された IPv6 アドレス（範囲）に一致すれば、一致成功         |

### Modifier

modifier の構文は mechanism とやや異なり、qualifier がなく、キーと値の区切りは `:` ではなく `=` です。現在、modifier は redirect と exp の 2 種類があります。exp は SPF 検証失敗後にサーバーに説明テキストをどのように生成するかを伝えるためのもので、ここでは紹介しません；redirect は後続の SPF 検証プロセスを対象ドメインへ「リダイレクト」できます。たとえば gmail.com の SPF レコード：



```bash
➞  dig gmail.com txt +short
"globalsign-smime-dv=CDYX+XFHUw2wml6/Gb8+59BsH31KzUr6c1l2BPvqKX8="
"v=spf1 redirect=_spf.google.com"

➞  dig _spf.google.com txt +short
"v=spf1 include:_netblocks.google.com include:_netblocks2.google.com include:_netblocks3.google.com ~all"
```

異なるドメインの下にありますが、_spf.google.com の SPF ポリシーは gmail.com を代表できます。

注意：redirect は SPF レコードの最後の部分として出現しなければならず、all が出現する場合、redirect は必ず無視されなければなりません。

## SPF レコードの実例分析



```bash
➞  dig chenxy.me txt +short
"v=spf1 include:spf.mail.qq.com ~all"
# 检查 spf.mail.qq.com 的匹配结果，如果匹配失败，则返回 soft fail

➞  dig spf.mail.qq.com txt +short
"v=spf1 include:spf-a.mail.qq.com include:spf-b.mail.qq.com include:spf-c.mail.qq.com include:spf-d.mail.qq.com include:spf-e.mail.qq.com include:spf-f.mail.qq.com include:spf-g.mail.qq.com -all"
# 依次检查各个 include 的匹配结果，如果都匹配失败，则返回 fail

➞  dig spf-a.mail.qq.com txt +short
"v=spf1 ip4:203.205.251.0/24 ip4:103.7.29.0/24 ip4:59.36.129.0/24 ip4:113.108.23.0/24 ip4:113.108.11.0/24 ip4:119.147.193.0/24 ip4:119.147.194.0/24 ip4:59.78.209.0/24 ip4:113.96.223.0/24 ip4:183.3.226.0/24 ip4:183.3.255.0/24 ip4:59.36.132.0/24 -all"
# 如果发件方不在这些 ip 段之中则返回 fail
```

実際に使用される SPF レコードでは exists、exp などの mechanism はほとんど使われず、多くは単に合法な IP 範囲を指定するだけのようです。

もう 1 つの比較的典型的な SPF レコードの書き方は次のとおりです：



```log
v=spf1 a mx ip4:114.5.1.4 -all
```

これは「本ドメインの a、mx レコードにある IP および 114.5.1.4 のみが本ドメインを代表してメールを送信できる」ことを表し、自前で構築した個人メールサーバーによく見られます。
