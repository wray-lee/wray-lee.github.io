## 2. 下载模式(最大的坑)[已验证]

- 直连 `--kickto 2` 在这台上**始终失败**:日志出现 `kick reboot timeout`,**但 spd_dump 退出码是 0**,bat 末尾 `pause`,像正常结束实际没写任何字节。用户之前"刷 B09 还是 B08"很可能就是这个 [推断]。
- **可用:短接模式命令**(不带 `--kickto`,手动加载 FDL1/FDL2):
```
spd_dump.exe --wait 300 exec_addr 0x65012f48 fdl <fdl1-dl.bin> 0x65000800 fdl <fdl2-dl.bin> 0xb4fffe00 exec path <dir> <操作...> reset
```
- 操作:拔线 → 短接测试点 → 保持短接插线(命令先启动或已连着都行)。
- 一次 `usb_send failed (0 / 1)` 是接触不稳,重来。**成功与否只看日志里的 `Write Part Done`,不要看退出码。**

## 3. 刷机步骤

### A 备份(用户做)
任何刷机前先有 B08 原始备份。

### B 刷 B09 ROM(擦 userdata)[已验证]
```
spd_dump.exe --wait 300 exec_addr 0x65012f48 fdl <fdl1> 0x65000800 fdl <fdl2> 0xb4fffe00 \
  exec path <temp> write_parts <zte-f50-b09\> e userdata reset
```
写入全部 `zte-f50-b09\*.bin`(含 splloader、ztepersist、super 2GB、misc),约 2.7GB。

### C root + 补丁 trustos [已验证]
```
... exec path <bin> w trustos <bin\f50b09_t.bin> w boot <bin\magiskf50b09.img> reset
```
只写当前 slot(slot a)的 `trustos_a`、`boot_a`,不擦 userdata。`f50b09_t.bin`(5178856 字节,MD5 前缀 a110ecb1)与作者 `trustos.bin` 相同。boot 用 `magiskf50b09.img`(0e9e8a4d);作者 kkroot 的 `boot.bin`(f2e8db4a)是另一个文件,都是 Magisk 镜像。刷后 `ro.boot.flash.locked` 仍显示 1,但 Linux 能启动。

### D 开 adb [效果已验证;机制 **[待补]**]
- **重要发现:刷 B09 或收缩 userdata 的恢复出厂之后,adb 仍然可用**:这个 ROM 自带 UFI-TOOLS(`com.minikano.f50_sms`)和 Magisk stub,且 `persist.sys.usb.config=adb`、`persist.adb.tcp.port=5555` 保存在 persist 分区,恢复出厂不丢。只有第一次(B08 刚刷完 B09 时)需要用临时无线 adb 工具开。
- 临时无线 adb 工具(静态逆向已完成,**详见附录 A**)。**更正**:我早先写过它"走串口 AT",那是错的,它**没有任何串口逻辑**。真实流程 6 步:① HTTP `USB_PORT_SETTING&usb_port_switch=0`(先关)→ ② `=1`(再开)→ ③ `REBOOT_DEVICE`(重启)→ ④ `adb wait-for-device` → ⑤ `adb shell` 改 `setprop` 并往 `/data/samba/etc/smb.conf` 写 `preexec = start adbd`、`guest ok = yes` 等 → ⑥ 用 Guest 空密码连 SMB(445)触发 `start adbd`;最后 `adb connect 192.168.0.1`。HTTP 登录:`H1=SHA256(pwd)`、`H2=SHA256(H1+LD)`,AD=`SHA256(SHA256(wa_inner_version+cr_version)+RD)`,端口 **8080**。"无法操作端口"其实是第 1 步 HTTP 响应里没有 `result`,不是串口错误。
- 所以"单纯网页开关不够"的原因:无线 adb 的开关是 Samba 的 `preexec = start adbd`,要有人(Guest)连一次 SMB 才会启动 adbd;重启后没人连就没有监听 [推断]。
- 替代脚本:`F:\Projects\tmp\f50\re\f50_wireless_adb.py`。**已在真机上测过(2026-10-27,见附录 A §A9)**:HTTP 登录、`USB_PORT_SETTING` 0→1、`REBOOT_DEVICE`、等 USB adb 回来,这一整段**验证通过**;Samba 那段在这个固件上不可用(`smb.conf` 是 immutable);`adb connect` 无线那段这次**没通**。风险见附录 A §A6。
- **更正前面的说法**:Samba 的 `preexec = start adbd` 不是这个固件上开 adb 的关键。真正让 adb 出现的是前三步的 HTTP(`USB_PORT_SETTING` 先 0 再 1,然后 `REBOOT_DEVICE`),这点已实测;TCP 5555 的监听来自 `persist.adb.tcp.port=5555`。
- **该程序有破坏性副作用**:每次先发 `usb_port_switch=0` 且失败不恢复,反复运行会把 `persist.sys.usb.config` 从 `adb,rndis` 改成 `adb` 并让 `192.168.0.1` 暂时不可达。同时存在 USB adb 和 `192.168.0.1:5555` 两个设备时它会报 `more than one device`,先 `adb disconnect`。
- 固件 adbd **不校验密钥**:`ro.adb.secure=1` 但 `/data/misc/adb/adb_keys` 不存在也能连,无需配对。

MU300_ANS_DEFAULT_LINUX=yes
MU300_ANS_BOOT_ATTEMPTS=5
MU300_ANS_ADB=yes
MU300_ANS_GPU=yes

- 命令:`install.ps1 -Lang en -NoResume -Package <包目录> -AnswersFile <answers>`。装完设备自动重启进 Linux。

## 4. Debian unstable 7.3 镜像(非官方构建)

**这不是项目官方镜像。** 官方只发 Ubuntu 24.04/26.04 与 OpenWrt;`docs/DISTROS.md` 的 Debian 13 构建只标 "same package names as Ubuntu",没在真机测过。本次由后台代理在 WSL 构建。

- 构建基础:`debian:unstable`(arm64,需 qemu binfmt),Dockerfile 补丁:`docker-compose-v2`→`docker-compose` 并补 `docker-cli`。
- `assemble.sh` 补丁:`KREL`、`UBUNTU` 可用 `MU300_KREL`、`MU300_UBUNTU_RELEASE` 覆盖;增加 `/release` 挂载复用 release 自带 `opt/mu300`、`etc/mu300` 等;**修复 NTFS 检出导致 overlay 变成 1000:1000/0777**(连 `/`、`/etc`、`/usr` 都被带成 777),按 release 清单还原属主权限。
- 保留清单里的 `SYSTEM=ubuntu-26.04`/`OS=ubuntu` 身份和文件名以过白名单,只替换 rootfs 载荷并更新 `SHA256_ROOTFS` 与 `SHA256SUMS`,删除签名(包未签名,仅本地自用)。
- 复用 release 的静态 aarch64 辅助程序(`logdw`、`adbd`、`mu300-keys`、`mu300-bt-init`、`mu300-carry`),内核模块来自 `mu300-kernel-7.3.tar.gz`(3059 个 `.ko`),**没自己编译内核**。
- 产物:rootfs `mu300-ubuntu-26.04-rootfs.tar.gz`(261.7 MiB,解包 834 MiB,SHA256 `5e5797470b61810c32d2d51b111ba6f9667b91aea0e0e7e373b39896ccb48bf2`);整个包 319.8 MiB。
- 验证:安装器 `package_load/package_verify` → `PACKAGE OK`;`dpkg --audit` 干净;apt 从 deb.debian.org 实测成功;关键组件齐全。

### 已知风险
- **`mu300-update apply` 会把系统整体换成 Ubuntu 24.04**(Debian 无 `VERSION_ID`,它退到 Ubuntu rootfs)。已处理:`/opt/mu300/bin/mu300-update` 与 `/usr/local/bin/mu300-update` 改名为 `.disabled`,`mu300-update-notice.timer` 已 disable。控制面板的更新接口在二进制缺失时返回 unsupported;`mu300-accounts.service` 仅在标记文件存在时才调用它(正常不存在)。Debian 更新用 `apt`。
- 面板/`mu300-os` 会把它当 Ubuntu 26.04 看待,版本号显示为空。
- sid 是滚动发行,构建结果随日期漂移。
- 没有 SIM,modem/移动数据未测;Wi-Fi 热点、蓝牙、GPU 未逐项验证。

## 7. 怎么切换系统(Linux ⇄ Android)

在 **Linux** 里(`wray` 需要 sudo,或用 adb root):
```
sudo mu300-next-boot android     # 下次(及之后)重启进 Android
sudo mu300-next-boot linux       # Linux 保持为默认(每次成功启动后自动重新武装)
sudo mu300-next-boot status
sudo mu300-next-boot attempts N  # 连续失败几次回 Android(1-6,现为 5)
sudo mu300-next-boot lock        # 无论如何都留在 Linux(失败启动也不回 Android)
sudo mu300-next-boot unlock
sudo mu300-os <系统>             # 多个 Linux 系统之间选(目前只有一个 ubuntu=本次的 Debian)
```
然后 `sudo reboot`。没有电脑时的兜底:在 Linux 启动期间连续断电 5 次,会自动回 Android。

在 **Android**(Magisk)里:`su -c mu300-linux` 在下次 Android 启动后进 Linux。

## 10. 踩坑清单

1. spd_dump 退出码不可信,看 `Write Part Done`。
2. 直连 `--kickto 2` 在这台上不可用,用短接模式命令。
3. 拿到 root 后 `su` 不在 PATH 之前用 `/debug_ramdisk/su`;Git Bash 设 `MSYS_NO_PATHCONV=1`。
4. 临时无线 adb 工具有破坏性副作用,别反复运行。
5. PowerShell 模块路径(`Get-FileHash`);GNU tar 解析 `F:\`;安装器自更新吞输出。
6. 缺 answers 变量时安装器中止且不写入,按报错补变量。
7. 自定义包不能走收缩事务的续装,要 `-NoResume` + `OVERWRITE=overwrite`。
8. 进程内存转储会混入当前环境变量(含令牌),用完立即 shred;**本次会话里这个令牌已进入过对话记录,建议轮换**。
9. 刷 ROM 会覆盖 ztepersist/splloader 等设备分区,务必先有 B08 原始备份。
10. heredoc 里未转义的 `$(...)` 在电脑端展开;设备上的密码用独立命令设置。
11. 反复在设备上运行 mu300-update 之类更新器会毁掉自建 Debian,已改名禁用。
12. 内存转储/读进程内存来"看串口指令"是错误方法:字符串被混淆,而且 `\\.\COM%u` 来自 Go 标准库,我据此得出"走串口"的结论是错的。要用真正的静态解包(壳 = LZMA)。

**修复后的 `network_block()`(替换 `/opt/mu300/bin/wifi-client` 中同名函数,约第 733–760 行;其余部分不变)**:

```sh
# the supplicant's network block. The name goes in hex, so any byte (quotes, UTF-8) is taken as it is. The
# passphrase goes in as wpa_passphrase's hash, handed to it on stdin (an argument would be on its command line
# for ps), and its "#psk=" comment with the plain passphrase is left out. SAE cannot use the hash: with SAE it
# also goes in as sae_password, which is why the file is root's alone.
# Debian sid: wpa_passphrase 2.11 calls tcgetattr on stdin and prints nothing when piped, so h is empty there;
# fall back to a quoted passphrase, which wpa_supplicant hashes itself (8..63 characters, same 0600 root file).
network_block() {  # network_block SSID PASS SAE
    printf 'network={\n\tssid=%s\n' "$(hex "$1")"
    if [ -z "$2" ]; then
        printf '\tkey_mgmt=NONE\n'
    else
        h=$(printf '%s\n' "$2" | wpa_passphrase "$1" 2>/dev/null | sed -n 's/^[[:space:]]*psk=\([0-9a-fA-F]\{64\}\)$/\1/p')
        if [ -n "$h" ]; then
            printf '\tpsk=%s\n' "$h"
        else  # wpa_passphrase failed (sid)
            [ "${#2}" -ge 8 ] && [ "${#2}" -le 63 ] || return 1
            printf '\tpsk="%s"\n' "$2"
        fi
        if [ "$3" = 1 ]; then
            # WPA2, WPA2/WPA3 and WPA3-only networks alike; WPA3 requires management frame protection
            printf '\tkey_mgmt=WPA-PSK SAE\n\tieee80211w=1\n\tsae_password=%s\n' "$(hex "$2")"
        else
            printf '\tkey_mgmt=WPA-PSK\n'
        fi
    fi
    printf '}\n'
}
```

### A3. HTTP 登录算法(`zreq`)[已验证]

- 基址 `http://192.168.0.1:8080`;请求头 `User-Agent: Mozilla/5.0`、`Referer: http://<ip>:8080/index.html`、`Content-Type: application/x-www-form-urlencoded`、`Cookie: <登录后 Set-Cookie 第一段>`。`Host` 头源码写 `<ip>`,Go 实际发送大概率是 `<ip>:8080` [未确认]。
- LD:`GET /goform/goform_get_cmd_process?isTest=false&cmd=LD&_=<毫秒>` → JSON `LD`。
- 登录:
  - `H1 = SHA256(password).upper()`
  - `H2 = SHA256(H1 + LD).upper()`
  - `POST /goform/goform_set_cmd_process` body `goformId=LOGIN&isTest=false&password=<H2>`,取 `Set-Cookie` 第一段为 Cookie。
- 取 UFI 信息:`GET …cmd=Language,cr_version,wa_inner_version&multi_data=1` → `wa_inner_version`、`cr_version`;取 RD:`GET …cmd=RD`。
- AD:`H3 = SHA256(wa_inner_version + cr_version).upper()`,`AD = SHA256(H3 + RD).upper()`(注意是 **RD**,不是 U20 脚本里的 JSESSIONID)。
- 最终 POST body 由 `url.Values.Encode()` 生成(key 字典序),例如 `AD=<AD>&goformId=USB_PORT_SETTING&isTest=false&usb_port_switch=0`。
- 密码是工具内置的一个 14 字节通用管理员登录串,`zreq` 对**字面 14 字节**做 SHA-256,不做 base64 解码。**本文不记录该串**;如需要,见 `F:\Projects\tmp\f50\re\f50_wireless_adb.py`。
- U20 的 PowerShell 脚本(`O:\F50\kkfile\bin\u20_openadb.ps1`)用的是另一套算法(`192.168.88.1`、80 端口、JSESSIONID),**不要混用**。

4. 第 5、6 步改成尽力而为:失败只警告,继续尝试 `adb connect`,以最终 adb 是否连上为准。

**新发现**
- `smb.conf` immutable → Samba 路线在这个固件上不可用;有线 adb 靠 HTTP 的 `USB_PORT_SETTING` + 重启就够。
- 重启后 `sys.usb.config` 从 `rndis,mtp,adb` 变成了 `ecm,mtp,adb`:Windows 没有 ECM 网卡驱动,**电脑的 USB 网卡消失**,所以 HTTP 通道必须走 Wi-Fi(连设备热点)才可靠。
- 设备的 `iptables` 里 `INPUT` 只放行来源 `192.168.0.0/24` 的 8080;从 `adb forward` 的回环进来的 8080 被丢(我临时加回环放行的命令挂住了,重启后规则自然消失)。
- `persist.sys.usb.config` 试验前后都是 `adb`,脚本的 `setprop persist.sys.usb.config adb,rndis` 在 shell 身份下没有生效。

**复原情况**
- `/data/samba/etc/`:`sed` 失败留下的 12 个临时文件(`smb.conf` + 6 位随机字符)和脚本建的 `smb.conf.bak.opener` 都已删除;`smb.conf` 的 MD5 前后一致(`cf419aec312cf4b6abaa849d67e31093`),immutable 属性未动。
- USB 调试开关最终为"开"(adb 可用),`persist.adb.tcp.port=5555`、`persist.sys.usb.config=adb` 与测试前相同。
- 设备已切回 Linux,SSH/docker/`wifi-client` 补丁/`mu300-update` 禁用均保持,`degraded` 是首次启动残留标记(`systemctl --failed` 为空)。
- Android 侧遗留(无害):`/data/local/tmp/bbdir/busybox`(下面切换要用),可在下次进 Android 时删除。

**切回 Linux 时踩到的坑(重要)**
- 在 Android 里 `su -c mu300-linux` 报 `misc resolves outside /dev/block ()`,接着 `status` 说 `boot_b … a copy of Android's boot image (no Linux installed)`——**这是误判,Linux 没丢**。根因:Magisk 自带的 `/data/adb/magisk/busybox` 在这台设备上是坏的(`--list` 为空,`readlink -f` 返回空),脚本拿不到 misc 的真实路径,两个镜像的头部 MD5 也都算成空串所以判成"相同"。
- 解决:用安装包里的 busybox,**必须用 `busybox` 这个文件名**(多合一二进制按 argv[0] 找 applet,命名成别的会报 `applet not found`):
  ```
  adb push <包目录>\mu300\busybox /data/local/tmp/bbdir/busybox ; chmod 755
  su -c "MU300_BUSYBOX=/data/local/tmp/bbdir/busybox mu300-linux status"     # 应显示 boot_b: the Linux boot image
  su -c "MU300_BUSYBOX=/data/local/tmp/bbdir/busybox mu300-linux --dry-run"   # 只显示将写的 32 字节,不写
  su -c "MU300_BUSYBOX=/data/local/tmp/bbdir/busybox mu300-linux"             # 真正切换并重启
  ```
- 额外观察:`dd` 出来的 `boot_b` 的 MD5(`9d7a4a10…`)与安装时推送的 `work/boot-linux-slotb.img`(`029289…`)不一致,但内容是 Linux 镜像(含 `mu300` 字符串、无 Magisk、能正常启动)。原因未查(可能是安装器写入前做了处理或首次启动后更新)。

**待办(无线 adb)**:查清 5555 为什么从电脑 Wi-Fi 进不去(看 `ip6tables`、`raw`/`mangle` 表、hostapd 客户端隔离、adbd 是否只监听回环);确认全新设备上第一次开 adb 是否同样只需要 HTTP 的 0→1 + 重启。

## 附录 B:`USB_PORT_SETTING` 在设备里到底做了什么(反编译网页后台 APK)

来源:`/system/priv-app/ZteWebServer/ZteWebServer.apk`(进程 `com.zte.web`,监听 8080,`sharedUserId=android.uid.system`)。代理离线反编译,完整报告与代码片段:`F:\Projects\tmp\f50\zteweb\notes\{REPORT.txt,UsbTools.java,DeveloperModule_usb_excerpt.java.txt,framework_adb_chain.txt}`。2026-10-27。标注 **[代码证据]** / **[推断]**;现场印证见 B5。

### B1. 核心结论
**`USB_PORT_SETTING` 只做一件事:写系统设置 `Settings.Global adb_enabled`(1 = 开,0 = 关,其它值按 0)。** 它不写 `persist.sys.usb.config`/`sys.usb.config`,不调 `UsbManager`,不执行 shell,不发广播,不重启。[代码证据]
```java
// com.zte.web.module.developer.DeveloperModule.processGoFormId()
case "USB_PORT_SETTING":
    String s = bundle.getString("usb_port_switch");
    setUsbDeveloperMode(getContext(), "1".equals(s));
    JSONUtils.responseSuccess(jSONObject);          // 即使没有真正生效也回 success
public static void setUsbDeveloperMode(Context c, boolean z) {
    Settings.Global.putInt(c.getContentResolver(), "adb_enabled", z ? 1 : 0);
}
```
状态查询 `cmd=usb_port_switch` 读的也是 `adb_enabled`,**不是 USB 的真实状态**。

### B2. 真正起作用的是 system_server [代码证据,来自同机 B09 的 services.jar]
- `AdbService.setAdbEnabled()`:**只有值真实变化才继续,同值直接 return**。真实变化时 `ctl.start adbd`/`ctl.stop adbd`,并回调 `UsbDeviceManager`。
- `UsbDeviceManager.setAdbEnabled()`:开 → `persist.sys.usb.config="adb"`;关 → `"charging"`;然后重配 `sys.usb.config`。
- 开机 `AdbService.systemReady()` 反过来:读 `persist.sys.usb.config`,含 `adb` → `adb_enabled=1`,否则 `0`——**会覆盖上次网页写进 Settings 的值**。
- init:`on post-boot && property:sys.usb.config=none` → `setprop sys.usb.config ${persist.sys.usb.config}`;`on property:sys.usb.config=adb && property:sys.usb.configfs=1` → `start adbd`。
- SettingsProvider 对"写入相同值"也不通知观察者。所以**重复写 1 是彻底的空操作**。

### B3. 其它
- `REBOOT_DEVICE`:先回 success,500ms 后 `PowerManager.reboot("manualreboot")`。[代码证据]
- `UsbTools`(`USB_PROPERTY_KEY=persist.sys.usb.config`、`USB_PROPERTY_KEY_TMP=sys.usb.config`,开写 `rndis,diag,diag_mdm,adb`、关写 `rndis`,最后无条件重启)只被 `DEVELOPER_MODE_SETTING`/`SET_DEVICE_MODE` 调用,而本 APK 的 `DeveloperModule` 只注册了 `USB_PORT_SETTING`,这条路径在本固件上**不可达**。[代码证据+推断]
- 网页 UI:`index.html#usb_port` → `js/adm/usb_port.js` → `setUsbPortSwitch()`,提交的就是 `goformId=USB_PORT_SETTING` + `usb_port_switch=1/0`;**需要点 Apply 才发请求**,只点 radio 不发。页面标签是 "USB Port / USB端口",控制的是 `adb_enabled`。
- APK 里**没有**任何写 `service.adb.tcp.port`/`persist.adb.tcp.port` 或启停 adbd 的代码;设备上的 `persist.adb.tcp.port=5555` 是 ROM 里本来就有的持久属性。

### B4. 对"没有 adb 时怎么开出来"的最终答案
- **有线 adb**:让 `adb_enabled` 发生**一次真实的 0→1 变化**。框架会立刻 `ctl.start adbd`、把 `persist.sys.usb.config` 写成 `adb`、重配 USB,**代码上不需要重启**;`REBOOT_DEVICE` 只是让重启后按 `persist=adb` 稳定地重新组装 USB,是最稳的做法。
- **为什么只在网页上点开关会没用(你的经历)**:若开关本来就是 1(UI 显示的是 `adb_enabled`,不是 persist,也不是 adbd 的实际状态),再提交 1 就是同值,被两层短路成空操作;`persist.sys.usb.config` 没被写成 `adb`,重启时 `systemReady()` 按 persist 重算,又回到 0 → 仍然没有 adb,而 UI 可以一直显示 ON。**工具先发 0 再发 1,就是强制制造一次真实的 1→0→1 变化。** 换句话说:网页上要**先关掉、点 Apply、再打开、再点 Apply**。
- 次要可能:点了 radio 没点 Apply;重启抢在异步写 persist 之前;特定 SIM 状态下的 `ZTE_ADB_USB_SECURITY_RESTRICTION` 强制关 adb;adbd/USB 端点卡死需要重新枚举。
- **无线 adb 的 TCP 监听**:adbd 启动时读 `service.adb.tcp.port`/`persist.adb.tcp.port`;本设备 ROM 已带 `persist.adb.tcp.port=5555`,所以 adbd 一启动就同时监听 TCP 5555。**Samba 那一套在本固件上既做不了(`smb.conf` immutable)也不是必须**。但我们这次从电脑 Wi-Fi 连 `192.168.0.1:5555` 仍然超时,原因未查清(A9)。

### B5. 现场印证(2026-10-27,设备在 Android)
通过网页接口只读查询并登录后:`usb_port_switch → '1'`、`developer_mode_enable → '1'`;设备上 `settings get global adb_enabled = 1`、`persist.sys.usb.config = adb`、`sys.usb.config = rndis,mtp,adb`、`init.svc.adbd = running`、`persist.adb.tcp.port = 5555`。与模型一致。两个诊断接口不需要 adb 就能用(登录后):
- `GET /goform/goform_get_cmd_process?isTest=false&cmd=usb_port_switch` → `adb_enabled`
- `GET /goform/goform_get_cmd_process?isTest=false&cmd=developer_mode_enable` → `persist.sys.usb.config` 是否含 `adb`
若前者是 1 而后者是 0,就是上面那种"UI 显示 ON 但 persist 没有 adb"的分叉,此时先 0 再 1 即可。

### B6. 风险
- 单独发 `usb_port_switch=0`(真实 1→0)会把 `persist.sys.usb.config` 写成 `charging`;如果随后的 1 没成功,重启后 USB 只剩充电,RNDIS/ECM 和网页后台可能都不可达。**不要在没有恢复手段时单独发 0**——这正是原程序和我们脚本第 1 步之后失败会留下的坏状态。
- 代理的框架侧证据来自同机 B09 备份镜像;若设备运行的不是这个固件,`services.jar` 细节可能不同(APK 侧不受影响)。
