# ZTE F50(MU300)装 Debian 笔记

2026-10-26 ~ 27,把一台中兴 F50 存储版从 B08 刷到 B09、root、缩小 userdata,再装上 Debian unstable(内核 7.3),做成 Android + Debian 双系统。前面是日常怎么用,后面是怎么装出来的、踩过的坑和逆向结果。

## 一、先看这里:日常使用

### 设备现在的样子

ZTE F50 / MU300 存储版,Unisoc UMS9620,eMMC 234 GiB,没有电源键,没有屏幕。

- Android 是 B09 固件(`F50_FLYMODEM_ZYV1.0.0B09`),已 root(Magisk 28.1,Shell 已授权),装在 slot a,userdata 缩到了约 30 GiB。
- Linux 是 Debian forky/sid,内核 7.3.0,装在 slot b 和 userdata 之后的 198 GiB 区域里(ext4,可用约 191G)。默认启动 Linux,连续启动失败 5 次才退回 Android。
- bootloader 显示 locked,补丁版 trustos 已经刷了,在 locked 状态下 Linux 照样能起。
- Linux 里只有一个用户 `wray`(sudo、docker 组、zsh + oh-my-zsh + powerlevel10k)。安装器建的 `ubuntu` 用户已删。root 被锁(`PermitRootLogin no`),要 root 用 `sudo -i` 或 `adb shell`。
- 装了 docker 28.5、ufw、neovim、fzf、zoxide、lsd、duf、fastfetch、git、curl 等。时区 `Asia/Tokyo`。
- 没有 SIM,所以没有蜂窝网络。上网靠 Wi-Fi(连家里路由器 RayWrt,设备 IP 10.17.1.143),或者电脑当代理。
- wray 的密码在 `F:\Projects\tmp\f50\wray-credentials.txt`(明文,用完自己处理)。`answers-install.txt` 里的安装密码已经抹掉。

### 连上设备

| 方式 | 命令 | 说明 |
|---|---|---|
| Wi-Fi | `ssh wray@10.17.1.143` | 设备连着路由器时用,IP 以路由器分配为准 |
| USB 网络 | `ssh wray@192.168.77.1` | USB 线直连电脑,NCM 网卡,Windows 11 免驱,电脑会拿到 192.168.77.111 |
| USB adb | `adb shell` | 直接是 root shell |

SSH 只认密钥(Windows 的 `~/.ssh/authorized_keys` 里的 3 把:Wray-Arch ed25519、Wray-Win rsa、手机 u0_a355)。Linux 里的 adb 也只认 `/etc/mu300/adb_keys` 里的密钥(`adb_auth=keys`),不是对所有电脑开放。安装器末尾提示的 `ssh ubuntu@192.168.77.1` 是固定文案,实际要用 `wray@`。

在 Git Bash 里用 adb 带 `/data/...` 这类路径时,先 `export MSYS_NO_PATHCONV=1`,不然路径会被改写成 Windows 路径。

### 切换系统:一个必须记住的坑

从 Android 里执行 `mu300-linux` 进 Linux,只是"一次性试启动",此时 `/etc/mu300/default-boot` 还是 `android`。在 Linux 里直接 `reboot` 就会回 Android,看起来像"重启后自动 fallback",其实是设计如此。想让 Linux 一直当默认,进去后执行一次 `sudo mu300-next-boot linux`。现在已经设好了(`default-boot` 内容是 `linux`)。

2026-10-27 的实例:启动日志里有 `mu300-next-boot: default boot is not linux, nothing to do`,上一次的内核日志在 pstore 里,是一次正常的 `Restarting system`,不是崩溃。

在 Linux 里:

```sh
sudo mu300-next-boot status      # 默认启动是谁、已经连续失败几次
sudo mu300-next-boot linux       # 默认进 Linux(每次成功启动后自动重新武装)
sudo mu300-next-boot android     # 之后重启进 Android
sudo mu300-next-boot attempts 5  # 连续失败几次后退回 Android(1-6,现为 5)
sudo mu300-next-boot lock        # 钉死在 Linux,失败也不回 Android
sudo mu300-next-boot unlock
sudo mu300-os <系统>             # 多个 Linux 系统之间选,目前只有一个(就是这个 Debian)
sudo reboot
```

在 Android 里(adb,root):

```sh
adb shell
su
MU300_BUSYBOX=/data/local/tmp/bbdir/busybox mu300-linux status    # 看两个 slot,不改动
MU300_BUSYBOX=/data/local/tmp/bbdir/busybox mu300-linux --dry-run # 只显示要写的 32 字节
MU300_BUSYBOX=/data/local/tmp/bbdir/busybox mu300-linux           # 武装一次性试启动并重启进 Linux
```

必须带 `MU300_BUSYBOX`,因为 Magisk 自带的 busybox 在这台上是坏的(`--list` 为空,`readlink -f` 返回空),不带的话会报 `misc resolves outside /dev/block ()`,`status` 还会误判成"boot_b 是 Android 镜像、没装 Linux"。那是误判,Linux 没丢。要用安装包里的 busybox,而且文件名必须就叫 `busybox`(多合一二进制按 argv[0] 找 applet,换名字会报 `applet not found`):

```sh
adb push <包目录>\mu300\busybox /data/local/tmp/bbdir/busybox
adb shell chmod 755 /data/local/tmp/bbdir/busybox
```

切换后 `status` 应该显示 `boot_b: the Linux boot image`。查 slot 状态时输出形如 `slot a priority 15, tries 1, successful 1`、`slot b priority 14, tries 1, successful 0`。

没有电脑时的兜底:Linux 启动期间连续断电 5 次,自动回 Android。

### Wi-Fi:让设备连路由器

SC2355 的无线电一次只能做一件事:当热点(AP)或当客户端(station)。连上路由器后,设备自己的热点 `FRayWrt` 就关了。热点变客户端要重启,客户端回热点不用。只支持 WPA2 和 WPA2/WPA3 混合,纯 WPA3 和 Wi-Fi 7 的网络会被拒。USB 的 192.168.77.1 不受影响。

```sh
sudo wifi-client scan-mode on && sudo reboot   # 想扫描时:下次开机保持客户端模式
sudo wifi-client scan
sudo wifi-client connect "SSID"                # 交互输密码,不回显;SSID 已知时不用 scan
sudo reboot                                    # 重启后才真正加入
wifi-client status                             # 连接、地址、防火墙状态
sudo wifi-client reconnect                     # 改了配置或防火墙后重新应用
sudo wifi-client disconnect
sudo wifi-client forget
```

如果无线电此时还是热点模式,`scan` / `connect` 会提示 "the radio is an access point right now … cannot turn it back into a client without a reboot"。这不是故障,`connect` 会先保存网络,重启后再加入。密码用交互输入或 `--password-file`,不要写在命令行里(会进 journal 和 `ps`)。配置存在 `/etc/mu300/wifi-client.conf`(0600,root),内容是 SSID、PSK、`ENABLE=1`、`METRIC=50`。连上之后 Wi-Fi 上行优先于移动数据,理论上能通过 NAT 共享给 USB 客户端(没实测)。

这台设备已经连上家里路由器,开机自动加入(服务 `mu300-wifi-client.service` 跑 `wifi-client up`)。

### 给设备临时上网(没有 Wi-Fi/SIM 时)

设备刚装好时没有互联网,时钟也是错的,做法是让电脑当代理:

```sh
bash /f/Projects/tmp/f50/tools/device-online.sh on    # 电脑起代理(127.0.0.1:7890) + adb reverse,设备的 apt/docker 走代理
bash /f/Projects/tmp/f50/tools/device-online.sh off   # 用完关,会删掉设备上的代理配置
```

时钟不对时先校时(`date -u -s @<时间戳>`),否则 TLS 会失败。设备现在已经能通过 Wi-Fi 直接上网,一般不需要这步。

### 防火墙

入站规则现在交给 ufw 管:默认拒绝入站、允许出站、拒绝转发,只放行 22(tcp/udp,含 IPv6)。

```sh
sudo ufw status verbose
sudo ufw allow 22/tcp
sudo ufw allow from 10.17.1.0/24 to any port 8080 proto tcp   # 例:只对局域网开某个端口
sudo ufw delete allow 22/udp
```

`wifi-client` 自带一张 nft 表 `inet mu300_wifi_filter`。它原来的 input 链会把 wlan0 上除已建立连接、DHCP 回复、限速 ping 之外的入站全部丢掉,所以局域网能 ping 通设备却 SSH 不上(sshd 本身监听 `*:22` 没问题)。现在这条 input 链已经删掉,只留 forward 链(共享上行时禁止转发到内网)。`wifi-client status` 正常应显示 `shared with the LAN (internet only)`;如果显示 `mu300_wifi_filter is not as wifi-client puts it`,说明规则和脚本生成的不一致。

补丁脚本是 `F:\Projects\tmp\f50\tools\wifi-client.noinput.sh`,原文件备份为 `/opt/mu300/bin/wifi-client.orig2`。补丁改的是已安装的文件,系统升级或重装会覆盖它,到时要重打。项目自己的 `mu300_filter`(`/etc/mu300/firewall.nft`)只管蜂窝口、docker0 和 br-*,不影响 wlan0。

### 日常维护

```sh
sudo apt update && sudo apt full-upgrade     # Debian 更新只用 apt
systemctl --failed
sudo systemctl reset-failed                  # 首次启动残留的 degraded 标记
sudo journalctl -b -p warning --no-pager | tail -50
df -h /; free -h
docker ps; docker run --rm hello-world
systemctl status mu300-adbd                  # Linux 自己的 USB adb
sudo mu300-usb adb off                       # 关 Linux 的 USB adb
sudo mu300-usb adb auth keys                 # 只认 adb_keys 里的密钥(现状)
```

Linux 里的 adb 和 Android 的 adb 是两套东西。Linux 这边的 adbd 是镜像自带的静态 aarch64 程序(`/opt/mu300/bin/adbd`),由 `mu300-adbd.service` 开机自启,把自己加到 USB gadget 里(FunctionFS),和 Android 里的 HTTP 开关、Samba 触发都没关系。每次 adb 连接结束,gadget 会解绑,脚本会重新绑上,所以电脑上看起来像拔插了一下。

### 出问题怎么办

**SSH 连不上。** 先 ping。能 ping 通但 SSH 不通,查 `sudo ufw status` 和 `wifi-client status`。ping 不通,先看设备是不是回了 Android(Android 没有 22 端口)。

**Linux 起不来 / 想看上次的日志。** 设备会自己重试,连续失败 5 次回 Android。到 Android 里可以只读挂载 Linux 根分区看 journal。区域偏移量是安装时算出来的(38700843008),根文件系统在挂载点下的 `ubuntu/` 目录里:

```sh
# Android root shell
MU300_OFF=38700843008 MU300_RO=recover sh /data/local/tmp/android-mount-mu300root.sh /data/local/tmp/mu300root
ls /data/local/tmp/mu300root/ubuntu/var/log/journal
sh /data/local/tmp/android-mount-mu300root.sh -u /data/local/tmp/mu300root    # 看完卸载
```

journal 是二进制格式,拉到电脑(或 WSL)用 `journalctl --file=<文件>` 读。上次崩溃的内核日志在 Android 的 `/sys/fs/pstore/console-ramoops-0`。注意不带 `MU300_OFF` 会报 `NO-EXT4 magic=0000`,因为默认偏移不是这台的区域。

**Android 没有 adb。** 刷了 B09 或恢复出厂之后 adb 仍然可用,因为 `persist.sys.usb.config=adb` 和 `persist.adb.tcp.port=5555` 存在 persist 分区里。万一真没有了,看后面"无线 adb 是怎么开的"一节,用 `F:\Projects\tmp\f50\re\f50_wireless_adb.py`。

**完全砖了。** 短接测试点进下载模式,用 B08 原始备份刷回去。

### 要避开的坑(速查)

1. `mu300-update` 已被改名成 `.disabled`。它的 `apply` 会把系统整个换成 Ubuntu 24.04,毁掉自建的 Debian。别反复运行这类更新器,Debian 更新用 apt。
2. 控制面板和 `mu300-os` 会把这个系统当 Ubuntu 26.04 看,版本号显示为空,正常。
3. 从 Android 进 Linux 只是一次性的,见上。
4. Debian sid 的 `wpa_passphrase` 有 bug,`wifi-client connect` 原版会报 `could not build the wpa_supplicant configuration`,已打补丁(后面有完整代码)。
5. 设备上没有 python3 和 openssl,写脚本用 sh / awk / sed。
6. sid 是滚动发行,`full-upgrade` 前想一想,出问题没有官方镜像能退。
7. 热点国家码 `COUNTRY=TR` 是项目默认值,在日本应改成 `JP`,**还没改**。
8. 反复运行"临时无线 adb 工具"有破坏性,别这么干(见后文)。

## 三、怎么装出来的

### 1. 进入下载模式(这台最大的坑)

直连 `--kickto 2` 在这台上始终失败:日志出现 `kick reboot timeout`,但 spd_dump 的退出码是 0,bat 末尾还有 `pause`,看上去像正常结束,实际一个字节都没写。之前"刷了 B09 却还是 B08"很可能就是这个。

能用的是"短接模式"命令,不带 `--kickto`,手动加载 FDL1 和 FDL2:

```
spd_dump.exe --wait 300 exec_addr 0x65012f48 fdl <fdl1-dl.bin> 0x65000800 fdl <fdl2-dl.bin> 0xb4fffe00 exec path <目录> <操作...> reset
```

操作顺序是:拔线 → 短接测试点 → 保持短接插线(命令先启动或者已经连着都行)。出现一次 `usb_send failed (0 / 1)` 是接触不稳,重来。**成功与否只看日志里的 `Write Part Done`,不要看退出码。**

### 2. 刷 B09(擦 userdata)

任何刷机前,先确认手里有 B08 的原始备份;刷 ROM 会覆盖 ztepersist、splloader 这类设备分区。

```
spd_dump.exe --wait 300 exec_addr 0x65012f48 fdl <fdl1> 0x65000800 fdl <fdl2> 0xb4fffe00 \
  exec path <临时目录> write_parts <zte-f50-b09\> e userdata reset
```

会写入 `zte-f50-b09\` 下全部 `.bin`(含 splloader、ztepersist、2GB 的 super、misc),共约 2.7GB。

### 3. root + 补丁 trustos

```
... exec path <bin目录> w trustos <bin\f50b09_t.bin> w boot <bin\magiskf50b09.img> reset
```

只写当前 slot(slot a)的 `trustos_a` 和 `boot_a`,不擦 userdata。`f50b09_t.bin` 5178856 字节(MD5 前缀 a110ecb1),与作者包里的 `trustos.bin` 相同。boot 用的是 `magiskf50b09.img`(0e9e8a4d);作者 kkroot 的 `boot.bin`(f2e8db4a)是另一个文件,两个都是 Magisk 镜像。刷完之后 `ro.boot.flash.locked` 仍然显示 1,但 Linux 能启动。

### 4. adb

刷 B09 或者收缩 userdata 之后的恢复出厂,adb 仍然可用:这个 ROM 自带 UFI-TOOLS(`com.minikano.f50_sms`)和 Magisk stub,`persist.sys.usb.config=adb`、`persist.adb.tcp.port=5555` 保存在 persist 分区里,恢复出厂不丢。只有刚刷完 B09 的第一次,才需要用"临时无线 adb 工具"开(见第五部分)。固件的 adbd 不校验密钥:`ro.adb.secure=1`,但 `/data/misc/adb/adb_keys` 不存在也能连,不需要配对。

### 5. Magisk

1. `adb install Magisk_28103_origin.apk`。root 后设备上只有 stub,版本显示 `1.0`。
2. 打开 app 做"修复环境",重启。
3. 用 scrcpy 连上屏幕,给 Shell 授 root 权限。
4. `adb shell su -c id` 应该是 `uid=0`。修复前 `su` 不在 PATH,只有 `/debug_ramdisk/su`。

收缩 userdata 触发的恢复出厂之后,Magisk 的 app 还在,但要再修复一次、再授权一次。

### 6. 安装器和收缩 userdata

安装器用 PowerShell 版 `install.ps1`(本机没有 lz4)。在 Git Bash 里跑之前要先处理三个环境坑:

```sh
# 1) PowerShell 5.1 找不到 Get-FileHash:Git Bash 把 PowerShell 7 的模块路径排前面了
export PSModulePath='C:\Program Files\WindowsPowerShell\Modules;C:\WINDOWS\system32\WindowsPowerShell\v1.0\Modules'
# 2) 校验自定义包时 Git 自带的 GNU tar 会把 F:\... 当成远程主机(Cannot connect to F: resolve failed)
export PATH="/c/Windows/System32:$PATH"
# 3) 否则脚本自更新后重新执行,输出被吞
export MU300_NO_SELF_UPDATE=1
```

只读检查:`install.ps1 -Check -Lang en`。

收缩 userdata 用答案文件(`-AnswersFile`)。答案变量见 `install.sh` 头部注释。缺任何一个变量,安装器都会在提问处报 `no answer to the question ... set MU300_ANS_xxx` 并中止,而且中止时什么都没写。

```
MU300_LANG=en
MU300_ANS_MAKE_ROOM=yes
MU300_ANS_LINUX_GIB=198
MU300_ANS_ERASE_ANDROID=ERASE
MU300_ANS_REBOOT=yes
```

结果:userdata 从 228.19 GiB 缩到 30.19 GiB,后面空出 198.00 GiB,Android 走 recovery 恢复出厂。

### 7. 装 Debian 包

用自定义包续装会失败:`The prepared installation cannot be continued: this installer's tools or the package differ`。原因是事务里的 payload identity 是收缩时(当时没有包)算的,装自定义包时 identity 变了。处理办法是加 `-NoResume`。区域起始处有安装器自己写的 token,它会提示 "unpartitioned space is not empty",答 `MU300_ANS_OVERWRITE=overwrite`(这块区域是自己划出来的,确认是空的)。

完整答案文件:

```
MU300_LANG=en
MU300_ANS_PASSWORD=<至少6位>
MU300_ANS_DEFAULT_LINUX=yes
MU300_ANS_BOOT_ATTEMPTS=5
MU300_ANS_ADB=yes
MU300_ANS_GPU=yes
MU300_ANS_HOTSPOT=yes
MU300_ANS_VPN=no
MU300_ANS_PANEL=no
MU300_ANS_CONFIRM=INSTALL
MU300_ANS_REBOOT=yes
MU300_ANS_OVERWRITE=overwrite
MU300_ANS_SYSTEMS=1
MU300_ANS_KERNEL=7.3
```

命令:

```
install.ps1 -Lang en -NoResume -Package <包目录> -AnswersFile <answers>
```

## 四、这个 Debian 镜像是怎么来的

这不是项目官方镜像。官方只发 Ubuntu 24.04 / 26.04 和 OpenWrt;`docs/DISTROS.md` 里的 Debian 13 构建只写了 "same package names as Ubuntu",没有在真机上测过。这次的镜像由后台代理在 WSL 里构建。

- 基础是 `debian:unstable`(arm64,需要 qemu binfmt)。Dockerfile 补丁:`docker-compose-v2` 改成 `docker-compose`,并补上 `docker-cli`。
- `assemble.sh` 的补丁:`KREL`、`UBUNTU` 可以用 `MU300_KREL`、`MU300_UBUNTU_RELEASE` 覆盖;增加 `/release` 挂载来复用 release 自带的 `opt/mu300`、`etc/mu300` 等;修复了 NTFS 检出导致 overlay 变成 1000:1000 / 0777(连 `/`、`/etc`、`/usr` 都被带成 777)的问题,按 release 清单还原属主和权限。
- 保留清单里的 `SYSTEM=ubuntu-26.04`、`OS=ubuntu` 身份和文件名,以通过安装器的白名单,只替换 rootfs 载荷,并更新 `SHA256_ROOTFS` 与 `SHA256SUMS`,删掉签名(包是未签名的,仅本地自用)。
- 复用 release 的静态 aarch64 辅助程序(`logdw`、`adbd`、`mu300-keys`、`mu300-bt-init`、`mu300-carry`),内核模块来自 `mu300-kernel-7.3.tar.gz`(3059 个 `.ko`),没有自己编译内核。
- 产物:rootfs `mu300-ubuntu-26.04-rootfs.tar.gz`(261.7 MiB,解包 834 MiB,SHA256 `5e5797470b61810c32d2d51b111ba6f9667b91aea0e0e7e373b39896ccb48bf2`),整个包 319.8 MiB。
- 验证:安装器的 `package_load` / `package_verify` 输出 `PACKAGE OK`;`dpkg --audit` 干净;apt 从 deb.debian.org 实测成功;关键组件齐全。

已知风险:

- `mu300-update apply` 会把系统整个换成 Ubuntu 24.04(Debian 没有 `VERSION_ID`,它退回 Ubuntu rootfs)。已处理:`/opt/mu300/bin/mu300-update` 和 `/usr/local/bin/mu300-update` 改名为 `.disabled`,`mu300-update-notice.timer` 已 disable。控制面板的更新接口在二进制缺失时返回 unsupported;`mu300-accounts.service` 只在标记文件存在时才调用它(正常不存在)。

- 没有 SIM,modem 和移动数据未测;Wi-Fi 热点、蓝牙、GPU 也没有逐项验证。

## 五、Wi-Fi 客户端的 sid bug 与补丁

连路由器时 `wifi-client connect` 报 `could not build the wpa_supplicant configuration`。

**排查过程。**用户先看到 "the radio is an access point right now … cannot scan either"(正常提示),按提示 `connect` 之后报上面的错。`grep -n "could not build the wpa_supplicant" /opt/mu300/bin/wifi-client` 定位到第 832 行,它调用 `network_block()`(约第 733–755 行)。函数里 `h=$(printf '%s\n' "$2" | wpa_passphrase "$1" | sed … psk=<64位hex>)`,`h` 为空就 `return 1`。在设备上直接试 `printf '%s\n' testpass1234 | wpa_passphrase test`:没有任何输出。

**根因。**Debian sid 的 `wpasupplicant 2.11` 里,`wpa_passphrase` 从管道读密码时会对 stdin 调 `tcgetattr`,在非终端上失败且无输出,`network_block()` 拿不到 PSK 的哈希。Ubuntu 的旧版没有这个问题。

**补丁思路。**`wpa_passphrase` 成功就照旧用哈希;失败就退回 `psk="密码"`,让 `wpa_supplicant` 自己算 PBKDF2。密码长度要 8–63 位。配置文件是 0600 root;SAE 路径本来就写明文 `sae_password`,安全性等同。单元验证过 WPA2、WPA2/WPA3(SAE)、开放网络、短密码(返回失败)四种输出,都正确。限制:密码含非 ASCII 或双引号时可能有问题,没测。

**修复后的 `network_block()` 完整版本**(替换 `/opt/mu300/bin/wifi-client` 里同名函数,约第 733–760 行,其余不变):

```sh
# the supplicant's network block. The name goes in hex, so any byte (quotes, UTF-8) is taken as it is. The
# passphrase goes in as wpa_passphrase's hash, handed to it on stdin (an argument would be on its command line
# for ps), and its "#psk=" comment with the plain passphrase is left out. SAE cannot use the hash: with SAE it
# also goes in as sae_password, which is why the file is root's alone.
# Debian sid: wpa_passphrase 2.11 calls tcgetattr on stdin and prints nothing when piped, so h is empty there;
# fall back to a quoted passphrase, which wpa_supplicant hashes itself (8..63 characters, same 0600 root file).
network_block() {  # network_block SSID PASS SAE
    printf 'network={\n\tssid=%s\n' "$(hex "$1")"
    if [ -z "$2" ]; then
        printf '\tkey_mgmt=NONE\n'
    else
        h=$(printf '%s\n' "$2" | wpa_passphrase "$1" 2>/dev/null | sed -n 's/^[[:space:]]*psk=\([0-9a-fA-F]\{64\}\)$/\1/p')
        if [ -n "$h" ]; then
            printf '\tpsk=%s\n' "$h"
        else  # wpa_passphrase failed (sid)
            [ "${#2}" -ge 8 ] && [ "${#2}" -le 63 ] || return 1
            printf '\tpsk="%s"\n' "$2"
        fi
        if [ "$3" = 1 ]; then
            # WPA2, WPA2/WPA3 and WPA3-only networks alike; WPA3 requires management frame protection
            printf '\tkey_mgmt=WPA-PSK SAE\n\tieee80211w=1\n\tsae_password=%s\n' "$(hex "$2")"
        else
            printf '\tkey_mgmt=WPA-PSK\n'
        fi
    fi
    printf '}\n'
}
```

与原版的差别只有这一处:

```diff
-        [ -n "$h" ] || return 1
-        printf '\tpsk=%s\n' "$h"
+        if [ -n "$h" ]; then
+            printf '\tpsk=%s\n' "$h"
+        else  # wpa_passphrase failed (sid)
+            [ "${#2}" -ge 8 ] && [ "${#2}" -le 63 ] || return 1
+            printf '\tpsk="%s"\n' "$2"
+        fi
```

**应用:**在设备上,root:

```sh
f=/opt/mu300/bin/wifi-client
cp -p $f $f.orig                       # 备份
# 方式一:adb push 补丁脚本后 sh 执行 F:\Projects\tmp\f50\tools\wifi-client.patch.sh(幂等,打过会提示 already patched)
# 方式二:手动编辑上面 diff 对应的两行
sh -n $f && echo SYNTAX_OK             # 语法检查
```

回退:`cp -p /opt/mu300/bin/wifi-client.orig /opt/mu300/bin/wifi-client`。

补丁脚本是按**行号**(第 742–743 行)用 awk 替换的,生成的文件里 `\t`、`\n` 会变成字面制表符和换行(在单引号里输出等价,语法正确,只是不好看);上面这份是手工整理的干净写法,内容等价。将来项目升级使行号变化的话,补丁脚本会改错行,应该改用手动方式。

**验证函数(不碰网络):**

```sh

sed -n "${s},${e}p" $f > /tmp/nb.sh

sh -c '. /tmp/nb.sh; network_block x abc 0; echo rc=$?'         # 期望 rc=1(密码太短)
```

**局域网 SSH 被挡的修复(同一个脚本的另一处)。**`rules_text` 生成 nft 事务,`fw_state` 把当前规则集和它逐条比对,多出任何一条就判为 `unknown`,于是 `fail_closed`。所以不能简单往 input 链里再加一条 accept。这次的做法是把 input 链整体拿掉,让 `rules_text` 只生成 forward 链;生成和比对用的是同一个函数,所以两边一致,`wifi-client status` 仍是 `shared with the LAN (internet only)`。具体改的是 `rules_text` 里从 `chain input` 到 input 链 `counter drop` 的几行 `printf`,开头改成直接 `table inet %s { chain forward {`。改完 `wifi-client reconnect` 生效。验证:电脑(10.17.1.x)`ssh wray@10.17.1.143` 通过。副作用:设备在 Wi-Fi 上没有任何入站过滤,必须靠 ufw。

### 1. 样本

### 3. HTTP 登录算法(zreq)

基址 `http://192.168.0.1:8080`;请求头 `User-Agent: Mozilla/5.0`、`Referer: http://<ip>:8080/index.html`、`Content-Type: application/x-www-form-urlencoded`、`Cookie: <登录后 Set-Cookie 的第一段>`。

- LD:`GET /goform/goform_get_cmd_process?isTest=false&cmd=LD&_=<毫秒>` → JSON 里的 `LD`。
- 登录:`H1 = SHA256(password).upper()`,`H2 = SHA256(H1 + LD).upper()`,`POST /goform/goform_set_cmd_process`,body `goformId=LOGIN&isTest=false&password=<H2>`,取 `Set-Cookie` 第一段作为 Cookie。默认密码在脚本里(`f50_wireless_adb.py` 的 `DEFAULT_PWD`)。
- 取版本信息:`GET …cmd=Language,cr_version,wa_inner_version&multi_data=1`;取 RD:`GET …cmd=RD`。
- AD:`H3 = SHA256(wa_inner_version + cr_version).upper()`,`AD = SHA256(H3 + RD).upper()`(注意是 RD,不是 U20 脚本里用的 JSESSIONID)。
- 最终 POST 的 body 由 Go 的 `url.Values.Encode()` 生成,即按 key 排序。

### 4. 网页后台里 USB_PORT_SETTING 到底干了什么

来自反编译 `/system/priv-app/ZteWebServer/ZteWebServer.apk`(进程 `com.zte.web`,监听 8080,`sharedUserId=android.uid.system`)。完整报告在 `F:\Projects\tmp\f50\zteweb\notes\`。

**`USB_PORT_SETTING` 只做一件事:写系统设置 `Settings.Global adb_enabled`(1 为开,0 为关,其它值按 0)。**它不写 `persist.sys.usb.config` / `sys.usb.config`,不调 `UsbManager`,不执行 shell,不发广播,不重启,哪怕没真正生效也回 success。状态查询 `cmd=usb_port_switch` 读的也是 `adb_enabled`,不是 USB 的真实状态。

真正起作用的是 system_server(证据来自同机 B09 备份里的 `services.jar`):

- `AdbService.setAdbEnabled()` **只有值真实变化才继续,同值直接 return**。真实变化时 `ctl.start adbd` / `ctl.stop adbd`,并回调 `UsbDeviceManager`。
- `UsbDeviceManager.setAdbEnabled()`:开 → `persist.sys.usb.config="adb"`;关 → `"charging"`;然后重配 `sys.usb.config`。
- 开机时 `AdbService.systemReady()` 反过来:读 `persist.sys.usb.config`,含 `adb` 就把 `adb_enabled` 设成 1,否则 0,**会覆盖上次网页写进 Settings 的值**。
- init 里:`on post-boot && property:sys.usb.config=none` → `setprop sys.usb.config ${persist.sys.usb.config}`;`on property:sys.usb.config=adb && property:sys.usb.configfs=1` → `start adbd`。
- SettingsProvider 对"写入相同值"也不通知观察者,所以重复写 1 是彻底的空操作。

`REBOOT_DEVICE` 先回 success,500ms 后 `PowerManager.reboot("manualreboot")`。`UsbTools`(开写 `rndis,diag,diag_mdm,adb`,关写 `rndis`,最后无条件重启)只被 `DEVELOPER_MODE_SETTING` / `SET_DEVICE_MODE` 调用,而本 APK 的 `DeveloperModule` 只注册了 `USB_PORT_SETTING`,这条路径在这个固件上不可达。网页 UI 是 `index.html#usb_port` → `js/adm/usb_port.js`,提交的就是 `goformId=USB_PORT_SETTING` + `usb_port_switch=1/0`,**需要点 Apply 才会发请求**,只点 radio 不发。APK 里没有任何写 `service.adb.tcp.port` / `persist.adb.tcp.port` 或启停 adbd 的代码;设备上的 `persist.adb.tcp.port=5555` 是 ROM 本来就带的持久属性。

### 5. "没有 adb 的时候怎么开出来"

- **有线 adb**:让 `adb_enabled` 发生一次真实的 0→1 变化。框架会立刻 `ctl.start adbd`、把 `persist.sys.usb.config` 写成 `adb`、重配 USB,代码上不需要重启;`REBOOT_DEVICE` 只是让重启后按 `persist=adb` 稳定地重新组装 USB,是最稳的做法。
- **为什么只在网页上点开关没用**:如果开关本来就是 1(UI 显示的是 `adb_enabled`,既不是 persist,也不是 adbd 的实际状态),再提交 1 就是同值,被两层短路成空操作;`persist.sys.usb.config` 没被写成 `adb`,重启时 `systemReady()` 按 persist 重算,又回到 0,于是仍然没有 adb,UI 却一直显示 ON。**原工具先发 0 再发 1,就是强制制造一次真实的 1→0→1 变化。**换成手动:网页上先关、点 Apply、再开、再点 Apply。
- 次要可能:点了 radio 没点 Apply;重启抢在异步写 persist 之前;特定 SIM 状态下 `ZTE_ADB_USB_SECURITY_RESTRICTION` 强制关 adb;adbd 或 USB 端点卡死需要重新枚举。
- **无线 adb 的 TCP 监听**:adbd 启动时读 `service.adb.tcp.port` / `persist.adb.tcp.port`;这台 ROM 带着 `persist.adb.tcp.port=5555`,所以 adbd 一启动就同时监听 TCP 5555。Samba 那一套在这个固件上既做不了(`smb.conf` 是 immutable),也不是必须的。

现场印证(设备在 Android 时,登录网页接口后查询):`usb_port_switch → '1'`、`developer_mode_enable → '1'`;设备上 `settings get global adb_enabled = 1`、`persist.sys.usb.config = adb`、`sys.usb.config = rndis,mtp,adb`、`init.svc.adbd = running`、`persist.adb.tcp.port = 5555`。两个诊断接口登录后不需要 adb 就能用:

- `GET /goform/goform_get_cmd_process?isTest=false&cmd=usb_port_switch` → `adb_enabled`
- `GET /goform/goform_get_cmd_process?isTest=false&cmd=developer_mode_enable` → `persist.sys.usb.config` 是否含 `adb`

如果前者是 1、后者是 0,就是上面"UI 显示 ON 但 persist 没有 adb"的分叉,先 0 再 1 即可。

风险:单独发 `usb_port_switch=0`(真实的 1→0)会把 `persist.sys.usb.config` 写成 `charging`;如果随后的 1 没成功,重启后 USB 只剩充电,RNDIS / ECM 和网页后台都可能不可达。**没有恢复手段时不要单独发 0**,原程序和我们脚本在第 1 步之后失败,留下的就是这种坏状态。框架侧的证据来自同机 B09 备份镜像,如果设备跑的不是这个固件,`services.jar` 的细节可能不同。

### 6. 替代脚本与真机测试(2026-10-27)

脚本 `F:\Projects\tmp\f50\re\f50_wireless_adb.py`(只用标准库;SMB 触发可选用 `impacket`,装在 `F:\Projects\tmp\f50\tools\venv`)。默认只打印计划,必须加 `--yes` 才执行;加了 `--yes` 后和原工具一样会重启,不想重启加 `--no-reboot`;`--login-only --yes` 只登录并算 AD,不改设备。

测试环境:设备在 Android(B09,Magisk root);电脑 Wi-Fi 连设备自己的热点 `FRayWrt`(电脑 192.168.0.50,设备 192.168.0.1)。起点是 USB adb 传输层卡住(`adb devices` 看不到设备,设备管理器里 ADB Interface 还在),正好是"没有 adb 时靠 HTTP 恢复"的场景。

| 阶段 | 结果 |
|---|---|
| 只读 `--login-only --yes` | 通过:登录、AD 都算出,逆向出的登录算法与真机一致 |
| `USB_PORT_SETTING=0` | 通过 |
| `USB_PORT_SETTING=1` | 第一次失败(脚本自己的 bug,见下),修复后通过 |
| `REBOOT_DEVICE` + `adb wait-for-device` | 通过:重启后 USB adb 自己回来了 |
| `sed -i` 改 `smb.conf` | 失败:`Operation not permitted`,`smb.conf` 带 immutable 属性(`lsattr` 为 `----i----E`),原程序在这个固件上同样做不了 |
| SMB Guest 触发 | 没有有效结果(第 5 步没写进去) |
| `adb connect 192.168.0.1:5555` | 失败:`10053` / `10060`;设备上 `[::]:5555` 在监听,`iptables filter INPUT` 默认 ACCEPT,但电脑从 Wi-Fi 进不去,原因没查清 |

脚本修过的东西:

1. Cookie 复用导致第二次登录失败:第 1 步登录后把旧 Cookie 带进第 2 步的登录请求,设备回 `{"result":0}` 且不发 `Set-Cookie`,报 `login: no Set-Cookie`。原程序每步都是新的 `zreq` 进程,登录时没有 Cookie。已改为每次 `login()` 先清 Cookie。这个问题会让设备停在 USB 调试关闭的状态,也是原程序同类副作用的来源。
2. 默认行为改回和原程序一致(`--yes` 就重启;之前默认跳过重启,会让 USB adb 出不来)。
3. SMB 触发增加 `impacket` 纯 Python 实现(Windows 默认拒绝 Guest SMB,也没有 `smbclient`)。
4. 第 5、6 步改成尽力而为:失败只警告,继续尝试 `adb connect`,以最终 adb 是否连上为准。

其它发现:

- 有线 adb 靠 HTTP 的 `USB_PORT_SETTING` 加重启就够。
- 重启后 `sys.usb.config` 从 `rndis,mtp,adb` 变成了 `ecm,mtp,adb`。Windows 没有 ECM 网卡驱动,所以电脑的 USB 网卡会消失,HTTP 通道必须走 Wi-Fi(连设备热点)才可靠。
- 设备 `iptables` 的 `INPUT` 只放行来源 `192.168.0.0/24` 的 8080,从 `adb forward` 的回环进来的 8080 会被丢。
- `persist.sys.usb.config` 试验前后都是 `adb`,脚本里的 `setprop persist.sys.usb.config adb,rndis` 在 shell 身份下没有生效。
- 同时存在 USB adb 和 `192.168.0.1:5555` 两个设备时,命令会报 `more than one device`,先 `adb disconnect`。
- 原程序每次先发 `usb_port_switch=0` 且失败不恢复,反复运行会把 `persist.sys.usb.config` 从 `adb,rndis` 改成 `adb` 并让 `192.168.0.1` 暂时不可达,所以别反复跑。

测完的复原:`/data/samba/etc/` 里 `sed` 失败留下的 12 个临时文件(`smb.conf` 加 6 位随机字符)和脚本建的 `smb.conf.bak.opener` 都已删除,`smb.conf` 的 MD5 前后一致(`cf419aec312cf4b6abaa849d67e31093`),immutable 属性没动。USB 调试开关最终是开的,`persist.adb.tcp.port=5555`、`persist.sys.usb.config=adb` 与测试前相同。Android 侧遗留一个无害的 `/data/local/tmp/bbdir/busybox`(切换 Linux 要用,别删)。

切回 Linux 时踩到的坑就是前面说的 Magisk busybox 问题。另外观察到:`dd` 出来的 `boot_b` 的 MD5(`9d7a4a10…`)与安装时推送的 `work/boot-linux-slotb.img`(`029289…`)不一致,但内容是 Linux 镜像(含 `mu300` 字符串,没有 Magisk,能正常启动),原因没查(可能是安装器写入前做了处理,或首次启动后被更新)。
