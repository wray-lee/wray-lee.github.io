In the currently widely used email sending protocol [SMTP](https://zh.wikipedia.org/zh-hans/%E7%AE%80%E5%8D%95%E9%82%AE%E4%BB%B6%E4%BC%A0%E8%BE%93%E5%8D%8F%E8%AE%AE), the sender can arbitrarily set the sender's email address, and anyone can impersonate *[boss@your-corp.com](mailto:&#x62;&#111;&#x73;&#115;&#x40;&#x79;&#111;&#117;&#114;&#x2d;&#99;&#x6f;&#114;&#x70;&#x2e;&#99;&#x6f;&#x6d;)* to send emails to others. Therefore, the SPF (Sender Policy Framework) mechanism was proposed to verify the email sender (Mail Transfer Agent, MTA); only servers recognized by *your-corp.com* can send emails with *[boss@your-corp.com](mailto:&#x62;&#x6f;&#115;&#115;&#64;&#121;&#111;&#x75;&#x72;&#45;&#x63;&#x6f;&#x72;&#x70;&#46;&#x63;&#x6f;&#x6d;)* as the sender. The email recipient uses SPF records and IP addresses to identify whether the sending server is legitimate, and according to the instructions in the SPF record decides whether to accept or reject the email.

## How to Deploy SPF

There was once a dedicated SPF resource record type in the DNS system, but it has been abolished. Nowadays, SPF exists in the form of TXT resource records, and the hostname is generally @. For example, this blog's SPF is as follows:

```bash
➞ dig chenxy.me txt +short
"v=spf1 include:spf.mail.qq.com ~all"
```

## Format of SPF Records

SPF records use a single space as the separator between multiple terms; each term consists of components such as qualifier, mechanism, and modifier. During parsing, matching proceeds from left to right; if any term matches successfully, the matching process is immediately stopped and the SPF verification result is returned according to the qualifier.

SPF records start with the fixed `v=spf1 `, indicating the SPF version, which is currently fixed as spf1.

### Qualifier and Mechanism

#### Qualifier

The qualifiers that exist in SPF are placed before the mechanism, and there are the following four types. Among them, + is the default qualifier and can be omitted.

| Qualifier | Result | Explanation (if the corresponding mechanism matches successfully) |
| --- | --- | --- |
| + | Pass | An explicit statement that the sender's machine has passed the check and can send email from this domain's mailbox |
| - | Fail | An explicit statement that the sender's machine has not passed the check and is not allowed to send email from this domain's mailbox |
| ~ | Soft Fail | A weaker statement that the sender's machine appears not to have passed the check |
| ? | Neutral | The administrator of this domain has not explicitly stated whether the sender's machine passes the check |

#### Mechanism

##### all

all will always match successfully; for this reason, mechanisms after all will not take effect. all is generally used as the last mechanism, together with a qualifier, to configure the "default behavior"—if all other policies fail to match, what this domain's policy is for these exceptions.

Take this site's SPF configuration `v=spf1 include:spf.mail.qq.com ~all` as an example: if the include mechanism fails to match, then it eventually reaches all and matches successfully, and according to its qualifier returns a "soft fail" result—generally the email recipient will not reject this email, but will put it into the spam folder.

##### include

The format of include is `include: *domain-spec*`; it will trigger a recursive SPF verification process, causing the email recipient to check the SPF record set by *domain-spec*. Only when the verification result of *domain-spec* is pass (note: soft fail also does not work) will this mechanism be considered a successful match.

The include mechanism is expected to handle "cross-administrative-boundary" situations, that is, when the required SPF rules are placed under a domain not under this domain's jurisdiction. It is more like "importing a third-party dependency library", while redirect, mentioned below, is more like "a piece of shared code within a company".

##### exists

The format is `exists: *domain-spec*`; the recipient will send an A record query to the specified domain (even for IPv6, an A record query is used). If there is any response, the match succeeds. It can be used for some relatively complex verification.

Here, *domain-spec* can include the following macros:

| Macro | Meaning | Example |
| --- | --- | --- |
| s | Sender's email address | &#x68;&#x73;&#x69;&#x97;&#x111;&#x78;&#x121;&#x99;&#x104;&#x65;&#x110;&#x40;&#x65;&#x78;&#x61;&#x109;&#x70;&#x6c;&#x65;&#x46;&#x63;&#x6f;&#x6d; |
| l | Sender's "local part" | hsiaoxychen |
| o | Sender's domain part | example.com |
| d | The SPF authoritative domain currently being verified. Usually the same as above, but may change when resolving include | example.com |
| i | Sender's IP | 114.5.1.4 |
| v | If IPv4, then in-addr; if IPv6, then ip6 | in-addr |
| h | Domain of HELO&#x2F;EHLO | mail.example.com |

Also, if r is appended after a macro, the value can be reversed. For example, suppose we have the following SPF record:

```log
v=spf1 exists:%{ir}.%{l}._spf.example.com -all
```

Also, under the _spf.example.com subdomain there is only one A record:

```log
4.1.5.114.noreply._spf.example.com IN A 127.0.0.1
```

Then only emails sent from `114.5.1.4` and originating from `noreply@example.com` can pass SPF verification.

##### Other Mechanisms

Other mechanisms include: a, mx, ip4, ip6, exists. Their mechanisms are all relatively similar and fairly easy to understand, summarized as follows:

| a | If the sender IP matches any A record (or AAAA record, depending on whether this sending goes over IPv4 or IPv6) IP address of the specified domain, the match succeeds |
| --- | --- |
| mx | If the sender IP matches any MX record of the specified domain, the match succeeds |
| ip4 | If the sender IP matches the specified IPv4 address (range), the match succeeds |
| ip6 | If the sender IP matches the specified IPv6 address (range), the match succeeds |

### Modifier

The syntax of a modifier is slightly different from that of a mechanism: it has no qualifier, and its key-value separation is not `:` but `=`. There are currently two modifiers, namely redirect and exp. exp is used to tell the server how to generate explanatory text after SPF verification fails, and is not introduced here; redirect can "redirect" the subsequent SPF verification process to the target domain. For example, gmail.com's SPF record:

```bash
➞  dig gmail.com txt +short
"globalsign-smime-dv=CDYX+XFHUw2wml6/Gb8+59BsH31KzUr6c1l2BPvqKX8="
"v=spf1 redirect=_spf.google.com"

➞  dig _spf.google.com txt +short
"v=spf1 include:_netblocks.google.com include:_netblocks2.google.com include:_netblocks3.google.com ~all"
```

Although it is under a different domain, the SPF policy of _spf.google.com can represent gmail.com.

Note that redirect must appear as the last part of the SPF record, and when all is present, redirect must be ignored.

## SPF Record Example Analysis

```bash
➞  dig chenxy.me txt +short
"v=spf1 include:spf.mail.qq.com ~all"
# 检查 spf.mail.qq.com 的匹配结果，如果匹配失败，则返回 soft fail

➞  dig spf.mail.qq.com txt +short
"v=spf1 include:spf-a.mail.qq.com include:spf-b.mail.qq.com include:spf-c.mail.qq.com include:spf-d.mail.qq.com include:spf-e.mail.qq.com include:spf-f.mail.qq.com include:spf-g.mail.qq.com -all"
# 依次检查各个 include 的匹配结果，如果都匹配失败，则返回 fail

➞  dig spf-a.mail.qq.com txt +short
"v=spf1 ip4:203.205.251.0/24 ip4:103.7.29.0/24 ip4:59.36.129.0/24 ip4:113.108.23.0/24 ip4:113.108.11.0/24 ip4:119.147.193.0/24 ip4:119.147.194.0/24 ip4:59.78.209.0/24 ip4:113.96.223.0/24 ip4:183.3.226.0/24 ip4:183.3.255.0/24 ip4:59.36.132.0/24 -all"
# 如果发件方不在这些 ip 段之中则返回 fail
```

It seems that SPF records in practical use almost never use mechanisms such as exists and exp; most simply define legitimate IP ranges.

Another relatively typical way to write an SPF record is:

```log
v=spf1 a mx ip4:114.5.1.4 -all
```

This means "only the IPs in this domain's a and mx records, as well as 114.5.1.4, can send email on behalf of this domain", commonly seen in self-built private mail servers.
