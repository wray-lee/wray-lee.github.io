### D Enable adb [effect verified; mechanism **[To be added]**]
- **Important finding: after flashing B09 or doing a factory reset from shrinking userdata, adb is still available**: this ROM comes with UFI-TOOLS (`com.minikano.f50_sms`) and Magisk stub, and `persist.sys.usb.config=adb` and `persist.adb.tcp.port=5555` are saved in the persist partition, so they are not lost on factory reset. Only the first time (when B08 had just been flashed to B09) was it necessary to enable it with the temporary wireless adb tool.
- Temporary wireless adb tool (static reverse engineering completed, **see Appendix A for details**). **Correction**: I earlier wrote that it "uses serial AT"; that was wrong—it **has no serial logic at all**. The real flow has 6 steps: ① HTTP `USB_PORT_SETTING&usb_port_switch=0` (turn off first) → ② `=1` (turn on again) → ③ `REBOOT_DEVICE` (reboot) → ④ `adb wait-for-device` → ⑤ `adb shell` changes `setprop` and writes `preexec = start adbd`, `guest ok = yes`, etc. to `/data/samba/etc/smb.conf` → ⑥ connect to SMB (445) with Guest and an empty password to trigger `start adbd`; finally `adb connect 192.168.0.1`. HTTP login: `H1=SHA256(pwd)`, `H2=SHA256(H1+LD)`, AD=`SHA256(SHA256(wa_inner_version+cr_version)+RD)`, port **8080**. "Cannot operate port" is actually because the step 1 HTTP response has no `result`, not a serial error.
- So the reason "the web switch alone is not enough": the wireless adb switch is Samba's `preexec = start adbd`, and someone (Guest) must connect to SMB once for adbd to start; after a reboot, if nobody connects, there is no listener [Inferred].
- Alternative script: `F:\Projects\tmp\f50\re\f50_wireless_adb.py`. **Tested on a real device (2026-10-27, see Appendix A §A9)**: HTTP login, `USB_PORT_SETTING` 0→1, `REBOOT_DEVICE`, waiting for USB adb to come back—this whole part **passed verification**; the Samba part is unavailable on this firmware (`smb.conf` is immutable); the `adb connect` wireless part **did not work** this time. For risks see Appendix A §A6.
- **Correction to the earlier statement**: Samba's `preexec = start adbd` is not the key to enabling adb on this firmware. What actually makes adb appear is the HTTP in the first three steps (`USB_PORT_SETTING` first 0 then 1, then `REBOOT_DEVICE`), which has been measured; the TCP 5555 listener comes from `persist.adb.tcp.port=5555`.
- **The program has destructive side effects**: it first sends `usb_port_switch=0` every time and does not restore on failure; repeated runs change `persist.sys.usb.config` from `adb,rndis` to `adb` and make `192.168.0.1` temporarily unreachable. When both USB adb and `192.168.0.1:5555` devices are present, it reports `more than one device`; first `adb disconnect`.
- Firmware adbd **does not verify keys**: even if `ro.adb.secure=1` but `/data/misc/adb/adb_keys` does not exist, it can still connect; pairing is not needed.

## 10. Pitfall list

1. spd_dump exit codes are not trustworthy; look at `Write Part Done`.
2. Direct connection to `--kickto 2` is unavailable on this device; use the short-pin mode command.
3. After getting root, before `su` is in PATH use `/debug_ramdisk/su`; in Git Bash set `MSYS_NO_PATHCONV=1`.
4. The temporary wireless adb tool has destructive side effects; do not run it repeatedly.
5. PowerShell module path (`Get-FileHash`); GNU tar parses `F:\`; installer self-update swallows output.
6. When an answers variable is missing, the installer aborts and writes nothing; add the variable according to the error.
7. A custom package cannot use the shrink transaction's resume installation; use `-NoResume` + `OVERWRITE=overwrite`.
8. Process memory dumps include current environment variables (including tokens); shred immediately after use; **in this session this token has entered the conversation record; rotation is recommended**.
9. Flashing the ROM overwrites device partitions such as ztepersist/splloader; always have a B08 original backup first.
10. Unescaped `$(...)` in a heredoc is expanded on the computer side; set the device password with a separate command.
11. Repeatedly running updaters like mu300-update on the device will destroy the self-built Debian; they have been renamed and disabled.
12. Using memory dumps/reading process memory to "see serial commands" is the wrong method: strings are obfuscated, and `\\.\COM%u` comes from the Go standard library; the conclusion I drew from it that it "uses serial" was wrong. Use real static unpacking (packer = LZMA).
13. When I read `hotspot.conf`, the filter rule did not match the `PSK=` line, and the hotspot password entered the conversation record in plaintext; `COUNTRY=TR` is the project default; in Japan it should be `JP` [not changed].

### 11.1 Complete patched version

**Patched `network_block()` (replaces the function of the same name in `/opt/mu300/bin/wifi-client`, around lines 733–760; the rest is unchanged)**:

```
```sh
# the supplicant's network block. The name goes in hex, so any byte (quotes, UTF-8) is taken as it is. The
# passphrase goes in as wpa_passphrase's hash, handed to it on stdin (an argument would be on its command line
# for ps), and its "#psk=" comment with the plain passphrase is left out. SAE cannot use the hash: with SAE it
# also goes in as sae_password, which is why the file is root's alone.
# Debian sid: wpa_passphrase 2.11 calls tcgetattr on stdin and prints nothing when piped, so h is empty there;
# fall back to a quoted passphrase, which wpa_supplicant hashes itself (8..63 characters, same 0600 root file).
network_block() {  # network_block SSID PASS SAE
    printf 'network={\n\tssid=%s\n' "$(hex "$1")"
    if [ -z "$2" ]; then
        printf '\tkey_mgmt=NONE\n'
    else
        h=$(printf '%s\n' "$2" | wpa_passphrase "$1" 2>/dev/null | sed -n 's/^[[:space:]]*psk=\([0-9a-fA-F]\{64\}\)$/\1/p')
        if [ -n "$h" ]; then
            printf '\tpsk=%s\n' "$h"
        else  # wpa_passphrase failed (sid)
            [ "${#2}" -ge 8 ] && [ "${#2}" -le 63 ] || return 1
            printf '\tpsk="%s"\n' "$2"
        fi

### A3. HTTP login algorithm (`zreq`) [Verified]

- Base URL `http://192.168.0.1:8080`; request headers `User-Agent: Mozilla/5.0`, `Referer: http://<ip>:8080/index.html`, `Content-Type: application/x-www-form-urlencoded`, `Cookie: <登录后 Set-Cookie 第一段>`. The `Host` header source writes `<ip>`; what Go actually sends is very likely `<ip>:8080` [Unconfirmed].
- LD: `GET /goform/goform_get_cmd_process?isTest=false&cmd=LD&_=<毫秒>` → JSON `LD`.
- Login:
  - `H1 = SHA256(password).upper()`
  - `H2 = SHA256(H1 + LD).upper()`
  - `POST /goform/goform_set_cmd_process` body `goformId=LOGIN&isTest=false&password=<H2>`, take the first segment of `Set-Cookie` as the Cookie.
- Get UFI info: `GET …cmd=Language,cr_version,wa_inner_version&multi_data=1` → `wa_inner_version`, `cr_version`; get RD: `GET …cmd=RD`.
- AD: `H3 = SHA256(wa_inner_version + cr_version).upper()`, `AD = SHA256(H3 + RD).upper()` (note it is **RD**, not the JSESSIONID in the U20 script).
- The final POST body is generated by `url.Values.Encode()` (key lexicographic order), e.g. `AD=<AD>&goformId=USB_PORT_SETTING&isTest=false&usb_port_switch=0`.
- The password is a 14-byte generic administrator login string built into the tool; `zreq` does SHA-256 on the **literal 14 bytes** and does not base64-decode. **This document does not record that string**; if needed, see `F:\Projects\tmp\f50\re\f50_wireless_adb.py`.
- The U20 PowerShell script (`O:\F50\kkfile\bin\u20_openadb.ps1`) uses a different algorithm (`192.168.88.1`, port 80, JSESSIONID); **do not mix them**.

## Appendix B: What `USB_PORT_SETTING` actually does on the device (decompiled web backend APK)

Source: `/system/priv-app/ZteWebServer/ZteWebServer.apk` (process `com.zte.web`, listening on 8080, `sharedUserId=android.uid.system`). ### B1. Core conclusion
**`USB_PORT_SETTING` does only one thing: write the system setting `Settings.Global adb_enabled` (1 = on, 0 = off, other values treated as 0).** It does not write `persist.sys.usb.config`/`sys.usb.config`, does not call `UsbManager`, does not execute shell, does not send broadcasts, and does not reboot. The status query `cmd=usb_port_switch` also reads `adb_enabled`, **not the real USB state**.

### B2. What actually takes effect is system_server [Code evidence, from services.jar of B09 on the same device]
- `AdbService.setAdbEnabled()`: **continues only when the value actually changes; the same value returns directly**. On a real change, `ctl.start adbd`/`ctl.stop adbd`, and calls back `UsbDeviceManager`.
- `UsbDeviceManager.setAdbEnabled()`: on → `persist.sys.usb.config="adb"`; off → `"charging"`; then reconfigure `sys.usb.config`.
- At boot, `AdbService.systemReady()` does the reverse: reads `persist.sys.usb.config`; if it contains `adb` → `adb_enabled=1`, otherwise `0`—**it overwrites the value last written to Settings by the web page**.
- init: `on post-boot && property:sys.usb.config=none` → `setprop sys.usb.config ${persist.sys.usb.config}`; `on property:sys.usb.config=adb && property:sys.usb.configfs=1` → `start adbd`.
- SettingsProvider also does not notify observers for "writing the same value". So **repeatedly writing 1 is a complete no-op**.

### B3. Other
- `REBOOT_DEVICE`: returns success first, then `PowerManager.reboot("manualreboot")` after 500 ms. [Code evidence]
- `UsbTools` (`USB_PROPERTY_KEY=persist.sys.usb.config`, `USB_PROPERTY_KEY_TMP=sys.usb.config`, writes `rndis,diag,diag_mdm,adb` on enable and `rndis` on disable, then unconditionally reboots) is only called by `DEVELOPER_MODE_SETTING`/`SET_DEVICE_MODE`, while this APK's `DeveloperModule` only registers `USB_PORT_SETTING`, so this path is **unreachable** on this firmware. [Code evidence + inference]
- Web UI: `index.html#usb_port` → `js/adm/usb_port.js` → `setUsbPortSwitch()`; what is submitted is `goformId=USB_PORT_SETTING` + `usb_port_switch=1/0`; **you must click Apply to send the request**; clicking only the radio does not send. The page label is "USB Port / USB port"; it controls `adb_enabled`.
- The APK has **no** code that writes `service.adb.tcp.port`/`persist.adb.tcp.port` or starts/stops adbd; `persist.adb.tcp.port=5555` on the device is a persistent property already present in the ROM.

### B4. Final answer to "how to enable it when there is no adb"
- **Wired adb**: cause `adb_enabled` to undergo **one real 0→1 change**. The framework immediately `ctl.start adbd`, writes `persist.sys.usb.config` as `adb`, and reconfigures USB; **code-wise no reboot is needed**; `REBOOT_DEVICE` only makes the USB reliably reassemble according to `persist=adb` after reboot, which is the most stable approach.
- **Why clicking the switch only on the web page does not work (your experience)**: if the switch is already 1 (the UI shows `adb_enabled`, not persist and not adbd's actual state), submitting 1 again is the same value and is short-circuited by two layers into a no-op; `persist.sys.usb.config` is not written as `adb`, and at reboot `systemReady()` recalculates according to persist and goes back to 0 → still no adb, while the UI can keep showing ON. **The tool sends 0 first and then 1, which forces one real 1→0→1 change.** In other words: on the web page you must **turn it off first, click Apply, then turn it on, then click Apply again**.
- Secondary possibilities: clicked the radio but not Apply; reboot raced ahead of the asynchronous persist write; `ZTE_ADB_USB_SECURITY_RESTRICTION` under a specific SIM state forcibly disables adb; adbd/USB endpoint hung and needs re-enumeration.
- **Wireless adb TCP listener**: adbd reads `service.adb.tcp.port`/`persist.adb.tcp.port` at startup; this device's ROM already has `persist.adb.tcp.port=5555`, so adbd listens on TCP 5555 as soon as it starts. **The Samba approach can neither be done on this firmware (`smb.conf` immutable) nor is it necessary**. However, this time connecting to `192.168.0.1:5555` from the computer Wi-Fi still timed out; the reason is not investigated (A9).

### B5. On-site confirmation (2026-10-27, device on Android)
After logging in and making read-only queries through the web interface: `usb_port_switch → '1'`, `developer_mode_enable → '1'`; on the device `settings get global adb_enabled = 1`, `persist.sys.usb.config = adb`, `sys.usb.config = rndis,mtp,adb`, `init.svc.adbd = running`, `persist.adb.tcp.port = 5555`. Consistent with the model. Two diagnostic interfaces can be used without adb (after login):
- `GET /goform/goform_get_cmd_process?isTest=false&cmd=usb_port_switch` → `adb_enabled`
- `GET /goform/goform_get_cmd_process?isTest=false&cmd=developer_mode_enable` → whether `persist.sys.usb.config` contains `adb`
If the former is 1 and the latter is 0, it is the branch described above where "the UI shows ON but persist has no adb"; in that case just send 0 then 1.

### B6. Risks
- Sending `usb_port_switch=0` alone (a real 1→0) writes `persist.sys.usb.config` as `charging`; if the following 1 does not succeed, after reboot USB will only charge, and RNDIS/ECM and the web backend may both be unreachable. **Do not send 0 alone when you have no recovery method**—this is exactly the bad state left after the original program and our script fail after step 1.
- The agent's framework-side evidence comes from the B09 backup image of the same device; if the device is not running this firmware, the `services.jar` details may differ (the APK side is unaffected).

### B7. Corrections to the preceding content
- The statement in Appendix A that "Samba's `preexec = start adbd` is the key to enabling wireless adb" and the corresponding inference in §3-D are **downgraded to: the original program's approach is not necessary on this firmware**; what is decisive is a real 0→1 change of `adb_enabled`.
- The statement in the A2 table that "`usb_port_switch=1` makes USB add the ADB interface" is inaccurate: it sets `adb_enabled`; the USB interface is reconfigured by system_server in response to the change.
