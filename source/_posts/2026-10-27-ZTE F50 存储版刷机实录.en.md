# Notes on Installing Debian on ZTE F50 (MU300)

On 2026-10-26–27, I flashed a ZTE F50 storage version from B08 to B09, rooted it, shrank userdata, then installed Debian unstable (kernel 7.3), making it an Android + Debian dual-boot system. The first part covers daily usage; the latter part covers how it was installed, the pitfalls encountered, and reverse-engineering results.

## 1. Read This First: Daily Usage

### Current State of the Device

ZTE F50 / MU300 storage version, Unisoc UMS9620, eMMC 234 GiB, no power button, no screen.

- Android is B09 firmware (`F50_FLYMODEM_ZYV1.0.0B09`), rooted (Magisk 28.1, Shell authorized), installed in slot a, with userdata shrunk to about 30 GiB.
- Linux is Debian forky/sid, kernel 7.3.0, installed in slot b and the 198 GiB area after userdata (ext4, about 191G usable). It boots Linux by default and falls back to Android only after 5 consecutive boot failures.
- The bootloader shows locked; the patched trustos has been flashed, and Linux can still boot in the locked state.
- Linux has only one user, `wray` (sudo, docker group, zsh + oh-my-zsh + powerlevel10k). The `ubuntu` user created by the installer has been deleted. root is locked (`PermitRootLogin no`); to get root, use `sudo -i` or `adb shell`.
- Installed docker 28.5, ufw, neovim, fzf, zoxide, lsd, duf, fastfetch, git, curl, etc. Time zone `Asia/Tokyo`.
- No SIM, so no cellular network. Internet access is via Wi-Fi (connected to the home router RayWrt, device IP 10.17.1.143), or using the computer as a proxy.
- wray's password is in `F:\Projects\tmp\f50\wray-credentials.txt` (plaintext; handle it yourself after use). The installation password in `answers-install.txt` has been erased.

### Connecting to the Device

| Method | Command | Description |
|---|---|---|
| Wi-Fi | `ssh wray@10.17.1.143` | Use when the device is connected to the router; the IP is whatever the router assigns |
| USB network | `ssh wray@192.168.77.1` | USB cable directly connected to the computer, NCM NIC, driver-free on Windows 11; the computer gets 192.168.77.111 |
| USB adb | `adb shell` | Directly a root shell |

SSH only accepts keys (the 3 keys in Windows' `~/.ssh/authorized_keys`: Wray-Arch ed25519, Wray-Win rsa, phone u0_a355). adb in Linux also only accepts keys from `/etc/mu300/adb_keys` (`adb_auth=keys`), and is not open to all computers. The `ssh ubuntu@192.168.77.1` shown at the end of the installer is fixed text; actually use `wray@`.

When using adb in Git Bash with paths like `/data/...`, run `export MSYS_NO_PATHCONV=1` first; otherwise the path will be rewritten as a Windows path.

### Switching Systems: A Pitfall You Must Remember

Running `mu300-linux` from Android to enter Linux is only a "one-time trial boot"; at this point `/etc/mu300/default-boot` is still `android`. Reboot directly in Linux with `reboot` and it returns to Android, which looks like "automatic fallback after reboot" but is actually by design. To make Linux the permanent default, run `sudo mu300-next-boot linux` once after entering it. This is now set (the content of `default-boot` is `linux`).

Instance on 2026-10-27: the boot log contains `mu300-next-boot: default boot is not linux, nothing to do`; the previous kernel log is in pstore and was a normal `Restarting system`, not a crash.

In Linux:

```sh
sudo mu300-next-boot status      # 默认启动是谁、已经连续失败几次
sudo mu300-next-boot linux       # 默认进 Linux(每次成功启动后自动重新武装)
sudo mu300-next-boot android     # 之后重启进 Android
sudo mu300-next-boot attempts 5  # 连续失败几次后退回 Android(1-6,现为 5)
sudo mu300-next-boot lock        # 钉死在 Linux,失败也不回 Android
sudo mu300-next-boot unlock
sudo mu300-os <系统>             # 多个 Linux 系统之间选,目前只有一个(就是这个 Debian)
sudo reboot
```

In Android (adb, root):

```sh
adb shell
su
MU300_BUSYBOX=/data/local/tmp/bbdir/busybox mu300-linux status    # 看两个 slot,不改动
MU300_BUSYBOX=/data/local/tmp/bbdir/busybox mu300-linux --dry-run # 只显示要写的 32 字节
MU300_BUSYBOX=/data/local/tmp/bbdir/busybox mu300-linux           # 武装一次性试启动并重启进 Linux
```

You must include `MU300_BUSYBOX`, because the busybox bundled with Magisk is broken on this device (`--list` is empty, `readlink -f` returns empty). Without it, it reports `misc resolves outside /dev/block ()`, and `status` will also incorrectly determine that "boot_b is an Android image and Linux is not installed." That is a misjudgment; Linux is not lost. Use the busybox from the installation package, and the filename must be exactly `busybox` (a multi-call binary looks up applets by argv[0]; changing the name causes `applet not found`):

```sh
adb push <包目录>\mu300\busybox /data/local/tmp/bbdir/busybox
adb shell chmod 755 /data/local/tmp/bbdir/busybox
```

After switching, `status` should show `boot_b: the Linux boot image`. When checking slot status, the output looks like `slot a priority 15, tries 1, successful 1`, `slot b priority 14, tries 1, successful 0`.

Fallback when there is no computer: cut power 5 times in a row during Linux boot, and it automatically returns to Android.

### Wi-Fi: Connecting the Device to a Router

The SC2355 radio can only do one thing at a time: act as a hotspot (AP) or as a client (station). After connecting to a router, the device's own hotspot `FRayWrt` turns off. Switching from hotspot to client requires a reboot; switching from client back to hotspot does not. Only WPA2 and WPA2/WPA3 mixed mode are supported; pure WPA3 and Wi-Fi 7 networks are rejected. USB's 192.168.77.1 is unaffected.

```sh
sudo wifi-client scan-mode on && sudo reboot   # 想扫描时:下次开机保持客户端模式
sudo wifi-client scan
sudo wifi-client connect "SSID"                # 交互输密码,不回显;SSID 已知时不用 scan
sudo reboot                                    # 重启后才真正加入
wifi-client status                             # 连接、地址、防火墙状态
sudo wifi-client reconnect                     # 改了配置或防火墙后重新应用
sudo wifi-client disconnect
sudo wifi-client forget
```

If the radio is still in hotspot mode at this point, `scan` / `connect` will report "the radio is an access point right now … cannot turn it back into a client without a reboot". This is not a fault; `connect` will save the network first and join after reboot. Enter the password interactively or with `--password-file`; do not put it on the command line (it will go into the journal and `ps`). The configuration is stored in `/etc/mu300/wifi-client.conf` (0600, root); its content is SSID, PSK, `ENABLE=1`, `METRIC=50`. After connecting, Wi-Fi uplink takes precedence over mobile data and can theoretically be shared to USB clients via NAT (not tested).

This device is already connected to the home router and joins automatically at boot (service `mu300-wifi-client.service` runs `wifi-client up`).

### Giving the Device Temporary Internet Access (When There Is No Wi-Fi/SIM)

Right after installation the device had no Internet and the clock was wrong; the approach was to use the computer as a proxy:

```sh
bash /f/Projects/tmp/f50/tools/device-online.sh on    # 电脑起代理(127.0.0.1:7890) + adb reverse,设备的 apt/docker 走代理
bash /f/Projects/tmp/f50/tools/device-online.sh off   # 用完关,会删掉设备上的代理配置
```

If the clock is wrong, sync the time first (`date -u -s @<时间戳>`); otherwise TLS will fail. The device can now access the Internet directly via Wi-Fi, so this step is generally unnecessary.

### Firewall

Inbound rules are now managed by ufw: deny inbound by default, allow outbound, deny forwarding, and only allow 22 (tcp/udp, including IPv6).

```sh
sudo ufw status verbose
sudo ufw allow 22/tcp
sudo ufw allow from 10.17.1.0/24 to any port 8080 proto tcp   # 例:只对局域网开某个端口
sudo ufw delete allow 22/udp
```

`wifi-client` ships with an nft table `inet mu300_wifi_filter`. Its original input chain dropped all inbound traffic on wlan0 except established connections, DHCP replies, and rate-limited ping, so the LAN could ping the device but could not SSH in (sshd itself listening on `*:22` was fine). This input chain has now been removed, leaving only the forward chain (which prohibits forwarding to the intranet when sharing the uplink). `wifi-client status` should normally show `shared with the LAN (internet only)`; if it shows `mu300_wifi_filter is not as wifi-client puts it`, the rules are inconsistent with what the script generates.

The patch script is `F:\Projects\tmp\f50\tools\wifi-client.noinput.sh`, and the original file is backed up as `/opt/mu300/bin/wifi-client.orig2`. The patch modifies an installed file; system upgrades or reinstalls will overwrite it, and it will need to be reapplied. The project's own `mu300_filter` (`/etc/mu300/firewall.nft`) only handles the cellular interface, docker0, and br-*, and does not affect wlan0.

### Daily Maintenance

```sh
sudo apt update && sudo apt full-upgrade     # Debian 更新只用 apt
systemctl --failed
sudo systemctl reset-failed                  # 首次启动残留的 degraded 标记
sudo journalctl -b -p warning --no-pager | tail -50
df -h /; free -h
docker ps; docker run --rm hello-world
systemctl status mu300-adbd                  # Linux 自己的 USB adb
sudo mu300-usb adb off                       # 关 Linux 的 USB adb
sudo mu300-usb adb auth keys                 # 只认 adb_keys 里的密钥(现状)
```

adb in Linux and adb in Android are two separate things. The adbd on the Linux side is a static aarch64 program included in the image (`/opt/mu300/bin/adbd`), started at boot by `mu300-adbd.service`, which adds itself to the USB gadget (FunctionFS); it has nothing to do with the HTTP switch or Samba trigger in Android. Each time an adb connection ends, the gadget unbinds, and the script rebinds it, so it looks like a plug/unplug on the computer.

### What to Do If Something Goes Wrong

**Cannot connect via SSH.** Ping first. If ping works but SSH does not, check `sudo ufw status` and `wifi-client status`. If ping does not work, first check whether the device has returned to Android (Android has no port 22).

**Linux will not boot / want to see the previous log.** The device retries by itself and returns to Android after 5 consecutive failures. In Android, you can mount the Linux root partition read-only to view the journal. The area offset was calculated during installation (38700843008); the root filesystem is in the `ubuntu/` directory under the mount point:

```sh
# Android root shell
MU300_OFF=38700843008 MU300_RO=recover sh /data/local/tmp/android-mount-mu300root.sh /data/local/tmp/mu300root
ls /data/local/tmp/mu300root/ubuntu/var/log/journal
sh /data/local/tmp/android-mount-mu300root.sh -u /data/local/tmp/mu300root    # 看完卸载
```

The journal is in binary format; copy it to a computer (or WSL) and read it with `journalctl --file=<文件>`. The kernel log from the last crash is in Android's `/sys/fs/pstore/console-ramoops-0`. Note that omitting `MU300_OFF` causes `NO-EXT4 magic=0000`, because the default offset is not this device's area.

**Android has no adb.** After flashing B09 or a factory reset, adb is still available because `persist.sys.usb.config=adb` and `persist.adb.tcp.port=5555` are stored in the persist partition. If it really is gone, see the later section "How Wireless adb Is Enabled" and use `F:\Projects\tmp\f50\re\f50_wireless_adb.py`.

**Completely bricked.** Short the test point to enter download mode and flash back using the original B08 backup.

### Pitfalls to Avoid (Quick Reference)

1. `mu300-update` has been renamed to `.disabled`. Its `apply` will replace the entire system with Ubuntu 24.04, destroying the self-built Debian. Do not repeatedly run this kind of updater; use apt to update Debian.
2. The control panel and `mu300-os` treat this system as Ubuntu 26.04, with the version number displayed as empty; this is normal.
3. Entering Linux from Android is only one-time; see above.
4. Debian sid's `wpa_passphrase` has a bug; the original `wifi-client connect` reports `could not build the wpa_supplicant configuration`, and it has been patched (full code later).
5. The device has no python3 or openssl; write scripts with sh / awk / sed.
6. sid is a rolling release; think before `full-upgrade`, because if something goes wrong there is no official image to roll back to.
7. The hotspot country code `COUNTRY=TR` is the project default; in Japan it should be changed to `JP` and **has not been changed yet**.
8. Repeatedly running the "temporary wireless adb tool" is destructive; do not do that (see below).

## 3. How It Was Installed

### 1. Entering Download Mode (The Biggest Pitfall on This Device)

Directly connecting `--kickto 2` always fails on this device: the log shows `kick reboot timeout`, but spd_dump's exit code is 0, and there is also `pause` at the end of the bat file. It looks like a normal finish, but not a single byte was actually written. The earlier "flashed B09 but it is still B08" was very likely this.

What works is the "short-circuit mode" command, without `--kickto`, manually loading FDL1 and FDL2:

```
spd_dump.exe --wait 300 exec_addr 0x65012f48 fdl <fdl1-dl.bin> 0x65000800 fdl <fdl2-dl.bin> 0xb4fffe00 exec path <目录> <操作...> reset
```

The procedure is: unplug the cable → short the test point → keep it shorted and plug in the cable (it does not matter whether the command is started first or is already connected). A single occurrence of `usb_send failed (0 / 1)` means unstable contact; start over. **Whether it succeeds depends only on `Write Part Done` in the log, not on the exit code.**

### 2. Flashing B09 (Erasing userdata)

Before any flashing, first confirm you have the original B08 backup; flashing the ROM will overwrite device partitions such as ztepersist and splloader.

```
spd_dump.exe --wait 300 exec_addr 0x65012f48 fdl <fdl1> 0x65000800 fdl <fdl2> 0xb4fffe00 \
  exec path <临时目录> write_parts <zte-f50-b09\> e userdata reset
```

It writes all `.bin` under `zte-f50-b09\` (including splloader, ztepersist, the 2GB super, misc), about 2.7GB in total.

### 3. root + Patched trustos

```
... exec path <bin目录> w trustos <bin\f50b09_t.bin> w boot <bin\magiskf50b09.img> reset
```

It only writes `trustos_a` and `boot_a` for the current slot (slot a) and does not erase userdata. `f50b09_t.bin` is 5178856 bytes (MD5 prefix a110ecb1), the same as `trustos.bin` in the author's package. The boot used is `magiskf50b09.img` (0e9e8a4d); the author kkroot's `boot.bin` (f2e8db4a) is another file; both are Magisk images. After flashing, `ro.boot.flash.locked` still shows 1, but Linux can boot.

### 4. adb

After flashing B09 or a factory reset following userdata shrinking, adb is still available: this ROM includes UFI-TOOLS (`com.minikano.f50_sms`) and the Magisk stub; `persist.sys.usb.config=adb` and `persist.adb.tcp.port=5555` are stored in the persist partition and survive a factory reset. Only the first time right after flashing B09 do you need to enable it with the "temporary wireless adb tool" (see Part 5). The firmware's adbd does not verify keys: `ro.adb.secure=1`, but it can connect even if `/data/misc/adb/adb_keys` does not exist, and pairing is not required.

### 5. Magisk

1. `adb install Magisk_28103_origin.apk`. After rooting, only the stub is on the device, and the version shows `1.0`.
2. Open the app and do "repair environment", then reboot.
3. Connect to the screen with scrcpy and grant root permission to Shell.
4. `adb shell su -c id` should be `uid=0`. Before repair, `su` is not in PATH; only `/debug_ramdisk/su` exists.

After the factory reset triggered by shrinking userdata, the Magisk app is still there, but you need to repair once more and authorize once more.

### 6. Installer and Shrinking userdata

The installer uses the PowerShell version `install.ps1` (this machine has no lz4). Before running it in Git Bash, three environment pitfalls must be handled first:

```sh
# 1) PowerShell 5.1 找不到 Get-FileHash:Git Bash 把 PowerShell 7 的模块路径排前面了
export PSModulePath='C:\Program Files\WindowsPowerShell\Modules;C:\WINDOWS\system32\WindowsPowerShell\v1.0\Modules'
# 2) 校验自定义包时 Git 自带的 GNU tar 会把 F:\... 当成远程主机(Cannot connect to F: resolve failed)
export PATH="/c/Windows/System32:$PATH"
# 3) 否则脚本自更新后重新执行,输出被吞
export MU300_NO_SELF_UPDATE=1
```

Read-only check: `install.ps1 -Check -Lang en`.

Shrinking userdata uses an answer file (`-AnswersFile`). For answer variables, see the header comments of `install.sh`. If any variable is missing, the installer reports `no answer to the question ... set MU300_ANS_xxx` at the prompt and aborts, and when it aborts nothing has been written.

```
MU300_LANG=en
MU300_ANS_MAKE_ROOM=yes
MU300_ANS_LINUX_GIB=198
MU300_ANS_ERASE_ANDROID=ERASE
MU300_ANS_REBOOT=yes
```

Result: userdata shrank from 228.19 GiB to 30.19 GiB, leaving 198.00 GiB free after it, and Android went through recovery to factory reset.

### 7. Installing the Debian Package

Continuing the installation with a custom package fails: `The prepared installation cannot be continued: this installer's tools or the package differ`. The reason is that the payload identity in the transaction was calculated during shrinking (when there was no package), and the identity changes when installing the custom package. The workaround is to add `-NoResume`. At the start of the area there is a token written by the installer itself; it will prompt "unpartitioned space is not empty", so answer `MU300_ANS_OVERWRITE=overwrite` (this area was carved out by yourself, and you confirm it is empty).

Complete answer file:

```
MU300_LANG=en
MU300_ANS_PASSWORD=<至少6位>
MU300_ANS_DEFAULT_LINUX=yes
MU300_ANS_BOOT_ATTEMPTS=5
MU300_ANS_ADB=yes
MU300_ANS_GPU=yes
MU300_ANS_HOTSPOT=yes
MU300_ANS_VPN=no
MU300_ANS_PANEL=no
MU300_ANS_CONFIRM=INSTALL
MU300_ANS_REBOOT=yes
MU300_ANS_OVERWRITE=overwrite
MU300_ANS_SYSTEMS=1
MU300_ANS_KERNEL=7.3
```

Command:

```
install.ps1 -Lang en -NoResume -Package <包目录> -AnswersFile <answers>
```

After installation the device automatically reboots into Linux. In this installation log, the area offset is 38700843008, size 198.0 GiB, ext4 is created, and it writes the Linux area, boot_b, and a 32-byte misc, without touching boot_a, GPT, or userdata.

After installation, `/etc/mu300/adb` on the device is `on` and `adb_auth` is `keys`, meaning USB adb only allows keys from `/etc/mu300/adb_keys`.

### 8. Post-Installation Environment Setup

When the device was set up it had no Internet and the clock was stuck at Oct 17. So the flow was: run `tools/proxy.py` on the computer (a minimal HTTP/CONNECT proxy listening only on 127.0.0.1:7890) → `adb reverse tcp:7890 tcp:7890` → sync the time in the device first → temporarily write the apt proxy `/etc/apt/apt.conf.d/99tmp-proxy` and the docker drop-in `99tmp-proxy.conf` → run `tools/setup-env.sh` as root on the device. `device-online.sh on|off` wraps these steps as a switch, and `off` deletes the proxy configuration on the device and stops the proxy.

The script installed: `zsh git sudo curl ca-certificates zoxide fzf lsd duf neovim fastfetch openssh-server docker.io docker-cli docker-compose`. User `wray` was created with `useradd -m -s /usr/bin/zsh -G sudo,docker`, and the SSH public keys were taken from Windows' `authorized_keys` (3 keys). Note that the script is sent to the device via heredoc; unescaped `$(...)` inside it will be expanded early on the computer, so the password must be set separately with `chpasswd`. oh-my-zsh + powerlevel10k + `zsh-autosuggestions` + `zsh-syntax-highlighting` were all installed; `.zshrc` and `.p10k.zsh` were taken from `wray-lee/dotfiles` (the `archlinux` plugin in zshrc is harmless on Debian; the clash/nas/n2n aliases are from the original machine's configuration and do not work here). Docker 28.5.2 uses overlay2, cgroup v2 + systemd; `/etc/docker/daemon.json` limits the log size, and `docker run hello-world` passes (pulling images through the proxy).

Verified after reboot: 192.168.77.1 is reachable after about 1 minute; SSH (key-based), docker, kernel 7.3.0, and `mu300-update` disabled all persist. The first `systemctl is-system-running` was `degraded` (leaving a failed marker), and it recovered after `systemctl reset-failed`.

### 9. Current USB Network State

The USB gadget is NCM (Windows 11 has built-in driver `UsbNcm Host Device`, so no driver installation is needed). `usb0` and `wlan0` are bridged into `br-lan`; the device IP is 192.168.77.1/24, the device side provides DHCP and DNS, and the computer gets 192.168.77.111 (NIC name "Ethernet 8"), restoring automatically after reboot. Kernel `ip_forward=1`. The NAT (masquerade) to the uplink is added by `mu300-mobile-data.service` after mobile data connects, and this device has no SIM (`+CME ERROR: 10`, log `no card in SIM1`), so the computer cannot access the Internet via USB for now. After inserting a SIM, in theory 5G would automatically be shared with the computer via USB and Wi-Fi hotspot `FRayWrt` (SSID and password already imported from Android), but this has not been tested. Conversely, "computer gives the device Internet access" requires no configuration change; use `device-online.sh` above. If you want to make it Windows ICS, administrator privileges are required; this was not done.

## 4. How This Debian Image Was Made

This is not the project's official image. The official project only releases Ubuntu 24.04 / 26.04 and OpenWrt; the Debian 13 build in `docs/DISTROS.md` only says "same package names as Ubuntu" and has not been tested on real hardware. This image was built by a background agent in WSL.

- The base is `debian:unstable` (arm64, requires qemu binfmt). Dockerfile patches: `docker-compose-v2` changed to `docker-compose`, and `docker-cli` added.
- Patches to `assemble.sh`: `KREL` and `UBUNTU` can be overridden with `MU300_KREL` and `MU300_UBUNTU_RELEASE`; added `/release` mount to reuse the release's bundled `opt/mu300`, `etc/mu300`, etc.; fixed the issue where an NTFS checkout caused the overlay to become 1000:1000 / 0777 (even `/`, `/etc`, and `/usr` were set to 777), restoring ownership and permissions according to the release manifest.
- Kept the identities and filenames of `SYSTEM=ubuntu-26.04` and `OS=ubuntu` in the manifest to pass the installer's whitelist, replaced only the rootfs payload, updated `SHA256_ROOTFS` and `SHA256SUMS`, and removed the signature (the package is unsigned and only for local use).

## 5. The sid Bug in the Wi-Fi Client and the Patch

When connecting to the router, `wifi-client connect` reports `could not build the wpa_supplicant configuration`.

**Troubleshooting process.** The user first saw "the radio is an access point right now … cannot scan either" (a normal prompt); after following the prompt and running `connect`, the above error appeared. `grep -n "could not build the wpa_supplicant" /opt/mu300/bin/wifi-client` located it at line 832, which calls `network_block()` (around lines 733–755). In the function, `h=$(printf '%s\n' "$2" | wpa_passphrase "$1" | sed … psk=<64位hex>)`; if `h` is empty, it does `return 1`. Trying `printf '%s\n' testpass1234 | wpa_passphrase test` directly on the device produced no output at all.

**Root cause.** In Debian sid's `wpasupplicant 2.11`, when `wpa_passphrase` reads the password from a pipe, it calls `tcgetattr` on stdin, which fails on a non-terminal with no output, so `network_block()` cannot get the PSK hash. The older Ubuntu version does not have this problem.

**Patch approach.** If `wpa_passphrase` succeeds, use the hash as before; if it fails, fall back to `psk="密码"` and let `wpa_supplicant` calculate PBKDF2 itself. The password length must be 8–63 characters. The configuration file is 0600 root; the SAE path already writes plaintext `sae_password`, so the security is equivalent. Unit-verified outputs for WPA2, WPA2/WPA3 (SAE), open network, and short password (returns failure) are all correct. Limitation: there may be problems when the password contains non-ASCII characters or double quotes; this was not tested.

**Complete fixed version of `network_block()`** (replacing the function of the same name in `/opt/mu300/bin/wifi-client`, around lines 733–760; everything else unchanged):

```sh
# the supplicant's network block. The name goes in hex, so any byte (quotes, UTF-8) is taken as it is. The
# passphrase goes in as wpa_passphrase's hash, handed to it on stdin (an argument would be on its command line
# for ps), and its "#psk=" comment with the plain passphrase is left out. SAE cannot use the hash: with SAE it
# also goes in as sae_password, which is why the file is root's alone.
# Debian sid: wpa_passphrase 2.11 calls tcgetattr on stdin and prints nothing when piped, so h is empty there;
# fall back to a quoted passphrase, which wpa_supplicant hashes itself (8..63 characters, same 0600 root file).
network_block() {  # network_block SSID PASS SAE
    printf 'network={\n\tssid=%s\n' "$(hex "$1")"
    if [ -z "$2" ]; then
        printf '\tkey_mgmt=NONE\n'
    else
        h=$(printf '%s\n' "$2" | wpa_passphrase "$1" 2>/dev/null | sed -n 's/^[[:space:]]*psk=\([0-9a-fA-F]\{64\}\)$/\1/p')
        if [ -n "$h" ]; then
            printf '\tpsk=%s\n' "$h"
        else  # wpa_passphrase failed (sid)
            [ "${#2}" -ge 8 ] && [ "${#2}" -le 63 ] || return 1
            printf '\tpsk="%s"\n' "$2"
        fi
        if [ "$3" = 1 ]; then
            # WPA2, WPA2/WPA3 and WPA3-only networks alike; WPA3 requires management frame protection
            printf '\tkey_mgmt=WPA-PSK SAE\n\tieee80211w=1\n\tsae_password=%s\n' "$(hex "$2")"
        else
            printf '\tkey_mgmt=WPA-PSK\n'
        fi
    fi
    printf '}\n'
}
```

The only difference from the original is this one place:

```diff
-        [ -n "$h" ] || return 1
-        printf '\tpsk=%s\n' "$h"
+        if [ -n "$h" ]; then
+            printf '\tpsk=%s\n' "$h"
+        else  # wpa_passphrase failed (sid)
+            [ "${#2}" -ge 8 ] && [ "${#2}" -le 63 ] || return 1
+            printf '\tpsk="%s"\n' "$2"
+        fi
```

## 6. Reverse-Engineering Results for the "Temporary Wireless ADB Tool" and the Wireless adb Mechanism

### 1. Sample

Analyzed was `opener.exe` (the original is `O:\F50\临时打开无线ADB工具【…】.exe`), completed by the background agent using static unpacking + Unicorn emulation + Go disassembly.

- SHA256 `34a7ebf72fb636e34cbffa4981f2a7bffbb88c9e51a463b67ec759977432edf6`.
- PE32+ x86-64, Go 1.23.7, custom `NM$L` packer, Garble obfuscation (function names changed, strings decrypted at runtime).
- The payload in the packer is compressed with LZMA raw (lc=7, lp=0, pb=4); after decompression it is 38,743,273 bytes, VA = file offset + 0x140001000.
- Four files are embedded: `AdbWinUsbApi.dll`, `AdbWinApi.dll`, `adb.exe`, `zreq.exe`. `zreq.exe` is a 32-bit Go program (source path `/Users/kano/GolandProjects/awesomeProject/main.go`), with SHA256 matching `O:\F50\kkfile\bin\zreq.exe`. This version does not have `adb.com` / `zreq.com`; those may be from another version.

**First, a correction to my earlier wrong judgment**: I once said it sends AT commands in 6 steps over serial port `\\.\COM%u`; that was wrong. The sample contains no serial APIs at all (no `SetCommState`, `GetCommState`, `SetupComm`, `PurgeComm`, `COMMTIMEOUTS`, `DCB`, and no COM1..9 or 115200), and the `\\.\COM%u` string in memory comes from a Go standard library path constant. The message "Cannot operate the port, please rerun this program" is not a serial error either: it is printed in step 1 when the literal `result` cannot be found in `zreq`'s stdout, and "port" refers to the USB port mode `USB_PORT_SETTING`. In the real trace, `zreq … usb_port_switch=0` hung for about 25 seconds and then exactly this sentence appeared. Lesson: strings in memory dumps are obfuscated; use real static unpacking.

### 2. The Six Steps

| Step | Channel | Target | Content |
|---|---|---|---|
| 1/6 | HTTP goform (`zreq`) | `192.168.0.1:8080` | `USB_PORT_SETTING&usb_port_switch=0` (turn off first); if stdout does not contain `result`, report "cannot operate port" and exit |
| 2/6 | HTTP goform | Same as above | `USB_PORT_SETTING&usb_port_switch=1` (turn on again) |
| 3/6 | HTTP goform | Same as above | `REBOOT_DEVICE` (reboot device) |
| 4/6 | adb USB | Device | `adb wait-for-device`; on success print "found device." |
| 5/6 | adb shell USB | Device | The 10 commands below; `cat smb.conf` output must contain `adbd`, otherwise "configuration failed!" |
| 6/6 | SMB (TCP 445) | `192.168.0.1` | Guest (capital G) / empty password; list shares, skip `IPC$` / `ADMIN$` / `C$`, mount normal shares and `ReadDir(".")`, total timeout 100 seconds; on failure report "verification failed!" |
| Afterward | adb TCP | `192.168.0.1:5555` | `adb connect 192.168.0.1` |

The 10 commands in step 5 (verbatim):

```

setprop persist.adb.tcp.port 5555

```

The original program's idea was: the "switch" for wireless adb is Samba's `preexec = start adbd`; each time someone (Guest) connects to an SMB share, Samba executes `start adbd`, and adbd reads `service.adb.tcp.port` / `persist.adb.tcp.port` = 5555 and starts listening. But **in actual testing this was not the key on this firmware** (see below).

### 3. HTTP Login Algorithm (zreq)

Base address `http://192.168.0.1:8080`; request headers `User-Agent: Mozilla/5.0`, `Referer: http://<ip>:8080/index.html`, `Content-Type: application/x-www-form-urlencoded`, `Cookie: <登录后 Set-Cookie 的第一段>`.

- LD: `GET /goform/goform_get_cmd_process?isTest=false&cmd=LD&_=<毫秒>` → `LD` in JSON.
- Login: `H1 = SHA256(password).upper()`, `H2 = SHA256(H1 + LD).upper()`, `POST /goform/goform_set_cmd_process`, body `goformId=LOGIN&isTest=false&password=<H2>`, take the first segment of `Set-Cookie` as the Cookie. The default password is in the script (`f50_wireless_adb.py`'s `DEFAULT_PWD`).
- Get version information: `GET …cmd=Language,cr_version,wa_inner_version&multi_data=1`; get RD: `GET …cmd=RD`.
- AD: `H3 = SHA256(wa_inner_version + cr_version).upper()`, `AD = SHA256(H3 + RD).upper()` (note it is RD, not the JSESSIONID used in the U20 script).
- The final POST body is generated by Go's `url.Values.Encode()`, i.e. sorted by key.

### 4. What USB_PORT_SETTING Actually Does in the Web Backend

From decompiling `/system/priv-app/ZteWebServer/ZteWebServer.apk` (process `com.zte.web`, listening on 8080, `sharedUserId=android.uid.system`). The full report is in `F:\Projects\tmp\f50\zteweb\notes\`.

**`USB_PORT_SETTING` does only one thing: write the system setting `Settings.Global adb_enabled` (1 is on, 0 is off, any other value is treated as 0).** It does not write `persist.sys.usb.config` / `sys.usb.config`, does not call `UsbManager`, does not execute shell, does not send broadcasts, does not reboot, and returns success even if it does not actually take effect. The status query `cmd=usb_port_switch` also reads `adb_enabled`, not the real USB state.

What actually takes effect is system_server (evidence from `services.jar` in the B09 backup of the same device):

- `AdbService.setAdbEnabled()` **continues only when the value actually changes; if it is the same value, it returns directly**. On a real change, it does `ctl.start adbd` / `ctl.stop adbd` and calls back `UsbDeviceManager`.
- `UsbDeviceManager.setAdbEnabled()`: on → `persist.sys.usb.config="adb"`; off → `"charging"`; then reconfigure `sys.usb.config`.
- At boot, `AdbService.systemReady()` does the reverse: reads `persist.sys.usb.config`; if it contains `adb`, set `adb_enabled` to 1, otherwise 0, **overwriting the value last written into Settings by the web page**.
- In init: `on post-boot && property:sys.usb.config=none` → `setprop sys.usb.config ${persist.sys.usb.config}`; `on property:sys.usb.config=adb && property:sys.usb.configfs=1` → `start adbd`.
- SettingsProvider also does not notify observers when "writing the same value", so repeatedly writing 1 is a complete no-op.

`REBOOT_DEVICE` first returns success, then after 500ms `PowerManager.reboot("manualreboot")`. `UsbTools` (write `rndis,diag,diag_mdm,adb` when on, write `rndis` when off, and finally reboot unconditionally) is only called by `DEVELOPER_MODE_SETTING` / `SET_DEVICE_MODE`, while this APK's `DeveloperModule` only registers `USB_PORT_SETTING`, so this path is unreachable on this firmware. The web UI is `index.html#usb_port` → `js/adm/usb_port.js`; what is submitted is `goformId=USB_PORT_SETTING` + `usb_port_switch=1/0`, and **you must click Apply for the request to be sent**; just clicking the radio does not send it. The APK contains no code that writes `service.adb.tcp.port` / `persist.adb.tcp.port` or starts/stops adbd; the `persist.adb.tcp.port=5555` on the device is a persistent property that the ROM already has.

### 5. "How to Enable It When There Is No adb"

- **Wired adb**: make `adb_enabled` undergo a real 0→1 change. The framework will immediately `ctl.start adbd`, write `persist.sys.usb.config` as `adb`, and reconfigure USB; code-wise, no reboot is needed. `REBOOT_DEVICE` just makes the USB reassemble stably after reboot according to `persist=adb`, and is the most reliable approach.
- **Why only clicking the switch on the web page does not work**: if the switch was already 1 (what the UI shows is `adb_enabled`, which is neither persist nor the actual adbd state), submitting 1 again is the same value and is short-circuited by two layers into a no-op; `persist.sys.usb.config` is not written as `adb`, and at reboot `systemReady()` recalculates from persist and goes back to 0, so there is still no adb, while the UI keeps showing ON. **The original tool first sends 0 and then 1, which forces a real 1→0→1 change.** To do it manually: on the web page, turn it off first, click Apply, then turn it on, and click Apply again.
- Secondary possibilities: the radio was clicked but Apply was not; the reboot happened before the asynchronous persist write; under certain SIM states, `ZTE_ADB_USB_SECURITY_RESTRICTION` forcibly turns off adb; adbd or the USB endpoint is stuck and requires re-enumeration.
- **TCP listening for wireless adb**: at startup, adbd reads `service.adb.tcp.port` / `persist.adb.tcp.port`; this ROM includes `persist.adb.tcp.port=5555`, so adbd listens on TCP 5555 as soon as it starts. The Samba approach can neither be done on this firmware (`smb.conf` is immutable) nor is it necessary.

On-site confirmation (when the device is in Android, query after logging in to the web interface): `usb_port_switch → '1'`, `developer_mode_enable → '1'`; on the device `settings get global adb_enabled = 1`, `persist.sys.usb.config = adb`, `sys.usb.config = rndis,mtp,adb`, `init.svc.adbd = running`, `persist.adb.tcp.port = 5555`. The two diagnostic interfaces can be used after login without adb:

- `GET /goform/goform_get_cmd_process?isTest=false&cmd=usb_port_switch` → `adb_enabled`
- `GET /goform/goform_get_cmd_process?isTest=false&cmd=developer_mode_enable` → whether `persist.sys.usb.config` contains `adb`

If the former is 1 and the latter is 0, that is the branch described above where "the UI shows ON but persist has no adb"; just do 0 then 1.

Risk: sending `usb_port_switch=0` alone (a real 1→0) will write `persist.sys.usb.config` as `charging`; if the subsequent 1 does not succeed, after reboot USB will only have charging, and RNDIS / ECM and the web backend may both become unreachable. **Do not send 0 alone when you have no recovery method**; if the original program or our script fails after step 1, this is the bad state left behind. The framework-side evidence comes from the B09 backup image of the same device; if the device is not running this firmware, the details of `services.jar` may differ.
